## Finding F1 — Cloudflare Queues REST publish shape is stale (adapter defect)

`src/platform/queue/cloudflare-queues.ts` `publishWire` sends `{"body": <value>, "content_type": ...}` to `POST /accounts/{account_id}/queues/{queue_id}/messages`. The live Cloudflare API (verified by the Lead on 2026-09-21 with the account API token, on the dedicated probe queue `zeck-preview-main-executions-probe`) REJECTS that shape:

- `{"body": "<string>", "content_type": "json"}` → HTTP 400, provider code 10207, `Validation error: Expected object, received string at "body", or Expected array, received string at "body"`;
- `{"messages": [ ... ]}` (any wrapper) → HTTP 400, `Validation error: Required at "body"`;
- the accepted shape is the BARE object `{"body": <plain JSON object>}` → HTTP 200 (`result.metadata.metrics.backlog_count` present).

Additional live contract facts from the same probe:

- REST pull (`POST .../messages/pull`) returns HTTP 405 `messages cannot be pulled unless http_pull mode is enabled` until the queue carries an `http_pull` consumer (created via `POST .../queues/{queue_id}/consumers` with `{"type": "http_pull"}` → HTTP 200, or `wrangler queues consumer http add`); after that, `POST .../messages/pull` with `{"batch_size": n}` → HTTP 200 with `result.messages[]`;
- the ack shape was NOT exercised by the Lead (no message remained to acknowledge) — verify it against current public Cloudflare documentation and record the verification basis honestly.

Requirements:

- update `publishWire` to the verified live contract (bare `body` object; drop the stale `content_type` handling or replace it with whatever the current public schema documents);
- verify `pullWire`/`settleWire`/`settle` shapes against the current public Cloudflare Queues REST documentation; correct what drifted, preserve every fail-closed behavior (401/403 permanent, 404 permanent, 429/5xx transient, bounded retries, redaction);
- update the unit tests/fakes that pin the wire contract to the corrected shapes;
- annotate `deploy/README.md` (queue provisioning notes): a REST-probeable queue needs the `http_pull` consumer — provisioning knowledge, not code.

## Finding F2 — deploy/smoke artifact-name drift check ignores the preview branch slug (tool defect)

`deploy/smoke.ts` (the `probeProviderObjectStore` cross-check) calls `computeResourceNames(conventions, environment, resources)` WITHOUT the preview branch slug, while the same smoke run's identity document (with `--branch main`) names the resource `zeck-preview-main-artifacts`. The check therefore reports a correctly-named per-branch bucket as drift: `zeck-preview-main-artifacts != zeck-preview-artifacts` → the concern reads `unavailable` although the bucket is reachable. Fix: thread the preview slug through every manifest-computed name comparison in the smoke (audit the whole file for the same omission), with a regression test pinning the per-branch expected name.
