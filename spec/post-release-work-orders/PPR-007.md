**Status:** AUTHORIZED / WAVE C (correction)

**Base:** current governed main at dispatch
**Origin:** the live plane's first open finding (F1, frontier 85efbb7): the deployed preview at https://zeck-preview-main.vercel.app serves the API plane only — 10 experience-surface journey steps and all 22 workload-family disclosures are honestly not-served (`/console/*`, `/trust/*`, `/admin/*` answer the honest Fastify 404 JSON; PPR-001's console composition exists in `apps/dashboard/**` but is not deployed; `ZECK_EXPERIENCE_DEPLOY_TOKEN` is already set on the Vercel project). ## Objective

Serve PPR-001's console composition (the `apps/dashboard` projection surface) on the public preview as a second serverless function, routed at `/console/*`, `/trust/*`, `/admin/*` and the root landing `/`, behind repository-resident configuration only — with the honest unbound mode preserved (when the experience credential is not materialized, the pages still serve and render their designed honest states; nothing fabricates).

## Requirements

1. **Dashboard request-listener export** — `apps/dashboard/index.ts` exports the composition's per-request handler as a reusable builder (e.g. `createDashboardHandler(options)` returning the `(request, response) => void` listener that `createDashboard`'s `createServer` wraps today), with `createDashboard` and the direct-execution entry unchanged in behavior. The export is additive; the existing surface (`createDashboard`, `DashboardOptions`) keeps its contract.

2. **The experience function entry** — a Vercel function entry (NEW file) that builds the dashboard composition ONCE PER ISOLATE (module-level singleton — PPR-006's cold-start pattern) and answers per-request. Environment contract: `ZECK_EXPERIENCE_API_URL` (the API plane base URL — the same origin in the preview), `ZECK_EXPERIENCE_TOKEN` (the materialized transport credential of the dashboard's reads; materialized from `ZECK_SECRET_EXPERIENCE_TOKEN_REF`), `ZECK_EXPERIENCE_APPLICATION_ID` (the application whose scope authorizes the dashboard's scoped reads). When the token is unbound/empty the entry must STILL SERVE — the dashboard pages render their designed honest unauthenticated/permission states (the projection surface's degradation); the entry fails closed only on structural misconfiguration (missing API URL or application id). Record this behavior in the docs.

3. **Routing + build composition** — the preview deployment serves BOTH functions: every `/console/*`, `/trust/*`, `/admin/*` path and the root `/` route to the experience function; every other path routes to the existing API function (PPR-006's entry, unchanged in behavior). The routing mechanism is the platform's sanctioned shape for a framework build + additional functions (verify against current Vercel documentation; `vercel.json` routes/rewrites or the equivalent — record the mechanism + doc source in the evidence). `deploy/build-vercel-output.ts` extended: the ESM specifier resolution + `type: module` marker + fail-closed verification apply to BOTH function graphs (the experience function's graph is walked with the same correction). The worker verifies the tool's transformation logic against a synthetic `.vercel/output` fixture (the worker holds NO Vercel credentials — every live build/deploy step is an honest NOT RUN with owner "Lead credentialed deployment run").

4. **Machine parity through the entry** — the 22 workload-family disclosure routes (`/console/playground/:family`) and the machine JSON views (e.g. `/console/usage/facts.json`, the validation-lab API surfaces) serve through the new entry exactly as the direct-execution host serves them — pinned by tests (the handler-level route table + representative renders; HTML presence, the availability disclosure, the machine JSON shapes).

5. **Environment contract manifests** — `deploy/manifests/variables.json` + `deploy/manifests/secret-references.json` carry the three experience variables (names, types, `holds` reference URIs — never values). These manifests are a SHARED ADDITIVE SURFACE with the concurrently-dispatched PPR-008: append your entries in your own region; do not reorganize existing content.

6. **Deployment contract documentation** — `deploy/README.md` + `deploy/PUBLIC-DEPLOYMENT.md` (PPR-002's status layer): the experience deployment contract — the env set above, the routing shape, the honest unbound mode, and the exact operator sequence the Lead runs after merge (set the experience env on the Vercel project → build via the committed pipeline → local artifact proof for BOTH functions → `vercel deploy --prebuilt --prod` → the journey harness re-run for the 10 experience steps + 22 disclosures). `deploy/PUBLIC-DEPLOYMENT.md` is also a shared additive surface with PPR-008 — append your sections, do not rewrite theirs.

7. **No credentials, no deployment by the worker** — the worker never deploys and never touches live Vercel (the Lead owns the credentialed run; `ZECK_EXPERIENCE_DEPLOY_TOKEN` already exists on the project). Every live-Vercel boundary is an honest NOT RUN with owner "Lead credentialed deployment run".
