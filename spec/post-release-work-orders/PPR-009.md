# PPR-009 — LiveKit Realtime Rail
Status: Architect-authorized successor work.
Base: 338cc46c1f6081c1cbfa9de94e607982a74a159d

## Objective
Integrate LiveKit as one replaceable realtime/WebRTC rail. Do not fork LiveKit.

## Worker scope
- first reconcile the existing realtime implementation against its own documented admission invariant: session-start rail side effects require policy -> capability -> secret mediation (budget only when a paid inference reservation exists), and human-transfer rail side effects require policy -> capability -> secret mediation;
- implement a LiveKit-backed RealtimeRail adapter;
- add a provider-neutral short-lived realtime client-access port if required;
- keep LiveKit SDK/protocol types in adapter files;
- use connections/secret mediation rather than moving API keys into domain or API contracts;
- use opaque/non-PII room and participant identifiers;
- preserve stable Zeck operation/idempotency keys;
- do not claim that the current injected single-rail composition is a multi-provider failover system; rail selection/failover remains a later provider-routing work order;
- represent actual transport semantics honestly; WebRTC delivery acknowledgement must not be promoted into an unconditional exactly-once guarantee;
- add fake-client tests for open, data delivery, close, retry/replay and failure normalization;
- do not claim external LiveKit execution until a credentialed environment has been exercised.

## Non-goals
- no LiveKit fork;
- no LiveKit-specific types in domain ports;
- no replacement of Execution Compiler, policy, capabilities, budget, verification or evidence;
- no LiveKit Agent handoff/state as a second agent authority;
- no permanent dependence on LiveKit Cloud;
- no live-provider claim without evidence.

## Required acceptance
1. provider dependency is adapter-local;
2. existing realtime tests pass;
3. fake-client conformance proves retry convergence at the Zeck protocol level;
4. short-lived client access is never persisted/logged;
5. API secret never crosses the public/domain boundary;
6. policy -> capability -> budget-when-paid -> secret admission remains before every governed side effect, including session open and human transfer;
7. stale tenant/session callbacks still fail closed;
8. provider failure maps to provider-neutral errors;
9. provider availability remains NOT RUN until externally proven;
10. alternative realtime rail could be substituted without changing the RealtimeSession domain.

## Reference facts
LiveKit's current JS server SDK is v2.19.1 and supports Node, Deno and Bun; it manages rooms and creates access tokens. The documentation requires API secrets to remain on the backend, states that join tokens encode participant identity/room/permissions, and explicitly warns against PII in room or participant identity. LiveKit Agents support Node.js and Python realtime participants and multimodal voice/video/data workflows. Cite current sources in the PR evidence rather than hardcoding them into domain contracts.
