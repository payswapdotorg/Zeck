## Requirements

1. **The realtime-rail conformance contract** (NEW `tests/conformance/realtime-rail/` or the repository's established conformance location — survey `tests/` first and follow the existing convention) — a SINGLE suite that runs against ANY `RealtimeRail` implementation: the open/deliver/transfer/close lifecycle over neutral coordinates; the idempotency-key convergence (re-issue the same key ⇒ the same acknowledgment, `replayed: true`, exactly-once upstream effect); the failure normalization (an unreachable/exhausted/refused upstream maps to the port's declared failure shapes — no vendor error strings cross); the honest delivery semantics (bounded previews + artifact references only, never raw media); the descriptor's neutral vocabulary (rail capability id + channel kinds, no vendor identifiers); the opaque non-PII channel-session refs. The simulated rail PASSES this suite by construction (it is the semantic reference); the LiveKit adapter MUST pass the same suite against a REAL local LiveKit server where the sandbox permits one (see 6).

2. **The LiveKit rail adapter** (NEW `src/modules/deployments/adapters/livekit-realtime-rail.ts` or the established adapter location) — implements `RealtimeRail` over the LiveKit Server SDK (`livekit-server-sdk` — use the published package UNMODIFIED; **no fork**): `openSession` maps the neutral session request to a LiveKit room creation + a SHORT-LIVED participant access grant; `deliverTurn` maps to the room's data/track delivery semantics; `transferCall` maps to the agent/handoff pattern; `closeSession` to the room close. ALL LiveKit types (Room, AccessToken, VideoGrant, etc.) stay INSIDE the adapter file(s); the port sees only neutral shapes. Credential materialization happens INSIDE the adapter through the connections vault (the secret-mediation pattern) — the LiveKit API key/secret NEVER appears in a port shape, a config default, a log line, or a test fixture (synthetic fixtures follow the repository's established `sk-…` synthetic style). Room names and participant identities are OPAQUE, NON-PII, derived from the neutral coordinates (e.g. deterministic hashes of the session refs — never user-provided strings verbatim).

3. **The short-lived client-access seam** (NEW, the adapter's public surface) — a bounded issuance that mints a SHORT-LIVED (≤ the session policy's ceiling, defaulting minutes not hours) client access grant for a browser to join the rail's channel, derived ONLY after the frozen admission order ran (policy → capability → budget → secret mediation); the grant carries the opaque session ref, expires, and is single-purpose (join, not administer). This seam is the one place client-facing credentials exist, and its shapes stay vendor-neutral at the port level (a `clientAccess` descriptor the session service can project), with the vendor grant confined to the adapter.

4. **Failure normalization + retry/replay convergence** — the adapter maps every LiveKit failure mode (unreachable server, auth failure, room-not-found, quota/limit, disconnect) onto the port's declared failure shapes with `retryable` honestly derived; the idempotency-key ledger implements exactly-once upstream effects (the LiveKit server's own room idempotency where it exists; the adapter's durable key ledger where it does not — document which). A crash between the durable claim and completion is recovered by REPLAYING under the same key — no duplicate upstream room/grant, ever (the port's documented contract).

5. **Honest delivery semantics** — the adapter NEVER claims a delivery it did not perform: acknowledgments carry the upstream's real answer (or the honest failure); no fabricated latency/quality facts; previews are bounded as the port requires.

6. **No credentials ⇒ no real-availability claims** — the worker has NO LiveKit credentials for any external/managed LiveKit service, and none may be invented. Where the sandbox can run a LOCAL LiveKit server (the open-source `livekit-server` binary or its docker image), the conformance suite + integration proofs run against it over real WebSockets/localhost (a REAL rail, honestly labeled `local-livekit-server`); where it cannot, those boundaries are honest NOT RUN with owner "Lead credentialed run". The evidence record NEVER states or implies managed/production LiveKit availability. The manifests (`deploy/manifests/variables.json` + `secret-references.json`) gain the LiveKit credential REFERENCE names only (e.g. `ZECK_SECRET_LIVEKIT_API_KEY_REF`-style, following the existing naming grammar) — append-only, no values.

7. **The composition binding + docs** — where a real rail binds in the composition follows the established materialization-gate pattern (bound only when the environment materializes the LiveKit credential set; otherwise exactly today's simulated/unbound shapes — pinned both ways). `deploy/PUBLIC-DEPLOYMENT.md` gains the rail's section (append-only): the env contract, the honest availability state, the operator sequence for a future credentialed run.
