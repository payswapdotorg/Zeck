# PPR-006 — Vercel Hosting Adapter (Experience-Delivery Enabler)

**Status:** AUTHORIZED / WAVE B (correction)
**Program:** zeck-post-release-public-productization
**Base:** current governed main at dispatch
**Origin:** the Lead's credentialed live-preview provisioning run (2026-09-21, Task 58) provisioned the Vercel project `zeck-preview-main` (created; token effective) and completed the entire §3.2 converge-and-attest chain on the Lead rail (migrations on the live Neon authority, provider smoke, local-boot public smoke with identity verified at the exact revision, release record bound) — the remaining boundary to a public URL is the hosting configuration the repository does not yet carry. This work order supplies it. It adds NO authority and changes NO route: the deployed surface is the identical `createApiServer` public route table.

## Objective

Make `deploy/api.ts`'s bootstrap composition deployable to Vercel (Hobby — the non-commercial preview rail; the commercial boundary in `deploy/manifests/provider-tiers.json` and `deploy/PUBLIC-DEPLOYMENT.md` stays the recorded rule) behind repository-resident configuration only.

## Requirements

1. **Shared composition export** — refactor `deploy/api.ts` so the bootstrap composition (identity document, environment contract, `createApiServer` wiring, honest unbound domain seams) is exported as a reusable builder (e.g. `buildBootstrapApp(...)`), with the existing CLI `main()` unchanged in behavior (same boot document, same SIGTERM drain, same exit codes).

2. **Request-handler entry** — a Vercel function entry that builds the SAME composition once per isolate (module-level singleton; cold start builds, warm requests reuse) and answers per-request. Verify the current Vercel documentation for the sanctioned Bun runtime function configuration (`vercel.json` functions `runtime`) and use it; if the Bun runtime is not available for this shape, the Node.js runtime is acceptable — record the choice and its source. The route table, `/identity` semantics (exact-revision attestation via `ZECK_DEPLOY_GIT_REVISION`), `/health` fail-closed semantics, and every honest boundary (401 `AUTHENTICATION_FAILED`, 422 `CAPABILITY_UNAVAILABLE`) must behave identically to the CLI host — pinned by tests.

3. **vercel.json** — repository-resident, at the location Vercel requires, functions configuration pointing at the entry. The repository's architecture/governance tests must stay green (check `tests/architecture` for top-level structure pins — if a root-level file conflicts, use the documented functions-path placement and record the decision).

4. **Deployment contract documentation** — annotate `deploy/README.md` + `deploy/PUBLIC-DEPLOYMENT.md` (PPR-002 status layer) with the exact deployment-time environment variables the function needs (the preview materialization set: `ZECK_ENVIRONMENT`, `ZECK_DEPLOY_GIT_REVISION`, the `ZECK_SECRET_*_REF` bindings and their materialized values — names only, never values) and the operator sequence: deploy → `deploy:public-smoke -- --url <public-url> --environment preview --branch main` (the exact-revision identity verification against the deployed plane).

5. **No credentials, no deployment by the worker** — the worker never deploys (the Lead owns the credentialed run; the Vercel project already exists). Every live-Vercel step is an honest NOT RUN with owner "Lead credentialed deployment run".

## Verification

- Full battery per the worker runbook (typecheck, lint, unit, architecture, integration, full suite, governance, deploy:validate);
- unit tests: the adapter serves the identical route table (inject-based), the identity document equals the CLI host's for the same inputs, the singleton reuses the built app, and a wrong `ZECK_DEPLOY_GIT_REVISION` changes the attested revision exactly as the CLI host would;
- the local-rail proof: boot the CLI host from the refactored builder and run `deploy:public-smoke -- --environment local` (or the preview-rail equivalent the sandbox permits) — the refactor must not change any observable behavior.
