# PPR-015 — Real-user browser audit and public productization correction

**Status:** AUTHORIZED / READY FOR TECH-LEAD DISPATCH
**Program:** zeck-post-release-public-productization
**Authorization date:** 2026-09-25
**Dispatch base:** the exact live `main` head recorded in `spec/post-release-state/frontier-state.json` after this authorization commit; never use the historical pre-authorization SHA if `main` has advanced
**Owner:** Tech Lead + implementation worker(s)
**Maximum concurrency:** 3, but use the minimum needed; this order is intentionally designed so one worker can own the coherent browser-driven experience correction
**Origin:** live user report + architect verification of the public Zeck preview. The user-visible Home action lands on `/console`, while the intended discovery-first Home surface and its outcome explanation are not surfaced. The deployed plane currently exposes the discovery-first content in source code but not through the public navigation path. The previously accepted 12-journey/28-step public harness is therefore insufficient as a sole product-quality gate because it can report the structural journey as passing while a human following the visible Home/navigation grammar encounters the wrong experience.

## Objective

Use `agent-browser` as a real user would use the public Zeck site, discover every material product defect in the primary user flows, fix every defect that is within the public-productization surface and does not require a frozen-architecture change, then repeat the same browser journey on the corrected local build and on the deployed public plane.

The goal is not merely to make URLs return 200. The finished product must make the intended story immediately discoverable:

```
Describe an outcome
→ Zeck plans it
→ executes it under policy
→ returns it with evidence
```

A first-time user must also be able to discover the supported capability families, understand their current availability, start safely, inspect what happened, understand evidence/cost, validate/rerun, compare/reproduce, find trust/limits, discover agent integration, and find the deployment path without first learning Zeck's internal architecture.

## Known defects that MUST be reproduced and corrected

### 1. Home navigation defect

Current public behavior: clicking the visible **Home** control sends the user to `/console`.

Required behavior: **Home must open the actual discovery-first Home experience**, not the Developer Console landing page.

The exact public route may be `/`, `/home`, or another explicitly governed experience route if the hosting platform requires it, but:

- the visible Home control must resolve to that route consistently;
- the route must be reachable from a clean browser session;
- the route must render the discovery-first Home content;
- `/console` may remain the Developer Console route, but it must not masquerade as the product Home;
- the bare public origin must lead to the same user-understandable Home experience rather than silently dropping the user into an internal-console surface.

The Tech Lead must determine the smallest hosting-safe implementation. Do not reintroduce the previously diagnosed Vercel filesystem-phase workaround merely because it is familiar; prove the final route behavior with the browser.

### 2. Missing outcome explanation

The Home experience MUST visibly and prominently communicate the product promise, in substance:

> Describe an outcome. Zeck plans it, executes it under policy, and returns it with evidence.

Do not bury this statement below developer controls, internal terminology, or a console-only route.

### 3. Missing capability discovery

The Home/discovery experience MUST provide an obvious path to capability discovery and must expose all 22 workload families through the existing machine-manifest projection.

For every family, the user must be able to reach a family surface and see the truthful current availability state:

- available;
- requires access;
- provider-gated;
- NOT RUN.

Never manufacture a capability to make the browser journey look complete.

### 4. Visible-navigation routing defects

The current deployment can render dashboard route definitions that are not publicly reachable because Vercel's rewrite set currently only exposes the `/console/*`, `/trust/*`, `/admin/*` and `/assets/client.js` experience paths.

The browser audit MUST identify every visible navigation/CTA route that falls through to the API plane instead of the experience plane, including but not limited to:

- `/build` and its visible children;
- `/runs` and its visible children;
- `/deployments`;
- `/agents`;
- `/assets/artifacts`;
- `/assets/competences`;
- `/assets/connections`;
- `/improve/*`;
- `/command`;
- `/attention`;
- `/mode`;
- `/appearance`;
- any other route actually exposed by the rendered shell.

Only routes intended to be API-plane routes (for example `/identity`, `/health`, API resources and other machine endpoints) must remain on the API plane.

Do not solve this by rewriting every path indiscriminately. Preserve the two-function hosting composition and its API/experience boundary.

## Browser-audit protocol

The Tech Lead MUST perform the audit with `agent-browser`, following the browser skill's lifecycle:

```text
open
→ wait for load/network idle
→ snapshot -i
→ interact using fresh refs
→ re-snapshot after every navigation/dynamic change
→ capture screenshots where a visual finding matters
```

A raw HTTP probe is not a substitute for the browser audit.

The audit begins in a clean session at:

```
https://zeck-preview-main.vercel.app/
```

The browser must exercise the site as a first-time user, not by guessing or directly entering internal routes first.

## Required browser journey

The Tech Lead MUST start at the landing page and follow visible affordances. At minimum:

1. **Landing / Home**
   - determine the first meaningful headline and primary action;
   - click **Home** and verify it remains the Home experience;
   - verify the outcome explanation is visible without searching;
   - verify capability discovery is visible or one click away;
   - verify the next safe action is obvious.

2. **Capability discovery**
   - navigate from the user-visible discovery affordance;
   - verify all 22 families are surfaced;
   - open representative families across each availability state;
   - verify provider/access boundaries are honest and understandable.

3. **Safe start**
   - open the guided sandbox from a visible CTA;
   - verify the safety envelope is shown before execution;
   - verify provider/model selection is not exposed where the architecture forbids it.

4. **Execution**
   - perform the supported first-run flow with the permitted synthetic task;
   - verify the result surface is comprehensible to a first-time user.

5. **Inspection / evidence / cost**
   - follow visible result affordances;
   - verify result, route, verification, evidence and cost surfaces are reachable;
   - verify "How Zeck did it" is understandable without reading implementation terminology.

6. **Validation / comparison / reproduction**
   - follow visible links to Validation Lab;
   - inspect rerun/evidence surfaces;
   - reach compare/reproduce from the user flow.

7. **Trust / limits**
   - reach Trust & Limits from visible navigation;
   - verify policy/spend/sandbox/verification facts are understandable and honestly scoped.

8. **Agents / developers**
   - reach the visible agent/developer integration entry;
   - verify the onboarding path is actionable without requiring a repository checkout first.

9. **Deployments / work / library / improve**
   - traverse every visible top-level group and every visible child the browser exposes;
   - any route returning an API 404/422 where a UI page is promised is a product defect;
   - any visible label describing a capability that is not actually reachable is a product defect;
   - any UI surface that claims a capability is live while the underlying capability is gated is a product defect.

10. **Failure states**
   - intentionally exercise at least one honest unavailable/provider-gated boundary;
   - verify it explains what is missing and what the user can do next;
   - verify there are no blank screens, generic upstream failures, dead ends or misleading success states.

## Responsive / accessibility pass

Repeat the browser audit at:

- desktop viewport;
- tablet-sized viewport;
- mobile-sized viewport.

Also exercise keyboard navigation for the principal landing and discovery flow:

```
Home
→ capability discovery
→ safe start
→ result
→ evidence/trust
```

Check:

- visible focus;
- keyboard reachability of primary actions;
- no trapped overlays;
- usable touch targets;
- no unintended horizontal page scroll;
- readable hierarchy;
- active navigation state;
- reduced-motion behavior where a motion-sensitive surface exists.

## Defect classification

Every material browser finding MUST be recorded with:

```
finding id
→ exact route / interaction
→ reproduction
→ observed behavior
→ expected behavior
→ user impact
→ root cause
→ owning source surface
→ smallest viable fix
→ alternatives/trade-offs
→ verification
```

Classify findings as one of:

- routing / hosting;
- navigation / information architecture;
- discoverability / copy;
- capability-state disclosure;
- interaction / form;
- result / evidence comprehension;
- responsive / accessibility;
- runtime / API integration;
- provider / credential boundary;
- frozen-architecture constraint.

A finding that requires a frozen-architecture change, new authority, new durable state, weaker assurance, or provider semantics entering domain logic MUST NOT be patched ad hoc. Record the constraint and stop at the governed boundary for that item.

## Scope authority

This Work Order MAY change:

- `vercel.json` experience rewrites/redirects where required to expose existing dashboard surfaces;
- experience/dashboard routing projections;
- dashboard navigation and Home/discovery presentation;
- existing product copy/labels needed for correct first-time discoverability;
- tests and browser/e2e harnesses that protect the corrected public experience;
- deployment/evidence documentation owned by this Work Order;
- no-authority-change UI wiring needed to expose already-existing capabilities.

This Work Order MUST NOT:

- change frozen execution/policy/capability/budget/verification/evidence authority;
- create a second route/experience authority;
- create duplicate APIs for existing dashboard pages;
- invent capability availability;
- weaken the existing public error/NOT RUN semantics;
- alter historical validation evidence;
- turn provider-gated or unavailable infrastructure into PASS;
- broaden the work into unrelated backend features solely because the browser encountered an unavailable feature.

## Required regression protection

The correction MUST add or strengthen an automated regression surface so the same class of defect cannot return.

At minimum:

1. an authoritative list or projection of public experience routes derived from the existing dashboard route table, rather than a manually duplicated stale list where practical;
2. an automated check that every user-visible experience route is mapped to the experience function;
3. an automated negative check that API-only routes remain API-plane routes;
4. a browser smoke covering the Home → capability discovery → safe start path;
5. assertions for the outcome explanation and capability-discovery affordance;
6. assertions for broken visible navigation/CTA destinations;
7. responsive/keyboard regression coverage for the primary landing path where the existing test harness supports it.

The test must fail on the class of bug found here, not only on the exact current URLs.

## Evidence and deployment sequence

The Tech Lead MUST produce exact-revision evidence in this order:

```
clean current main
```

The final public verification MUST prove:

- Home opens the intended Home experience;
- the outcome explanation is visible;
- capability discovery is visible and all 22 families are reachable;
- the guided sandbox path is discoverable;
- the major result/evidence/trust/validation/integration paths are reachable through visible UI;
- no visible navigation control produces an unexpected API 404/422;
- API-only endpoints remain API endpoints;
- no browser console errors attributable to the product correction remain;
- desktop/tablet/mobile principal flows pass;
- keyboard principal flow passes;
- existing 12-journey / 28-step acceptance still passes;
- public smoke passes;
- exact revision is attested.

A second worker MAY be used only when a truly conflict-free test/harness surface can be separated without delaying semantic reconciliation.

A third worker should remain unused unless the Tech Lead can prove a clean boundary.

Workers must:

- start from the exact current main;

- never merge themselves;
