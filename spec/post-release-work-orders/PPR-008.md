# PPR-008 — Preview Credential Issuance & the Deterministic Sandbox Substrate

**Status:** AUTHORIZED / WAVE C (correction)
**Program:** zeck-post-release-public-productization
**Base:** current governed main at dispatch
**Origin:** the live plane's second open finding (F2, frontier 85efbb7): 7 credentialed journey steps (sandbox start, first execution, inspection, evidence/cost, validation rerun, export bundle) are honestly not-run owned by the Lead's credential boundary; the credentials authority is unbound in the bootstrap composition (honest 422 `CAPABILITY_UNAVAILABLE` today). **Lead decision (recorded):** the frontier's decision space offered (a) bind a credentials authority for the preview materialization set or (b) record the honest boundary as the product state. The decision is (a) BIND — the plan's acceptance gates require "first sandbox execution works" on the public preview; the Neon relational authority is provisioned, migrated and READY; the SQL adapters and services exist in `src/modules/**`; the honest-boundary alternative would leave the plan's own gate unmet. This work order binds the REAL authorities and supplies the deterministic sandbox substrate that drives a created sandbox execution to a terminal state — no model credentials, no fabricated facts, every unmaterialized shape keeps today's honest unbound behavior.

## Objective

When the preview environment materializes its authority set, the bootstrap composition binds the REAL seams — bearer authentication over the materialized transport token, SQL scope resolution, the credential lifecycle service, the execution service, the agents inventory — over the Neon `DatabasePort`, and a repository-resident deterministic substrate drives created sandbox executions to an honest terminal receipt. The preview's credentialed journeys become real; local/dev shapes are unchanged.

## Requirements

1. **The authority materialization module** (NEW `deploy/preview-authorities.ts` or equivalent) — reads the environment contract: `ZECK_DATABASE_URL` (the existing materialization pattern — the same value `/health`'s relational-state probe already uses) and `ZECK_TRANSPORT_TOKEN` (materialized from `ZECK_SECRET_TRANSPORT_TOKEN_REF`) plus `ZECK_PREVIEW_APPLICATION_ID`. When materialized, construct over the real `DatabasePort`: the bearer authenticator (`src/api/server.ts`'s factory) over the token→principal map; the scope resolver (`src/modules/auth/application/scope-resolver.ts`); the credential service (the SQL stores + idempotency in `src/modules/auth/adapters/` — the canonical wiring reference is `tests/integration/postgres/`'s credentials world); the execution service (`sql-execution-store` + `sql-executions-idempotency` + `createExecutionService` — the executions world is the reference); the agents inventory (`listAgentIdsOfApplication`) over the SQL registry. **Idempotent preview seeding:** ensure (create-if-absent, never duplicate) the tenant, the preview application (the env's id) and the transport credential's principal/membership rows so the token resolves and the scope derives on a migrated database — the seeding is runtime-idempotent (safe on every cold start).

2. **The composition binding** — `deploy/api.ts`'s `buildBootstrapApp`: when the preview authority set is fully materialized, bind the REAL seams (authenticate/scopeResolver/executions/credentials/agents inventory); otherwise EXACTLY today's unbound shape (local/dev behavior unchanged — pinned by tests both ways). The boot document reports which composition served (the honest unbound bootstrap vs the materialized preview authorities) — a new composition fact field, truthfully derived.

3. **The deterministic sandbox substrate** (NEW) — drives a created sandbox execution to a terminal state through the execution service's OWN governed state machine (start → run → complete; the legality rules are the service's, no bypass): a deterministic summarize result in the wire contract's receipt/result shapes, an honest verification outcome, step events on the same append-only ledger, and truthful zero-cost reporting for the deterministic substrate. It engages ONLY the preview materialization (never local/dev unbound shapes). Every substrate-produced record labels its origin honestly (e.g. execution metadata `origin: preview-deterministic-substrate`) — never masquerading as a model-backed run; the docs state what the substrate is and is not. The hook point (inline post-create drive in the composition, or the equivalent governed seam) is the worker's design choice — document it and its trade-offs in the evidence record.

4. **The issuance path documentation** — `deploy/PUBLIC-DEPLOYMENT.md`: how a transport credential is issued/bound on the preview (the `POST /credentials` lifecycle over the materialized authority, and the Lead's directly-materialized journey token), the substrate's honest label and boundary (no model-backed execution on the preview), the env contract. This file is a SHARED ADDITIVE SURFACE with the concurrently-dispatched PPR-007 — append your sections, do not rewrite theirs.

5. **Environment contract manifests** — `deploy/manifests/variables.json` + `deploy/manifests/secret-references.json` carry the authority variables (`ZECK_SECRET_TRANSPORT_TOKEN_REF` + `ZECK_PREVIEW_APPLICATION_ID`; the database URL is already contracted). Shared additive surface with PPR-007 — append in your own region.

6. **No credentials, no live deployment by the worker** — the worker never touches live Neon/Vercel. Integration tests run against the local real-PG rail (`ZECK_PG_TEST_URL`) exactly as the repository's integration suites do; every live-Neon/live-Vercel boundary is an honest NOT RUN with owner "Lead credentialed run".
