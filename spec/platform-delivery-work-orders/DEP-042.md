# DEP-042 — Fresh-Agent Integration Trial

Status: AUTHORIZED / WAVE P4 (dispatch-gated on DEP-040)
Dependencies: DEP-040 (the validated deployment chain); runs after or alongside DEP-041
Base: exact current `main` at dispatch

## Objective

A fresh CODING AGENT integrates Zeck through the agent-oriented public surface with zero maintainer intervention: discover the repository's agent entry paths (AGENTS.md, docs/developer/machine/ artifacts), read the machine manifests (openapi.json, capability-manifest.json, env-vars.json, error-codes.json, examples-manifest.json, integration-recipe.json), authenticate, create an application, configure a sandbox, run executions across the supported capability portfolio, retrieve results and evidence, list and rerun the validation library — using ONLY machine-readable artifacts and the public API. No human-oriented docs, no console browsing, no internal knowledge.

This validates the roadmap's agent-usability requirement: "A coding agent must be able to discover Zeck without chat with a maintainer… Examples should be copy/paste runnable and avoid hidden assumptions."

## Trial protocol

- The "fresh agent" persona consumes ONLY: AGENTS.md at the repo root, docs/developer/machine/**, the public API wire surface, and the SDK if the docs point to it. NO human docs, NO console, NO specs/work orders, NO src/ reading to figure out contracts (machine manifests are the contract source).
- The trial runs against a real locally-booted plane (real processes, real HTTP). The public-internet variant is the Lead credentialed boundary.
- The journey: agent discovery (AGENTS.md entry) → machine-contract reading (openapi/capability/env-vars/error-codes/examples/recipe) → auth → application create → sandbox config → executions across workload families (runnable set; provider-gated families are honest NOT RUN with named contracts) → results/evidence/cost retrieval → validation library list + rerun → export path.
- Copy/paste runnability is verified LITERALLY: examples from the manifests are executed as written; any hidden assumption (undeclared env var, unstated prerequisite, wrong path) is a finding.

## Allowed surfaces

The trial REPORT and findings are the deliverable. Fixes for surfaced defects within the owning surface: `docs/developer/machine/**` (manifest/docs fixes), `apps/dashboard/**` only if a machine-surface defect traces to the console's served artifacts. `scripts/fresh-agent-trial-dep042.ts` (the reproducible trial driver). `deploy/evidence/dep-042.json`. No `src/` edits — public-contract defects go to the Lead as merge notes.

## Acceptance criteria

1. The agent journey completes end to end through machine artifacts + public API with zero maintainer intervention (or every blocker is a recorded finding).
2. Every machine-manifest example that claims runnable status either runs as written or is a recorded finding with exact reproduction.
3. Each finding carries root-cause classification (Zeck / console / docs / harness / provider / access) and either a fix (with pin) or a Lead merge note.
4. Honest boundaries: provider-gated capabilities and unavailable engines are NOT RUN with named contracts/owners.
5. Governance, typecheck, lint, unit, architecture, integration stay green; existing pins stay in sync.
6. `deploy/evidence/dep-042.json` records the verified/notRun split.

## Required verification

Governance, typecheck, lint, full test suite; the trial driver run against a fresh real plane; every fix's regression pin.

## Reporting

The trial report separates Zeck defects, console defects, docs/machine-manifest defects, harness defects, provider limitations, missing credentials and environmental failures.

Workers do not change `spec/platform-delivery-state/*` and do not merge their own PR.
