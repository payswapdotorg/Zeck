# DEP-002 — Environment, Secret and Sandbox-Account Provisioning Automation

Status: AUTHORIZED / WAVE P0 (deployment chain — unblocked by DEP-001)
Dependencies: DEP-001 (the deployment foundation — delivered)
Base: exact current `main` at dispatch

## Objective

Automate the last manually-operated span of the deployment chain DEP-001 left
honest: turning the manifest-declared environment matrix, secret-reference
inventory and sandbox policy into a single reproducible operator path —
`provision` — that converges an environment class from repository truth:
resource plan (already DEP-001's `bootstrap.ts`), secret-reference
materialization scaffolding (templates and CI/operator variable skeletons —
never secret plaintext), and sandbox-account records (the disposable,
synthetic-data, quota-enveloped identities the preview/sandbox environments
need), with idempotent re-runs and classification-guarded teardown.

Provisioning is infrastructure-plane plumbing over the repository's manifests.
It must not create a second credential, identity, tenant or budget authority:
application-plane credentials stay governed by the credential service and the
`zeck-secret://` reference discipline; sandbox-account policy facts stay
governed by the DEP-014 quota/expiration surface; the manifests under
`deploy/manifests/` remain the only source of truth. The provision tool
materializes what the manifests declare — it never invents topology.

## Allowed surfaces

`deploy/**` (new `provision.ts`, extensions to `bootstrap.ts`/`teardown.ts`/
`validate.ts`, additive manifest rows under `deploy/manifests/`);
`deploy/PUBLIC-DEPLOYMENT.md` (operator recipe extension); deployment tests
under `tests/unit/deployment/` and `tests/integration/deployment/`;
`deploy/evidence/dep-002.json`. If a new non-secret environment variable is
genuinely required, `deploy/manifests/variables.json` and
`docs/developer/machine/env-vars.json` get the additive row (machine-manifest
sync is a required check). No `src/` module edits: the platform's
secret/identity/budget ports are consumed, never modified.

## Required behavior

- `bun run deploy:provision --environment <class>` (exact CLI shape may follow
  the house convention of the existing deploy tools) performs documented
  convergence for the target environment class: manifest validation →
  resource plan → secret-reference scaffold → sandbox-account records →
  post-convergence validation, with `--plan` (dry-run) and `--json` modes.
- Secret materialization stays external-only: the tool emits per-environment
  reference templates / CI variable skeletons mapping each
  `secret-references.json` entry to where its value must be injected; it never
  accepts, stores, logs or renders secret plaintext. The existing secret scan
  stays green by construction.
- Sandbox-account provisioning records the disposable identity set the
  environment class permits (synthetic-data policy, quota envelope wiring to
  `quota-guards.json`, expiry hooks consistent with the DEP-014 surface) —
  recorded as references and policy facts, projected from the manifests, never
  a parallel account registry in the tool.
- Re-running provision converges (idempotent — a second run reports
  already-converged, no duplicate resources); `teardown.ts` classification
  guards extend to the provisioned records.
- Live-provider provisioning steps (Neon project/branch creation, R2 bucket,
  Cloudflare queue/workflow, Upstash) execute only when their credentials are
  present; without credentials they record honest NOT RUN with the owner
  (Lead credentialed re-run) — exactly the DEP-001 evidence discipline.
- `validate.ts` fails closed on any new manifest surface (additive rows are
  validated, malformed rows abort before any provider call).

## Acceptance criteria

1. A fresh operator can run the provision path for a disposable environment
   class end to end from repository configuration (plan mode requires no
   credentials at all).
2. Secret handling is proven external-only: templates/skeletons carry
   references only; the secret-scan test and the redaction doctrine stay
   green; a hostile probe confirms no plaintext path exists through the tool.
3. Idempotence is proven by test: second convergence reports no changes; a
   drifted state re-converges; teardown removes exactly the classification-
   permitted records.
4. Sandbox-account records render their policy facts (synthetic data, quota
   envelope, expiry) from the manifests — never tool-local state.
5. Live-provider steps without credentials record NOT RUN with owner and
   reason in `deploy/evidence/dep-002.json`; nothing claims a live result.
6. Governance, typecheck, lint, unit (including the deployment suites) and
   architecture stay green; machine manifests stay in sync for any additive
   env-var row.
7. The operator recipe (`deploy/PUBLIC-DEPLOYMENT.md`) documents the provision
   step in the reproduction chain with its honest boundaries.

## Required verification

Governance, typecheck, lint, unit, architecture, integration (PG suites skip
honestly without `ZECK_PG_TEST_URL`), deployment validation
(`bun run deploy:validate`), provision plan-mode execution, idempotence and
teardown-guard tests, secret scan, hostile-input probes on every new render
path.

## Reporting

Any defect must include exact reproduction, root-cause classification (Zeck /
console / harness / provider / access), viable solutions, recommended
solution with trade-offs and the exact verification needed for closure.

Workers do not change `spec/platform-delivery-state/*` and do not merge their
own PR.
