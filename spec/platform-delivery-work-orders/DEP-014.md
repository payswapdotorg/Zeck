# DEP-014 — Sandbox Budgets, Quotas, Expiration, Reset and Safe Synthetic-Data Policy

Status: AUTHORIZED / WAVE B
Dependencies: DEP-010
Base: exact current `main` at dispatch

## Objective

Give the sandbox lifecycle its developer-facing governance surface: per-application and per-sandbox budgets and quotas, expiration with explicit semantics, reset with disposable identity, and a visible, enforced safe-synthetic-data policy — projected through the public contracts the console already consumes.

The budgets module is and remains the ONE budget authority and the sandbox module is and remains the ONE environment/admission authority. This order extends their public surface with the lifecycle dimensions a developer must see and control (quotas, expiration, reset, data policy); it must not create a second authority, and the console must not hold any budget, quota or policy state of its own.

## Platform side (the authority extension)

- Extend the `budgets` module following the budget-service house pattern: a quota/lifecycle service (`application/quota-service.ts` or the natural extension of `budget-service.ts`), provider-neutral ports, and SQL + in-memory adapters, exported through the module's public barrel.
- Quota records carry: owner scope (application/tenant), dimension (spend, wall-clock time, concurrent runs, artifact count/size), the limit, the current consumption, the window/reset semantics and status. Spend quotas resolve through the existing `BudgetAuthority` fail-closed discipline; time/concurrency/artifact quotas enforce at sandbox admission exactly as costed compute does today.
- Expiration: sandbox identities carry a time-to-live; expiry transitions are explicit lifecycle events on the executions evidence ledger (the existing EventEnvelope seam — no new ledger), and post-expiry reads render an honest expired state rather than silently disappearing records.
- Reset: re-establishing a disposable sandbox identity after expiry/quota exhaustion is an idempotent, confirmable operation that NEVER carries state forward — a fresh admission under fresh budgets. Reset is per-identity and auditable.
- Public routes in `src/api/routes/` (following the executions.ts facade: `Idempotency-Key` required on POSTs, scope-checked reads, strict body-key rejection, serialization-boundary redaction) exposing: quota state per scope, expiration state per sandbox identity, the reset operation, and the deployment's synthetic-data policy document (the policy text as served data — one source of truth).
- The synthetic-data policy is a governed, versioned platform artifact: what data classes are permitted in sandboxes (synthetic fixtures only — never real PII, secrets, credentials or production data), how the composer and admission path enforce it, and how violations are recorded. Enforcement points: sandbox admission (policy admission already REQUIRED in the chain — extend the admission contract with the data-class check) and the console composer (DEP-013 consumes this surface).

## Console experience (the projection side)

- Budgets & quotas visibility: per application/environment — every quota dimension with limit, consumption, window and status, rendered from the public routes; explicit boundary rows naming any fact the public API does not carry (e.g. real-time consumption telemetry).
- Expiration & reset: sandbox identities list their TTL/expiry state; an expired or quota-exhausted identity offers the confirm-then-act reset flow with the explicit "nothing carries forward" contract; idempotent semantics visible (re-confirming a reset is safe).
- Synthetic-data policy: the policy document renders in the console (playground and sandbox surfaces) from the served policy route — never a console-local copy; the composer surfaces the permitted-data contract at input time.
- Honest unavailable states wherever a dimension the console could show is not exposed by the public API — naming the missing contract, never inventing.

## Honesty and safety rules

- Quota enforcement is fail-closed at admission — an unenforceable dimension must fail the admission honestly, never default-allow.
- No route, log or render path may expose another scope's quota or consumption facts; `assertScopeCovers` on every mutation and scope-checked read on every query.
- The policy artifact carries no secrets; violations record facts (class, decision), never payloads.
- Machine manifests (`openapi.json`, `env-vars.json`) and the route-count pin stay in sync (additive rows only; the Lead reconciles at merge).

## Acceptance criteria

1. Quota state per application scope renders from public routes with every dimension (spend, time, concurrency, artifacts), its limit, consumption, window and status.
2. Spend quotas fail closed at admission; time/concurrency/artifact quotas enforce at admission with the same discipline; probe tests demonstrate each dimension's rejection path.
3. Sandbox identities carry TTL/expiry; expiry emits ledger events; post-expiry reads render honest expired states (no silent disappearance).
4. Reset is idempotent, confirmable, state-non-carrying and auditable; probe tests confirm a second reset is a no-op success and that no pre-reset state survives.
5. The synthetic-data policy is a versioned platform artifact served through a public route; admission-path enforcement rejects non-synthetic data classes with recorded violations (facts, not payloads).
6. The console renders budgets/quotas/expiration/reset and the policy from the public routes only; boundary rows name any non-exposed fact.
7. Cross-scope access attempts fail with the house `TENANT_SCOPE_VIOLATION` semantics on every new route.
8. Machine manifests and the route-count pin stay in sync with the new routes.
9. Unit tests (services + adapters), API integration tests, dashboard unit tests and a browser smoke of view quotas → expire → reset → policy render pass in the house style.

## Required verification

Governance, typecheck, lint, unit, architecture, integration, dashboard/browser smoke, quota fail-closed probes, reset idempotency probes, hostile-value probes and machine-manifest sync checks.

## Reporting

Any defect must include exact reproduction, root-cause classification (Zeck / console / harness / provider / access), viable solutions, recommended solution with trade-offs and the exact verification needed for closure.
