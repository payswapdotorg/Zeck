# DEP-025 — Validation Library and Rerunnable Experiment Center

Status: AUTHORIZED / WAVE A
Dependencies: DEP-010, DEP-020

## Objective
Expose the complete executed Zeck validation corpus inside the developer console so a developer or coding agent can discover, understand, configure, execute, compare and reproduce the validation work without accessing Zeck internals.

The validation library is not a second validation system. It is a public projection and controlled execution interface over the already-built `benchmarks/validation/**`, `docs/work-items/VAL-*.md`, validation manifests, public SDK/API and governed sandbox.

## Required experience

Console navigation:

```text
Playground
└── Validation Lab
    ├── All experiments
    ├── By capability
    ├── By workload
    ├── By validation stage
    ├── Recommended starting points
    └── Agent / machine interface
```

Every executed validation Work Order from VAL-001..VAL-052 must have a corresponding discoverable validation definition where the underlying experiment is safe and reproducible. Historical evidence must remain immutable/read-only; reruns create new experiment runs linked to the original validation definition and source revision.

## Experiment detail surface

Each validation item must expose:

- objective and what it proves;
- workload/capability;
- input/corpus and fixture identity;
- required environment/provider/model access;
- expected outcome and failure semantics;
- quality, safety, reliability and economic metrics;
- runnable configuration;
- copyable SDK/API example;
- source/repository reference;
- exact validation revision/evidence that originally established the result;
- current availability and NOT RUN boundaries;
- estimated/known resource cost before launch;
- run button and reproducibility controls;
- run history, traces, output, environment state and comparison against the recorded baseline.

## Rerun modes

Support at minimum:

1. **Replay exact** — same corpus, configuration, provider/model selection and revision where still available.
2. **Rerun current** — same validation definition against the current sandbox/platform.
3. **Modify and run** — user changes allowed inputs/constraints while preserving lineage from the original experiment.
4. **Compare** — compare two or more runs and, where applicable, direct/non-Zeck/competing baselines.

Runs must never mutate historical evidence.

## Agent interface

Expose machine-readable validation catalog and run schemas so an agent can:

```text
list validation experiments
→ inspect definition/schema
→ check required capabilities/access
→ estimate cost
→ start run
→ poll/stream status
→ retrieve result + trace + evidence
→ compare to baseline
→ export reproducibility bundle
```

No undocumented UI-only state may be required for an agent to reproduce a validation.

## Safety and sandbox rules

All public reruns default to disposable sandbox resources, synthetic data, hard budget/time limits, concurrency limits and provider allowlists. Consequential external side effects require an explicit governed test connection. Provider/API credentials are never exposed to the browser or stored in experiment definitions.

## Acceptance criteria

1. Every completed validation family VAL-001..VAL-052 is represented in a console-discoverable catalog, including honest entries for experiments whose live external dependencies are currently unavailable.
2. A developer can open a validation item, understand what it proves, see its original evidence and launch a safe rerun from the console.
3. A coding agent can perform the same discovery and execution through machine-readable public interfaces without maintainer-only knowledge.
4. Exact replay and current rerun produce distinct immutable run identities and preserve historical evidence.
5. Rerun results capture outcome, trajectory, environment state, cost, latency and evidence and can be compared to the original result.
6. Missing provider/model access is surfaced before execution with the exact dependency and is never represented as PASS.
7. Sandbox budget, timeout, artifact and side-effect controls are enforced.
8. Validation definitions are sourced from repository truth rather than duplicated as hand-maintained console-only copies.
9. Browser, API, accessibility, isolation and secret-safety tests cover the complete validation-library flow.

## Required verification

Governance, typecheck, lint, dashboard/browser smoke, API integration, validation-catalog integrity, exact replay lineage, sandbox budget negatives, secret-flow tests, agent/machine API tests and representative real reruns from multiple capability families.

## Reporting

Any defect must include exact reproduction, root-cause classification, viable solutions, recommended solution with trade-offs and exact verification needed for closure. The delivery report must distinguish console, validation-harness, Zeck, provider and access failures.
