# DEP-031 — Playground Compare Mode: Baseline vs Zeck Strategy and Execution Explanation

Status: AUTHORIZED / WAVE P3
Dependencies: DEP-013 (the interactive playground — delivered)
Base: exact current `main` at dispatch

## Objective

Give the interactive playground a compare mode: a developer composes a workload once, runs it through the governed platform, and can compare the outcome against another run of the same composed task — a baseline (a plain single-model execution through the same public contract) vs the platform's chosen strategy — with the execution explanation of WHY the platform planned the route it did (the planning decision's own recorded facts: deterministic-first sufficiency, strategy candidates, cost/quality/latency trade-offs, selection rationale).

Compare is a projection over execution records. It must not create a second comparator, benchmark or evaluation authority: the validation program's comparator harness (benchmarks/validation) is the established comparison machinery; this order projects the SAME composition discipline into the playground console surface.

## Console experience (the projection side)

- From the playground family page and the execution explorer, a developer selects two runs of the same workload family (the run history the playground already records + the explorer's records) and opens a compare view: status, terminal outcome, recorded cost/usage, route summary (strategy class, provider/model where recorded), verification outcomes, and duration — side by side, every fact from the public records.
- The explanation panel renders the platform's OWN recorded planning rationale (the planning-decision facts the event ledger carries: sufficiency outcome, candidates with expected cost/quality/latency, selected strategy, rationale, substrate selection) — never re-derived or approximated console-side.
- A baseline launcher: the same composer, the same public create contract, but the request carries the baseline lineage metadata the platform can record (never a provider/model override — provider selection is structurally impossible in the frozen create contract; a baseline is an execution the platform plans under baseline semantics the public API supports, or an honest unavailable state naming the missing contract if it does not).
- Machine parity: a JSON compare view under the console's public routes serving the composed records verbatim.
- Honest boundaries: runs of different workload families compare only on the generic axes and say so; missing facts (e.g. quality scores the public API does not expose) render as honest unavailable states naming the missing contract.

## Platform side (only what the flows require)

- Additive public routes only where genuinely required (facade pattern). Baseline semantics that would require a create-contract extension go through the Lead as a merge note — the frozen create vocabulary (no provider/model selection) is never widened by a console order.

## Acceptance criteria

1. A developer can select two runs of the same composed workload and see a side-by-side compare of the public facts (status, cost, usage, route, verification, duration).
2. The explanation panel renders the platform's recorded planning rationale verbatim from the event ledger facts.
3. The baseline path uses the frozen public create contract only, or renders an honest unavailable state naming the missing contract.
4. Machine parity: a JSON compare view serves the same composed records; no UI-only state.
5. Unit tests (house vitest style) + hostile-value probes; existing pins stay in sync.
6. Machine manifests and the route-count pin stay in sync with any new additive routes (additive rows only).
7. The surface follows the house composed-surface pattern and the honesty doctrine.
