# DEP-011 — Credentials/API-Key UX and Safe Connection Management

Status: AUTHORIZED / WAVE B (dispatch-gated by the Lead on DEP-001's merge — this order shares the `src/api` route table and machine manifests with DEP-001's identity seam)
Dependencies: DEP-010
Base: exact current `main` at dispatch

## Objective

Turn the credentials surface from an honest-unavailable placeholder into the real credential lifecycle: console-mediated issuance of scoped transport credentials (secret shown exactly once at creation), metadata-only listing, rotation, revocation, and safe bring-your-own connection management.

There is and remains exactly ONE credential authority: the `auth` module. This order extends that authority with a credential-issuance service and projects it through the public API into the console. It must not create a second credential, secret or connection authority, and the console must not hold any credential state of its own.

## Authority extension (the platform side)

- Add a credential service to `src/modules/auth` following the membership-service house pattern: `application/credential-service.ts`, a provider-neutral `ports/credential-store.ts`, and an adapter (SQL + in-memory test double) under `adapters/`, exported through the module's public barrel.
- Credential records carry: stable identity, label, application/tenant scope, role/permission scope, creation/rotation timestamps, status (active/retired/revoked). Secret material is stored as a `SecretReference` through the platform secret-store (classification `provider-credential`/`signing-key` as applicable) — never in the credential record itself.
- Issuance returns the secret exactly once; no later route, log or render path can retrieve it. Rotation issues a successor secret under the same credential identity and retires the predecessor; revocation is immediate and idempotent. All mutations honor the module's scope-resolution guard (`assertScopeCovers`) and the house idempotency discipline.
- Public routes in `src/api/routes/credentials.ts` following the executions.ts facade pattern: `Idempotency-Key` required on POSTs, scope-checked reads, strict body-key rejection, and serialization-boundary redaction. Register them in the API server and sync `docs/developer/machine/openapi.json`, `env-vars.json` and the route-count pin test (additive rows only — DEP-001's identity route shares this table; the Lead reconciles at merge).

## Console experience (the projection side)

The credentials page (`/console/applications/keys`) grows the real flows:

- **Issue**: a guided form (label, scope selection) → the show-once reveal with copy affordance and an explicit "you will not see this again" contract; honest unavailable state if issuance is not enabled for the deployment.
- **List**: every credential visible to the application scope with metadata only — identity, label, scope, created/rotated timestamps, status; an explicit boundary row naming any fact the public API does not carry (e.g. last-used telemetry).
- **Rotate / revoke**: confirm-then-act flows with idempotent semantics, status transitions rendered from the authority.
- **Connections**: the safe bring-your-own connection facts the public records carry — provider rails, connection labels, BYOK status — composed with the existing safe-credential-rules vocabulary; no secret values anywhere.

## Honesty and safety rules

- No wire shape the console renders may carry secret material; the redaction doctrine (`[not displayed]`) and its hostile-value probes must cover every new render path.
- Missing facts render as honest unavailable states naming the missing public contract — never invented.
- The environment-contract table (names, never values) stays accurate for any new env binding.

## Acceptance criteria

1. A developer can issue a scoped credential through the console; the secret is shown exactly once at creation and is never retrievable afterwards through any route, log or render path.
2. Credential listing is metadata-only and honors application/tenant scope.
3. Rotation issues a successor secret (show-once) and retires the predecessor; revocation is immediate and idempotent; both are reflected in the list.
4. Connection management facts render from public records with the safe-connection rules; zero secret values.
5. Secret-safety probes over every new route response and console render path pass; no secret material crosses the serialization boundary.
6. All credential mutations pass the scope-resolution guard; cross-tenant attempts fail with the house `TENANT_SCOPE_VIOLATION` semantics.
7. Machine manifests (`openapi.json`, `env-vars.json`) and the route-count pin stay in sync with the new routes.
8. Unit tests (service + adapters), API integration tests, dashboard unit tests and a browser smoke of issue → reveal → list → rotate → revoke pass in the house style.

## Required verification

Governance, typecheck, lint, unit, architecture, integration, dashboard/browser smoke, secret-flow tests and machine-manifest sync checks.

## Reporting

Any defect must include exact reproduction, root-cause classification (Zeck / console / harness / provider / access), viable solutions, recommended solution with trade-offs and the exact verification needed for closure.
