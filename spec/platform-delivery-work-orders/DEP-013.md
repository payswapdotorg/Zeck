# DEP-013 — Interactive Sandbox Playground for Every Workload Class

Status: AUTHORIZED / WAVE B
Dependencies: DEP-010
Base: exact current `main` at dispatch

## Objective

Turn the sandbox playground from the guided-example gallery DEP-010 shipped into a real INTERACTIVE playground: a developer selects any supported workload class, composes their own run spec over the public Zeck contracts, executes it in a governed disposable sandbox, and inspects the outcome end to end — with editable parameters, not canned demos.

The playground is a projection and composition surface. It must not create a second execution, sandbox, capability or environment authority: every run is a real execution through the public API with a sandbox environment spec admitted by the existing governed chain (policy admission → capability resolution → budget admission, fail-closed), and every rendered fact comes from the public records those contracts expose.

## Platform side (only what the interactive flows require)

- Where composing a run requires facts the public API does not yet expose (for example the workload-class catalog with its input schemas and the environment-template shapes a developer may parameterize), expose them as additive public routes following the executions.ts facade pattern: `Idempotency-Key` required on POSTs, scope-checked reads, strict body-key rejection, serialization-boundary redaction.
- The workload-class catalog served to the console must be the SAME catalog the capability registry and the machine manifests carry (`docs/developer/machine/capability-manifest.json`, `examples-manifest.json`) — one source of truth, projected; never a console-local copy that can drift.
- Interactive runs are ordinary executions: the playground composes the public execution + sandbox contracts and never bypasses the admission chain, budget reservation or evidence ledger.

## Console experience (the projection side)

- A first-class interactive playground surface following the `validation-lab.ts` composed-surface pattern: **choose** a workload class (every family the capability catalog carries — text, structured, RAG, tools/workflows, long-running, voice/realtime where available, image, video, vision/VLM/audio, multimodal, 3D, browser/computer use, human review, training/batch — the complete list, rendered from the catalog, never hardcoded), **compose** the run (editable inputs constrained to synthetic data, environment/resource parameters within the deployment's advertised envelopes), **run** it (real public-API execution under a disposable-sandbox identity), **inspect** it (deep links into the execution explorer's public facts).
- Every workload class the catalog carries must appear. Where live provider access or capability is absent for a class, the class renders in an honest NOT RUN state naming exactly what is missing — never hidden, never faked.
- Composition state is client-side and disposable: nothing a developer types into the composer is persisted beyond the browser session unless they execute it (then the execution record is the durable truth, owned by the executions authority).
- Machine parity: for every workload class, the playground links the copyable example from the integration kit (`examples/**`, `examples-manifest.json`) so an agent can reproduce the same run without the console; no UI-only path to capability.

## Honesty and safety rules

- All sandbox runs use synthetic data only; the composer must reject or neutralize input that violates the deployment's synthetic-data policy (DEP-014 owns the policy surface — this order consumes it).
- Hard budgets, timeouts, concurrency and artifact limits apply to every interactive run by default (the existing budget-admission discipline; DEP-014 deepens it).
- Missing facts render as honest unavailable states naming the missing public contract. No console-local source of truth may be introduced.

## Acceptance criteria

1. A developer can select any workload class from the catalog-rendered picker and reach a composer whose input schema matches the class's advertised contract.
2. A composed interactive run executes through the public API as a real execution under a disposable-sandbox identity, passing the full admission chain (policy, capability, budget — fail-closed).
3. Every workload family in the capability catalog appears in the picker; families without live provider access render honest NOT RUN states naming the missing capability or provider contract.
4. Run outcomes deep-link into the execution explorer's public facts (result, verification, events, costs where exposed).
5. The workload-class catalog the console renders is served from the same authority the machine manifests carry — verifiably one source of truth (no drift between console picker, capability manifest and examples manifest).
6. Machine parity holds: every class links its copyable integration-kit example; an agent can reproduce any playground run without the console.
7. Synthetic-data-only enforcement is active in the composer; hostile-input probes confirm neutralization.
8. Machine manifests (`openapi.json`, `env-vars.json`) and the route-count pin stay in sync with any new additive routes.
9. Unit tests (console surface + any new route), API integration tests, a browser smoke of choose → compose → run → inspect, and hostile-value probes pass in the house style.

## Required verification

Governance, typecheck, lint, unit, architecture, integration, dashboard/browser smoke, hostile-input probes, catalog-single-source verification and machine-manifest sync checks.

## Reporting

Any defect must include exact reproduction, root-cause classification (Zeck / console / harness / provider / access), viable solutions, recommended solution with trade-offs and the exact verification needed for closure.
