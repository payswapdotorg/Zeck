# DEP-030 — Usage, Economics and Optimization Dashboard

Status: AUTHORIZED / WAVE P3 (dispatch-gated on DEP-014)
Dependencies: DEP-014 (the sandbox budget/quota/expiration policy surface — the usage dashboard composes its recorded facts)
Base: exact current `main` at dispatch

## Objective

Turn the per-run cost facts scattered across the console (the explorer's Costs view, the applications usage tab, the operator spend surfaces) into a first-class developer-facing usage, economics and optimization dashboard: what an application spent, on which runs, under which budgets and quotas, what the platform's optimization decisions were (strategy classes, deterministic-first wins, cache reuse), and where honest aggregate facts are not yet exposed by the public API.

The dashboard is a projection surface. It must not create a second budget, economics, ledger or optimization authority: every rendered fact comes from the budgets/economics public barrels, the execution records the public API already exposes, and the planning-decision facts the event ledger carries.

## Console experience (the projection side)

- A first-class Usage surface in the developer console following the established composed-surface pattern (validation-lab.ts / playground.ts / explorer.ts / credentials.ts): application-scoped usage over the runs the public records carry, per-run cost/usage (from `GET /executions/:id/results`), budget and quota facts (from the budgets public barrel — limits, reservations, spend categories), and the optimization view (per-run route summaries, strategy classes, deterministic-first and cache-reuse outcomes from the planning decision records).
- Aggregates the public API does not expose render as honest unavailable states naming the missing contract (an application-scoped usage/aggregate route) — never approximated from console-local accumulation beyond the browser's own disclosed recents.
- Where DEP-014's sandbox quota/budget policy surface records facts (envelopes, expirations, resets), project them; where they are module-internal, name the missing projection seam honestly (merge note to the Lead, never a module edit).
- Machine parity: a JSON view of the composed usage facts under the console's public routes, same composition as the HTML (no drift).

## Platform side (only what the flows require)

- Additive public routes only where a required fact is genuinely missing AND can follow the executions.ts facade pattern (scope-checked reads, strict body-key rejection, serialization-boundary redaction). If the fact can be projected from existing records client-side, add NO route.
- The budgets/economics modules are authorities: consume their public barrels, never edit them. A genuinely missing projection seam goes through the Lead as a merge note.

## Acceptance criteria

1. A developer can see per-run cost and usage facts for the executions their scope covers, composed from the public records.
2. Budget/quota facts render from the budgets authority's public surface; missing aggregates render as honest unavailable states naming the missing contract.
3. The optimization view renders the platform's own recorded decisions (strategy class, deterministic-first, cache/reuse, route summary) per run — never re-derived console-side.
4. Machine parity: a JSON view serves the same composed facts; no UI-only state.
5. Unit tests (house vitest style) + hostile-value probes over every new render path; existing pins stay in sync.
6. Machine manifests (openapi.json, env-vars.json) and the route-count pin stay in sync with any new additive routes (additive rows only).
7. The surface follows the house composed-surface pattern and the honesty doctrine (missing facts name their missing public contracts).
