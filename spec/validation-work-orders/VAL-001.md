# VAL-001 — Validation Lab Bootstrap and Governance

**Status:** AUTHORIZED / PENDING
**Program:** Zeck Validation Roadmap
**Assurance:** HIGH_ASSURANCE
**Dependency:** none

## Objective

Establish the executable validation laboratory and governance seams required for the customer-style validation program. The result must let the Tech Lead dispatch up to three independent validation workers against exact repository revisions and maintain reproducible experiment evidence.

## Allowed surfaces

- `spec/validation-state/**`
- `spec/validation-work-orders/**`
- `docs/VALIDATION-ROADMAP.md`
- `docs/LLM-VALIDATION-TECH-LEAD-CONTRACT.md`
- `benchmarks/validation/**`
- validation-specific scripts/configuration/tests
- `docs/VALIDATION-REPORT.md`

## Forbidden

- modifying frozen v1.0 semantics;
- modifying completed product Work Order state as part of validation;
- credentials or API keys in source control;
- weakening Zeck authority/security boundaries;
- claiming external provider results that were not executed;
- implementing application-specific validation WOs outside this scope.

## Acceptance criteria

1. A deterministic validation program entrypoint exists and points to the canonical roadmap, Tech Lead contract and validation state.
2. Validation state records dependencies, frontier, in-flight work and maximum concurrency of three workers.
3. A standard worker submission/evidence structure exists with exact base, final head, changed files, test results, issue findings and proposed solutions.
4. Validation runs have stable identifiers and enough metadata to reproduce the experiment.
5. The cumulative validation report structure exists and separates observed facts, failures, hypotheses, recommendations and NOT RUN boundaries.
6. Governance tests reject simultaneous ownership of the same protected validation surface where reconciliation is non-mechanical.
7. No product authority or development-state authority is duplicated by the validation layer.
8. Required local validation documentation is self-contained for a fresh Tech Lead.

## Required evidence

- exact base and final revision;
- validation-state consistency check;
- architecture boundary check;
- worker/evidence contract tests;
- fresh-clone or clean-checkout bootstrap proof where available;
- changed-file inventory.

## Issue solution protocol

Every bootstrap defect must include exact reproduction, impact, root-cause classification, candidate fixes and a recommended fix with trade-offs. External-access gaps must be recorded as NOT RUN and surfaced to the Tech Lead.

## Completion

Complete only after all criteria are evidenced, the Architect/Tech Lead accepts the result, the PR is merged, and validation state is finalized.
