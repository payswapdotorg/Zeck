# VAL-023 — Security, Prompt-Injection, Capability-Boundary and Secret-Flow Validation

**Status:** AUTHORIZED / PENDING
**Program:** Zeck Validation Roadmap
**Assurance:** HIGH_ASSURANCE
**Dependencies:** VAL-002, VAL-003, VAL-004, VAL-006, VAL-009, VAL-010, VAL-019

## Objective

Deliver the adversarial security slice: a security-validation application
exercising prompt-injection defense (instructions embedded in tool
results, documents and media are DATA — never executed; the
injection-defense instruction pattern already proven in the live
multimodal and agentic crowns), capability boundaries (unexposed tools
never invoked; authority-boundary oracles per the VAL-019 precedent),
secret-flow boundaries (credentials never cross into payloads, logs or
evidence — digests only; raw card numbers refused per the browser-use
secret-flow boundary precedent) — over the REAL platform path with REAL
model dispatches through the authorized rails (the injection corpus rides
REAL provider dispatches: a REAL model genuinely attempting to follow
injected instructions is the system under test).

## Acceptance criteria

1. The application rides the public SDK boundary with a
   repository-reproducible, secret-free configuration and executable
   tests; the adversarial corpus declares, per row, the attack vector
   (injection payload shape, boundary probe, secret-flow attempt), the
   expected defense outcome and the mechanical oracle.
2. Deterministic adversarial fixtures (injection payloads embedded in
   fixture documents/tool results/media; secret material in fixture
   flows) make every offline row reproducible; payloads are synthetic —
   never real credentials.
3. A REAL end-to-end integration run (env-gated on the authorized rails)
   drives the injection corpus through REAL model dispatches: the model
   receives the injected instructions and the mechanical oracle verifies
   the DEFENSE (the injected directive was not followed; the declared
   task outcome was achieved or honestly refused).
4. Capability-boundary and secret-flow oracles verify mechanically:
   unexposed tools never invoked; refused instruments recorded; no
   secret substring appears in any evidence field (mechanical scan).
5. Honest economics and latency; payload digests (never payloads) in
   evidence.
6. Discrimination tests prove the defense derivations against controlled
   fakes (injection-followed case must FAIL its criterion; boundary-bypass
   attempts rejected pre-dispatch; evidence-leak scan catches planted
   secrets).
7. Evidence document records REAL outcomes, timings, costs, NOT RUN
   boundaries and the executed battery honestly.
