# Zeck E1.1 Research Baseline

**Purpose:** Durable evidence for the E1.1 architectural decisions. External products inform optimization design but never override Zeck authority.

## Conclusions adopted

### OpenAI

OpenAI's August 2026 GPT-5.6 builder guidance highlights three complementary efficiency patterns: reuse prior reasoning/context, parallelize when appropriate, and move deterministic work into code through programmatic tool calling. It also documents deterministic prompt-cache controls and reports that lower reasoning effort can improve price-performance on some workloads.

**Zeck adoption:** retained/compact context, programmatic execution, safe parallelism, cache-aware context planning and model/reasoning selection inside one Execution Compiler.

Source: https://openai.com/index/builders-guide-to-gpt-5-6/

### AWS Bedrock

AWS describes Intelligent Prompt Routing as selecting the model with the best predicted quality/cost trade-off, while prompt caching and multiple inference modes target cost/latency optimization. AWS also notes that application-specific performance data can be necessary because generic routing is not universally optimal.

**Zeck adoption:** quality-constrained model selection plus observed application/workload evidence; never rely on headline model price alone.

Sources:
- https://aws.amazon.com/bedrock/intelligent-prompt-routing/
- https://aws.amazon.com/bedrock/prompt-caching/
- https://aws.amazon.com/bedrock/cost-optimization/

### Google Gemini

Google's current Gemini API documentation provides implicit context caching and exposes cached-token usage, reinforcing that repeated context should be treated as an economic resource.

**Zeck adoption:** cacheability belongs in the Execution IR and compiler decision model; cache state is disposable and never authoritative.

Source: https://ai.google.dev/gemini-api/docs/caching

### Anthropic

Anthropic's production reports show increasingly long-running agent sessions and document the operational fragility of prompt-caching/long-context optimizations when cache/state semantics are incorrect.

**Zeck adoption:** continuation and context optimization must be correctness-sensitive, revision-aware and explicitly verified; caching is not a correctness authority.

Sources:
- https://www.anthropic.com/news/measuring-agent-autonomy
- https://www.anthropic.com/engineering/april-23-postmortem

### E2B

E2B emphasizes isolated cloud sandboxes, persistence, parallel execution and snapshot-based reuse. Recent case studies show snapshots can materially reduce startup overhead for repeated environments and that sandbox performance affects overall agent economics.

**Zeck adoption:** substrate capabilities include isolation, persistence/snapshot facts and warm/reuse economics; E2B stays an adapter.

Sources:
- https://e2b.dev/blog/e2b-is-now-in-agents-sdk
- https://e2b.dev/blog/replicas
- https://e2b.dev/blog/paperinstruments

### Daytona

Daytona documents persistent snapshots and warm pools that keep matching sandboxes pre-created and ready, trading idle capacity for lower startup latency.

**Zeck adoption:** warm-pool availability and startup/readiness cost become substrate-selection facts rather than a Zeck-specific runtime abstraction.

Sources:
- https://www.daytona.io/docs/snapshots/
- https://www.daytona.io/docs/en/warm-pools/

### Modal

Modal's sandbox work distinguishes created, scheduled, started, ready and in-use states, and shows that application initialization can dominate raw container startup. Modal recommends warm pools and readiness probes for latency-sensitive production workloads and exposes snapshots/directory snapshots for reusable environments.

**Zeck adoption:** distinguish "started" from "ready" in substrate evidence; optimize total readiness latency, not VM boot time; warm pools/snapshots remain provider mechanisms.

Sources:
- https://modal.com/blog/unpacking-sandbox-startup-latency
- https://modal.com/blog/directory-snapshots-resumable-project-state-for-sandboxes

## Industry cost lesson

Current AI infrastructure material repeatedly shows that better token unit economics can increase total spend because agentic workloads consume more steps and more complex workflows. Gartner's August 2026 forecast explicitly frames an "inference paradox" where falling unit costs coexist with rising per-workflow cost.

**Zeck adoption:** optimize **cost per successfully resolved outcome**, not cost per token or cost per model call.

Source: https://www.gartner.com/en/newsroom/press-releases/2026-08-17-gartner-predicts-ai-inference-costs-per-agentic-workflow-will-increase-more-than-fivefold-through-2028

## Inference/routing ecosystem lesson

Commercial routing products increasingly position model selection, routing and spend attribution as a central optimization layer. DigitalOcean's current inference-router discussion warns that adding a separate LLM classifier to route every request can create "double taxation" and brittle maintenance.

**Zeck adoption:** routing is not a separate model-call tax by default. Optimization decisions are deterministic compiler work wherever possible and use application evidence; Zeck's Execution Compiler remains the single optimization authority.

Source: https://www.digitalocean.com/blog/inference-router-architecture

## Deliberate non-adoptions

Zeck will not:

- create one optimizer service for every cost dimension;
- make a provider cache authoritative;
- make E2B, Daytona or Modal domain authorities;
- require MCP universally;
- use multi-agent execution by default;
- add a routing-model call merely to route another model unless the measured quality/cost benefit justifies it;
- treat warm pools as universally optimal when idle capacity costs more than saved startup latency;
- replace the existing planner with the compiler.

## Research-to-architecture rule

External evidence can justify a new adapter capability or optimization fact. It cannot authorize a new Zeck authority.

When an external product introduces a useful optimization, first ask:

1. Can the existing Execution Compiler express the decision?
2. Can the existing substrate/tool/context/economics authority provide the facts?
3. Can the behavior remain provider-neutral through an adapter?
4. Can the value be demonstrated with exact-revision evidence?

Only if the answer is no should a new architecture proposal be considered.
