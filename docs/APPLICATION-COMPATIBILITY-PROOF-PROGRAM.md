# Zeck Application Compatibility Proof Program

Status: ARCHITECT-APPROVED
Date: 2026-09-26
North star: demonstrate with real application code that materially different open-source AI applications can make Zeck their AI execution authority without redefining Zeck completeness.

## Mission

Move from:

Zeck can execute many AI workload types

to:

an independent application can remove its direct AI-execution/provider infrastructure and continue operating with Zeck as its AI execution authority.

The program is staged from clean provider boundaries toward fragmented execution graphs.

## Representative portfolio

### Wave 1 — clean execution boundaries

1. Aider — coding assistant
2. Cline — IDE agent
3. OpenHands — software-engineering agent
4. Continue — IDE/model platform

### Wave 2 — multi-surface agents

5. Hermes-Agent — general/autonomous agent
6. OpenClaw — broad general agent
7. Browser Use — browser agent

### Wave 3 — multimodal application platforms

8. Open WebUI — general AI UI
9. AnythingLLM — RAG/knowledge application

The ordering is an integration-friction progression, not a quality ranking.

## Certification target

AI_EXECUTION_COMPLETE requires the full Application Execution Graph to be declared and every material AI edge to pass the delegation proof.

A green model call alone never qualifies.

## Proof battery

Every application proof includes:

1. Pin exact upstream application revision and exact Zeck integration revision.
2. Inventory every material AI edge.
3. Replace each applicable edge with the Zeck public boundary.
4. Ensure application runtime has no direct AI-provider credentials.
5. Block direct provider endpoints for the application runtime.
6. Replay the representative application corpus.
7. Map every delegated edge to Zeck execution identity and evidence.
8. Replay timeout, provider failure, duplicate and retry scenarios.
9. Compare direct and strong manually optimized baselines using cost per successfully resolved outcome.
10. Run static and runtime no-bypass inspection.
11. Prove application-specific customization remains expressible.
12. Measure deterministic/reuse/verified-computation opportunities rather than assuming them.
13. Prove telemetry can explain plan, route, provider/model/substrate, cost, latency, failures, retries, reuse and evidence.
14. Launch the same certified journey from the Zeck website.

## Demo Mirror requirements

Each certified demo exposes:

- application name and pinned revision;
- Run this application through Zeck;
- representative task;
- live progress;
- result/output;
- execution timeline;
- chosen execution representation;
- provider/model/substrate route when available;
- cost and latency;
- verification/evidence;
- warnings and external limitations;
- direct-baseline comparison when available;
- reproducibility instructions.

A demo must never conceal an incomplete edge behind a polished UI.

## Architecture-gap trigger

Escalate when an application requires a representation that cannot be expressed through:

Intent → Policy → Capability → Budget → Planning → Execution Compiler → Execution → Verification → Evidence

without creating a second authority, weakening an invariant, leaking provider semantics into domain modules, or making application-domain state authoritative inside Zeck.

## Completion

Success requires evidence that clean-boundary applications can be Zeck-complete, fragmented applications can be progressively absorbed without bypasses, new execution surfaces become explicit rather than hidden, and public demos reproduce the real certified integrations.
