# Zeck E1.1 Implementation Program

**Status:** ARCHITECT-APPROVED IMPLEMENTATION CHARTER
**Architecture:** v1.0 + D1.0 + E1.0 + E1.1
**Current deployment prerequisite:** WORK-048 / D-07
**Maximum concurrent workers:** 3
**Authority:** Architect

## Purpose

This document converts E1.1 into a deterministic implementation program that a fresh LLM Tech Lead can execute without conversation history.

It is a **program charter**, not itself an executable Work Order. Each implementation stage becomes executable only when the Architect issues the corresponding repository Work Order and dependency-state/frontier state makes it eligible.

Workers have no authority to widen this program. A worker may implement only the exact issued Work Order.

## Frozen objective

For every governed outcome, Zeck must choose the lowest expected-cost execution representation that satisfies policy, capability, quality, reliability, latency, verification and side-effect constraints.

Primary business metric:

```text
cost per successfully resolved outcome
```

Supporting metrics include successful-resolution rate, time to successful resolution, model/inference cost, context cost, tool/control-plane overhead, retry/escalation cost, verification cost, substrate readiness/startup cost, duplication rate, and provider/infrastructure failure rate.

## Non-negotiable architecture

The architecture contains one optimization authority: **Execution Compiler**.

The following are compiler decisions or provider-adapter mechanisms, not new core authorities:

- model selection;
- reasoning-effort selection;
- tool-surface selection;
- context reduction;
- caching;
- result reuse;
- duplicate-work coalescing;
- batching/parallelism;
- agent-count selection;
- retry/escalation;
- substrate selection;
- service/inference tier selection;
- sandbox warm/readiness optimization;
- deterministicization.

The existing authorities remain canonical: tenant/application identity, policy, capabilities, budgets/economics, planning, execution lifecycle, sandbox/substrate, verification, evidence and learning.

## Canonical execution representation ladder

The compiler must consider the cheapest sufficient representation first when hard constraints permit:

```text
deterministic computation
 → cache/reuse
 → verified competence / existing tool
 → programmatic execution
 → small/sufficient model
 → higher reasoning effort
 → stronger/larger model
 → profitable parallel/multi-agent execution
 → computer use / human escalation where justified
```

This is a decision preference, not a mandatory linear pipeline.

## Work Order sequence

### WORK-049 — Execution IR and outcome-economics foundation

**Depends on:** WORK-048

**Scope:** machine-readable Execution IR; hard/soft optimization constraints; expected successful-resolution cost model; optimization decision record; provenance; invariant validation.

**Forbidden:** replacing the existing planner or execution authority; new optimizer service; speculative provider integration.

**Completion outcome:** a governed plan can be represented as an optimizable IR with deterministic validation and auditable decision evidence.

### WORK-050 — Deterministic Execution Compiler

**Depends on:** WORK-049

**Scope:** compiler engine and semantics-preserving transformations: constant folding, dead-step elimination, common-subexpression reuse, memoization hooks, safe parallelization, batching, result shaping, retry normalization, decomposition into deterministic/probabilistic subgraphs, verification insertion and model/effort selection hooks.

**Forbidden:** authorization changes; execution-state duplication; autonomous capability expansion.

**Completion outcome:** a governed plan can be transformed into an optimized IR under explicit preconditions.

### WORK-051 — Tool Surface Compiler and Programmatic Execution

**Depends on:** WORK-050

**Scope:** minimal useful tool-surface derivation; direct/deferred/CLI/script/code/MCP/competence representations; bounded programmatic execution in the existing sandbox authority; compact structured results.

**Forbidden:** universal MCP dependency; new tool authority; bypass of capability/policy.

**Completion outcome:** only the tools and representations required for the task cross the model boundary, and mechanical fan-out/filter/aggregate work can execute outside model context.

### WORK-052 — Context, cache, reuse and duplicate-work economics

**Depends on:** WORK-050

**Scope:** context-cost measurement; prompt/prefix cache planning; reusable artifacts/results; memoization; equivalent in-flight work coalescing; tenant-safe cache keys; duplication accounting.

**Forbidden:** cache as an authority; cross-tenant reuse; cache-derived authorization.

**Completion outcome:** repeated work is reused or coalesced when semantics, freshness, policy and identity permit it.

### WORK-053 — Adaptive model/reasoning and multi-agent economics

**Depends on:** WORK-050

**Scope:** quality-aware model selection; reasoning-effort selection; 0/1/N agent gate; expected quality gain versus cost/latency/verification burden; service-class selection where supported; fresh-escalation decision hooks.

**Forbidden:** always-on multi-agent behavior; model choice overriding Work Order assurance requirements; model routing as a separate authority.

**Completion outcome:** the compiler can select the least expensive model/effort/agent strategy consistent with the required outcome quality.

### WORK-054 — Economic substrate selection and runtime adapters

**Depends on:** WORK-050

**Scope:** neutral substrate facts and selection; readiness/startup lifecycle measurement; warm/snapshot-aware execution; provider adapters for E2B, Daytona and Modal; customer/self-hosted adapters where already supported.

**Provider treatment:**

```text
E2B       → adapter
Daytona   → adapter
Modal     → adapter
self-host → adapter
```

**Forbidden:** provider control-plane authority in domain modules; hard-coded provider semantics; mandatory provider adoption.

**Completion outcome:** Zeck can compare compute substrates by expected quality, readiness, latency, reliability and cost, then choose the least expensive sufficient substrate.

### WORK-055 — Failure-aware recovery, fresh escalation and continuation

**Depends on:** WORK-053, WORK-054

**Scope:** unified failure attribution; infrastructure/provider/tool/resource versus intelligence failure; retry/re-route rules; fresh escalation; continuation package; environment fingerprinting.

**Forbidden:** retry loops driven only by generic failure; attributing infrastructure failure to model quality; continuation as a second execution state machine.

**Completion outcome:** failures produce economically appropriate recovery strategies and long-running work can resume without unnecessary reconstruction.

### WORK-056 — Competence-aware optimization and progressive deterministicization

**Depends on:** WORK-051, WORK-052, WORK-053, WORK-055

**Scope:** competence as a selectable representation; progressive retrieval; successful-trajectory mining; deterministic replacement candidates; differential/property/replay evaluation; shadow/canary promotion; rollback.

**Forbidden:** self-promotion by agents; deterministic replacement without equivalence evidence; learning silently changing authority.

**Completion outcome:** repeated successful probabilistic work can become governed reusable competence or deterministic execution when evidence supports equivalence.

## Three-worker concurrency rule

The Tech Lead may dispatch **at most three** workers simultaneously.

Before every parallel dispatch, the Tech Lead must compare:

- declared source/module surfaces;
- tests and fixtures;
- migrations/schema files;
- package/toolchain configuration;
- shared architecture/governance documents;
- public contracts;
- runtime/provider manifests;
- development-state files.

No two workers may independently edit the same migration number, public contract, development-state file or architecture authority.

When reconciliation would require semantic manual invention rather than mechanical composition, the work is **not safe to parallelize**.

## Recommended safe waves

After WORK-050 is merged and finalized, the natural maximum-width wave is:

```text
WORK-051  Tool Surface + Programmatic Execution
WORK-052  Context + Cache + Reuse + Coalescing
WORK-054  Substrate Economics + Runtime Adapters
```

WORK-053 may replace WORK-054 in the wave when model/agent economics has the lower conflict profile for the current repository tree. The Tech Lead must decide from live surfaces, not this example alone.

## Quality gate

An optimization is not successful merely because it reduces tokens, calls or runtime cost.

It must preserve the required quality/reliability/verification threshold and must not increase governed side-effect or authority risk beyond the Work Order's contract.

The canonical comparison is:

```text
               lower expected cost
                       AND
        sufficient quality / reliability
                       AND
          preserved authority / safety
```

## Drift prevention

A worker MUST stop and request an Architect amendment when any of the following occurs:

- a required surface is not present;
- the implementation needs a new authority;
- the implementation changes a frozen v1.0 invariant;
- the implementation changes the E1.1 objective or compiler role;
- a provider-specific feature would become domain semantics;
- the required evidence cannot be executed honestly;
- the intended optimization cannot preserve the Work Order's assurance profile;
- another worker's changes become a prerequisite in a way not represented by dependency state;
- the work would require a second state machine, ledger or cache authority.

No worker may reinterpret an external provider's API or product model as Zeck architecture.

## Completion of the program

E1.1 is complete only after WORK-049 through WORK-056 are individually merged, finalized and governance-validated, and the Architect records a final architecture acceptance against the exact merged repository state.
