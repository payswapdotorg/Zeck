## Implementation

Surfaces (declared): `src/modules/executions/` (domain: identity/create contract, frozen state machine, envelope + verification-record types; ports: `ExecutionStore` (single mutation surface), `ExecutionAuthorizationPort` (REQUIRED inbound policy seam), `ExecutionsIdempotencyPort`; application: the single write-path service; adapters: SQL store + transactional idempotency arbitration over `platform.idempotency_records`; `public.ts` barrel), `src/platform/db/migrations/0004_executions.sql`.

Surfaces (directly required, disclosed): `tests/**` (new unit/PG/discrimination/architecture suites + shared fixtures `tests/unit/executions/fakes.ts`, `tests/integration/postgres/executions-world.ts`, `tests/discrimination/lib/execution-write-path.ts`), `spec/development-state/*.json` (the worker-protocol in-flight transition + checkpoint outcomes — the checkpoint-state entry was the prior session's uncommitted edit, verified and committed with this evidence). `package.json`/`bun.lock` untouched — runtime dependencies remain `[]`; no new packages.

Key mechanics:
- **Single write path, four layers**: (1) the frozen domain table is the only legality oracle; (2) the transition service is the only status writer (lock-before-decide on `SELECT … FOR UPDATE`); (3) the store port exposes exactly one mutation method (`updateExecutionForTransition`) paired with `appendEvent`; (4) migration 0004's `executions_forward_only` trigger rejects any execution-row UPDATE that does not append exactly one matching envelope, every UPDATE of a terminal row, and every DELETE. A static architecture gate (shared scanner) additionally pins exactly one UPDATE site, one event INSERT site, zero ledger mutation sites, zero out-of-module table references.
- **Creation atomicity**: ledger row + CREATED execution row + sequence-1 envelope commit in one transaction; a crash between any two writes rolls back both (proven on real PG).
- **Completion binding**: `pass` requires ≥1 `PASS` verification result in code (`VERIFICATION_FAILED` before any write), inserts the durable verification rows in the same transaction, and binds their ids on the row; `executions_completion_requires_verification` + `executions_verification_binding_shape` CHECKs and the `executions_verification_refs_durable` trigger (every referenced id must be a durable row of THIS execution) make the provider-success/planner-success shortcut uncommittable even with every service guard removed.
- **Authority seams**: `ExecutionAuthorizationPort` is REQUIRED (no default-allow implementation exists — a service cannot be constructed without a policy authority; the engine is WORK-007); the WORK-004 `BudgetAuthority` seam is consulted at `start`-with-dispatch (reservation BEFORE the transition commits); no policy/budget logic is reimplemented here.
- **Tenant authority**: application/environment existence + tenant asserted from durable rows at create; migration 0004 uses composite FKs (`(application_id, tenant_id)` → `applications.applications`, `(environment_id, application_id)` → `applications.environments`, children bind `(execution_id, application_id)`) so cross-tenant/cross-application rows are unrepresentable (proven on real PG).

## Design decisions (architect-review pointers)

1. **Idempotency arbitration mirrors the platform ledger exactly.** Same `(applicationId, operationName, idempotencyKey, requestFingerprint)` tuple as auth/applications/connections/budgets, over the same `platform.idempotency_records` partial unique index; scope is the APPLICATION, not the actor (per `spec/contracts.md`; proven by concurrent same-key creates with distinct actor ids converging). `executions.create` and `executions.transition` are distinct operation names; the transition fingerprint carries `(executionId, command, dispatch/verification/reason extras)` so a replayed command is recognized while a different logical command under a reused key fails `IDEMPOTENCY_KEY_REUSED`.
2. **Single write path made physical, not conventional.** The "no alternative write path" guarantee rests on four independent layers (domain table → service lock-before-decide → port surface → migration triggers), each individually proven; the scanner gate over real `src/` plus synthetic second-writer mutants (R3a/b/c) proves the static boundary discriminates. Direct SQL status mutation without a matching envelope is rejected by the database itself (schema suite) — the strongest form available.
3. **Gapless per-execution sequence (choice), not merely monotonic.** `IMPLEMENTATION.md` §4 requires "monotonically increasing"; gapless `1..N` is strictly stronger and chosen deliberately: the ledger is the authoritative ordered history, so every sequence number denotes exactly one committed envelope — consumers never distinguish a missing event from an in-flight one, and physical triggers can reject gaps and duplicates outright (`events_gapless_sequence` + `events_sequence_unique`). Cost, disclosed: the per-insert `MAX(sequence)` check makes the trigger O(events-of-execution); the service's row lock already serializes per-execution writers so the trigger is a backstop, and the ledger is bounded by the lifecycle's own edge count.
4. **Completion-verification binding is a physical invariant.** Code guard (`VERIFICATION_FAILED` unless ≥1 PASS), CHECK constraints (refs ≥1 iff COMPLETED) and the durable-reference trigger (refs must be rows of THIS execution, insertable only in-transaction) together remove every shortcut: a raw `UPDATE … SET status='COMPLETED'` with fabricated refs is uncommittable (proven), and the discrimination R2 mutant shows the green binding assertions detect a store that drops the binding.
5. **Provenance chain shape.** Every envelope carries who (`actor`), what (`command` + `type`), why (`cause`) and the durable facts the transition is bound to (`reference`: reservation id on `start`, verification-result ids on `pass`/`fail`, artifact/environment/user references on `create`) — satisfying EXECUTION-PROVENANCE's static+dynamic proofs with NOT NULL columns and real-PG lifecycle assertions.
6. **Replay semantics = current durable outcome, never a rewind.** Replays re-read the current row (create receipt and transition outcome both); a create retried after the execution progressed returns the CURRENT status with `replayed: true` and issues zero writes. Terminal states are final in code (no legal edge) and physically (trigger) — proven including direct SQL.
7. **Budget reservation ordering + failure semantics.** At `start`-with-dispatch the reservation is placed BEFORE the transition commits (admission precedes dispatch). The budgets fabric owns its own transaction, so a reservations-first order means: a rolled-back start attempt leaves a convergent hold that the SAME-key retry re-converges to (budgets' own idempotency — create-or-converge, lock invariant #11); the reservation id is durable provenance on the start envelope. Known limitation #3 records the residual (a permanently abandoned start leaves a releasable hold; release/settle orchestration belongs to the runtime Work Orders).
8. **Migration-surface disclosure: one additive `ALTER TABLE applications.environments`.** To make the environment binding composite-FK-safe (`(environment_id, application_id)`), 0004 adds `UNIQUE (id, application_id)` to `applications.environments` — an additive, non-behavioral constraint (id is already the PK) on a WORK-002 table, from within the declared migrations surface (WORK-003 precedent: DDL in migrations touching prior schemas for composite-FK anti-ambiguity). No other application/auth/budgets/connection/capability surface is modified.
9. **Provider selection is unrepresentable, not merely ignored.** The create input type has no provider field, and unknown TOP-LEVEL keys are rejected — the provider vocabulary (`provider`, `model`, `rail`, `connectionId`, …) fails with a specific "provider selection is forbidden" message while any other unknown key fails generically (both `POLICY_DENIED`, zero writes — proven). `metadata` remains free-form USER data by contract (never interpreted as routing), and the create path consults no provider/rail/connection surface at all — the provider fabric (WORK-003) is dispatched underneath executions by future runtime Work Orders, never named in this contract.

## Known limitations

1. **Authorization seam is a port, not an engine** (by design): `ExecutionAuthorizationPort` evaluates admission facts at the `authorize` edge; the policy engine, tenant policy administration and admission semantics are WORK-007 (`policies`). No default-allow ships — construction requires an authority; test fakes live under `tests/`.
2. **Waiting/resume, planning, tool and verification AUTHORITY semantics are future Work Orders**: WORK-006 owns identity, the frozen legality table, the ledger and the completion binding; what CAUSES a `wait-tool` or produces evaluator verdicts (WORK-008/010/013) is not implemented here — the `verify`/`pass` edges record and bind verification RESULTS, they do not evaluate.
3. **Dispatch-failure hold semantics**: a `start`-with-dispatch that fails after reserving leaves a convergent budget hold (same-key retry re-converges via the budgets fabric's own idempotency); release/settle orchestration for permanently abandoned starts belongs to the runtime Work Orders (WORK-009/010 seam).
4. **Gapless trigger cost**: the per-insert `MAX(sequence)` check is O(events-of-execution); acceptable because the service's row lock already serializes writers and lifecycles are edge-bounded; a high-volume ledger would warrant a counter column (future Work Order, not required now).
5. **CI has no PostgreSQL service** (carried over, governance-flagged since WORK-002): the 98 real-PG tests skip with an explicit reason in CI; local runs are the recorded proof (standing precedent).
6. **Webhooks (API-004), receipts with cost/quality summaries (API-005), listing/pagination** are WORK-015 surfaces; this wave exposes the service + store read paths only.
