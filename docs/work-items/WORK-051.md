## What this order IS

E1.1 stage 3: the **tool-surface compiler and bounded programmatic execution** — a new platform plane (`src/platform/tool-surface/`, 7 modules, ~2,600 new source lines) plus the ONE declared module-side seam adapter (`src/modules/sandbox/adapters/tool-surface-compute-seam.ts`, +1 additive barrel line). `deriveToolSurface` is a PURE function of (plan IR, governing constraints, configuration, digest): it extracts the plan's declared tool needs (`call-tool` steps, capability-bound), conditions every need READ-ONLY against the capability facts and the policy tool facts (the WORK-049 constraint mirrors of what the authorities captured at planning time — fail closed on unmet or absent facts; the derivation can never widen, grant or bypass), and selects EXACTLY ONE representation per need — the first admissible in the frozen canonical order over the closed seven-representation set (direct/deferred/cli/script/code/mcp/competence — MCP participates ONLY when both a binding exists AND the adapter is explicitly enabled, never a universal dependency) — recording one closed rejection code per non-selected representation. The surface is content-addressed (`surfaceId` = sha256 over the canonical form), MINIMAL by proof (`assertSurfaceMinimal`: exactly the declared need set, nothing else), and auditable (`auditToolSurface` re-derives deterministically — zero violations on a clean chain, typed violations on drift). Bounded programmatic execution (`fan-out`/`filter`/`aggregate`/`projection` over the closed JSON universe) runs OUTSIDE model context INSIDE the EXISTING sandbox authority: every run is a fully admitted, dispatched and journaled sandbox execution through the sandbox module's PUBLIC service (durable identity, policy → capability → budget admission, ledger envelopes, the REAL platform process runtime), with the four explicit bounds (items, iterations, output bytes, wall clock) enforced fail-closed at validation, inside the runner, and by the authority's timeout. The v1 crossing (content-addressed run file with the validated spec + bounded input embedded as constants) exists BECAUSE the frozen authority's request fingerprint covers the whole canonical task at ≤500 chars — argv/publicEnv crossings of real payloads are unrepresentable durably; the digest-pinned path keeps the durable task tiny while recording exactly which runner+payload content ran, and the idempotency fingerprint stays a pure function of the crossing content. Results are compact, structured, typed (`CompactStructuredResult`: per-operation typed shapes, bounded serialization, sha256 `resultDigest`, exact provenance — spec/sandbox/output-digest/surface identities), bound to the plan's mechanical-family step contract. **No new authority, no new state machine, no new durable surface (zero migrations — the store count stays 29), no changes to the foundation or the compiler engine, no planner/execution-lifecycle modifications, no vendor vocabulary, no runtime tool routing.**

## Selection decision examples (why a representation was / was not chosen)

- **Direct chosen** (integration, real planner): the real governed analysis plan declares one tool need (`document-retrieval`); the config binds `direct` (rank 0: context 0, orchestration 0, failure surface 0) plus `cli` and `mcp`. `direct` wins as the first admissible representation in the canonical order; `cli` records `lower-canonical-rank` (admissible but ranked after — the deterministic preference itself is the recorded evidence); `mcp` records `mcp-adapter-disabled` (the adapter is not enabled — MCP is one representation among the closed set, never required).
- **CLI chosen over MCP** (unit): with the adapter disabled and only `mcp` + `cli` bound, `mcp` records its typed rejection and `cli` is selected — the honest fall-through, never a silent MCP dependency. With ONLY `mcp` bound and the adapter disabled, the derivation fails closed `no-admissible-representation` (never a silently dropped tool).
- **Competence chosen when direct is absent** (unit): a tool binding all seven representations but `direct` selects `competence` (rank triple 1/0/1 — the next in the canonical order), recording `lower-canonical-rank` for the remaining admissible representations.
- **Programmatic execution enabled vs disabled** (unit + unit): a mechanical step declaring filter work under `programmaticEnabled: true` records the `declared` decision with the validated spec (the work executes through the sandbox authority); the same plan under `programmaticEnabled: false` records the honest `disabled` decision (the declaration is preserved as evidence; the work simply does not execute programmatically — never a silent degradation).

## Known limitations (honest boundaries)

- **Live MCP servers, live tool providers, live compute substrates: NOT RUN** — out of scope for stage 3 (and for this worker environment, which holds no provider credentials). The catalog's per-tool representation bindings are configuration DATA the composition root provides; no MCP session, CLI process, script artifact, code API or competence reference is materially invoked by this order — the surface records WHICH representation crosses, and the programmatic path proves the sandbox-authority execution mechanics with the real local process runtime.
- **The v1 crossing is the content-addressed run file**: the frozen sandbox authority's request fingerprint (500 chars over the whole canonical task) makes argv/publicEnv crossings of real payloads unrepresentable durably (the synthesis executor's own `-e` form only fits tiny programs — the same frozen budget). The run file persists for the host process lifetime (one bounded, write-if-absent file per distinct crossing content; ~39KB max); eviction/TTL of stale run files is later substrate work (WORK-054 territory), not this plane's authority. The runner file is written under the OS temp domain — the same best-effort domain the platform's own ephemeral sandbox workspaces use.
- **The closed mechanical vocabulary is deliberately small**: four operations (fan-out/filter/aggregate/projection) with closed parameters (equality filters, count/sum aggregates, bounded field projections) and the closed JSON universe. Richer mechanical work (joins, sorts, expressions, streaming) is later E1.1/E1.2 work — the kernel/runner drift-pinning test is the contract that keeps any future extension honest.
- **Programmatic execution requires a registered process-class environment** with the `process-sandbox` capability and an admitted timeout covering the declared wall-clock bound; container/microVM programmatic environments are the substrate stage's work (WORK-054 was deliberately deferred from this wave precisely because its sandbox/compute boundary pins overlap this order's footprint).
- **Plan-declared programmatic work requires the plan author to declare it**: the planner itself does not yet synthesize programmatic declarations (that is the compiler/later-stage integration WORK-056 consumes); the derivation records the honest `not-declared` decision for undeclared mechanical steps.
