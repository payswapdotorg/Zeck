## Design decisions (architect-review pointers)

1. **Verification is an authority, not a status field.** The module owns WHAT the evidence establishes (criteria registry, immutable results, conclusions); it owns NO policy (REQUIRED admission seam — the WORK-007 engine), NO execution lifecycle (only `verify`/`pass` issued THROUGH the executions authority port; the evaluator-job journal is `denied|evaluating|concluded` — the Work Order's allowed evaluator lifecycle, never execution states), NO planner state (the ReplanningBoundary port reports; the planner decides), NO provider fabric (the judge dispatches behind the `ModelJudge` port). Every "second authority" mutant is scanner-rejected (M13–M18).
2. **Provider success ≠ verification PASS is enforced at FOUR layers.** The domain (`validateResult`), the service (the conclusion derivation requires revision-matching PASS), the storage (migration 0007 CHECKs: status vocabulary + PASS-requires-evidence + PASS-requires-criteria) and the judge adapter (unbound/non-committal judgments map to INCONCLUSIVE). The M1 headline negative test is proven by static mutants (mapping gutted, HTTP-status shortcut), runtime red records (R1: fabricated completion rejected by the executions authority; R5: raw provider-success payload → INCONCLUSIVE) and PG facts (provider-success evidence never completes).
3. **Deterministic-first applies to verification itself (ADR-0007/0011).** Criterion kinds are closed: five deterministic kinds (schema/invariant/digest/exact-match/reference) are established ONLY by deterministic evaluators — evaluator selection is kind-bound (`establishes`), so a hidden AI call replacing deterministic verification is unrepresentable (M18 static + the unit "deterministic criteria never dispatch a model"). Model judges exist only for `model-judged` criteria and are themselves admitted per-dispatch (provider/model facts against the real policy engine).
4. **INCONCLUSIVE is an honest state, never acceptance.** The conclusion derivation takes the LATEST revision-matching result per required criterion; anything not PASS is unmet with its exact status (FAIL vs INCONCLUSIVE — the planner's distinct decision inputs per ADR-0008/0009). Stale PASS results for older plan revisions do not satisfy the current one (M12 — revision equality is load-bearing in the derivation, and the plan-revision resolver fail-closes unrecorded revisions).
5. **Human evaluation is governed evidence, not a customer-domain state machine (ADR-0009/0012).** Requests exist only through the policy-admitted path (M8); decisions are attributable (mandatory `decidedBy` + rationale — M19), exactly-once per request (trigger-enforced), and become ordinary immutable human-evaluator results journaled like every other result. The execution-side WAITING_HUMAN is the executions module's own edge, driven by the planner/orchestrator — the verifier never touches it.
6. **Candidate comparison is explicit and planner-owned (VER-004).** Non-planner initiation is rejected BEFORE any evaluation (service validation + storage CHECK); the winner is exactly-one-PASS (multiple satisfying candidates ⇒ INCONCLUSIVE with an explicit "no forced winner" rationale — the ADR-0012 uncertainty discipline); candidate identity and per-candidate evidence persist on the immutable comparison record.
7. **Completion is produced by /verification through the executions authority.** `concludeEvaluation` orders evidence-first: boundary report (unmet) → journal completion → conclusion envelope on the canonical ledger → `pass` transition LAST (terminal executions accept no further ledger events — the executions module's terminal-immutability discipline). The pass input is derived from THIS module's durable results; the executions authority enforces ≥1 PASS and the physical completion binding.
8. **Idempotency and convergence.** The evaluation journal keyed `(application_id, evaluation_key)` is the idempotency authority: same key + fingerprint replays the durable conclusion; different fingerprint fails `IDEMPOTENCY_KEY_REUSED`; concurrent duplicates converge via unique-index arbitration + in-process single-flight (N=4 PG test: ONE journal row, ONE PASS result, one completion); a crash-interrupted `evaluating` row is honestly re-drivable (new key) or replayed (same key+ fingerprint); human decisions and comparisons carry their own keyed anchors; the decision is journaled on its own evaluation row (M24's provenance binding holds for the human path too).
9. **Substrate-neutral targets (ACR-003/ADR-0016).** The target vocabulary is seven kinds (execution-output, plan-revision, artifact, tool-output, model-output, record, candidate) — evidence about a result, never one modality; target resolvers validate identity in the caller's scope through the OWNING modules' public services (artifacts content-addressed identity; executions-ledger planning decisions) — no parallel artifact identity system is created.

## Known limitations

1. The model-judge evaluator's production transport is the `ModelJudge` port seam; the real-PG and unit suites use scripted judges (the transport fake — the same discipline as the tools suites' fake adapters). Wiring the port over the models public gateway (structured-output judge prompts) belongs to the composition root / a later integration Work Order; the port contract, the binding check and the INCONCLUSIVE discipline are what this branch proves.
2. Cross-PROCESS concurrent duplicate evaluations converge on the durable identity (unique-index arbitration) but may append duplicate result rows (append-only evidence; the conclusion counts the latest per criterion — honest, never incorrect). In-process duplicates are single-flighted. A distributed single-flight/lock belongs with the platform's future coordination layer.
3. The policy authority's current nine-dimension vocabulary has no dedicated human-escalation dimension; the admission adapter maps human evaluation onto the autonomy ladder (the agents-module approval-gate precedent: `maxAutonomy: none` denies gated interactions — a real, tested deny path) and the model-judge dispatch onto provider/model facts. A dedicated dimension (if the architect adds one on the policies surface) maps trivially in the adapter.
4. `criteriaFingerprint` convergence uses structural comparison (kind/required/description/definition) — redeclaring with reordered object keys converges (canonical comparison); the SQL path compares serialized JSON (key-order-sensitive) and fails closed as a conflicting declaration rather than converging. Both behaviors are safe (never silent divergence); perfect canonicalization parity is cosmetic polish.
5. Evaluation-journal `denied` rows are insert-time or evaluating→denied only (a policy denial after partial evaluation throws; the durable denial is on the journal and replays as POLICY_DENIED). Mid-evaluation denial leaves the execution honestly VERIFYING (the verification phase started; the evaluation itself was denied) — the orchestrator decides the next edge.
6. CI has no PostgreSQL service (the standing WORK-002 flag): the real-PG proofs above are local-run evidence against the embedded server at `127.0.0.1:55432`.
