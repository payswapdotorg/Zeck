## Selection examples (why a cheaper substrate was / was not chosen)

- **Cheaper sufficient chosen** (unit, the representative corpus): with the 0.8 hard quality floor — `cheap-process-c` at 50 µUSD (quality 0.6) is below the floor: NEVER selected, every verdict carries exactly `quality-below-floor`; among the sufficient, `mid-container-b` snapshot wins (startup 25 + exec 200 = 225; `ceil(225/0.93)` = **242 µUSD** expected successful-resolution cost) over `mid-container-b` cold (280), `std-microvm-a` warm (437) and cold (548) — the warm mode wins over cold on a FRESH ready observation (startup collapse 400 vs 9000 ms readiness) when economics justify it, and never on stale evidence.
- **Cheaper NOT chosen** (the quality floor): the cheapest candidate is inadmissible below the floor — price never overrides quality, and the floorless/softened-floor selection forms are unconstructible (typed rejections, discrimination-proven).
- **Fail-closed negative outcomes** (never errors): zero candidates → `no-candidates` (zero-provider operation, no fallback substrate invented); all-below-floor → `no-sufficient-substrate` (mandatory adoption impossible). The negative outcomes are recorded, replayable evidence, so a caller can never misread an absence as an implicit provider default.

## Known limitations (honest boundaries)

- **Live provider APIs (E2B, Daytona, Modal, self-hosted runners): NOT RUN** — no provider credentials exist in this worker environment. Every adapter is exercised against typed CONTRACT DOUBLES implementing its declared transport contract (the documented provider-API surface each adapter translates); the doubles' behaviors encode the E1.1 research-baseline phase semantics (E2B creating/running/stopped, Daytona pending/running/stopped/archived, Modal's created/scheduled/started/ready/in-use/terminated). When live credentials arrive, the transport ports bind to the real SDK clients inside the adapter directory per the reconciled boundary table.
- **The provider SDKs are not dependencies**: `src/` contains zero SDK imports by design — the adapters ride typed transport ports so this order ships mechanism + boundary without vendor lock-in; the SDK allowlist entries are the reviewed pre-declaration of where each SDK may live.
- **No new durable semantics are claimed** — the accounting record composition is pure; the append through the EXISTING WORK-049 store is the caller's seam (invariant 8: zero new durable surface, zero migrations). The full real-PG integration battery provides regression evidence only; a dedicated substrate-append integration suite was deliberately not added because the plane holds no store.
- **Warm/snapshot awareness is decision INPUT, not runtime state**: the adapters report readiness through the neutral ladder at probe time; the plane does not maintain a durable readiness cache (freshness classification is over the caller-provided observations, bounded by the freshness window). A durable observation store would be a new durable surface — a later order's decision.
- **The adapters' readiness polls are bounded busy-waits over the transport's phase observation** (the `readinessTimeoutMs` budget, bounded [1s, 10min], fail-closed on expiry) — appropriate for the mechanism level; a production composition root may wire a backoff policy at its own seam without changing this plane's contracts.
- **The self-hosted adapter's readiness reporting requires the deployment to expose a health probe**; without one it is a typed PERMANENT failure (the adapter never fabricates readiness and never treats probe absence as ready) — deployments without probes keep full run capability, with readiness evidence unavailable by honest design.
- **One environment identity per adapter instance**: each adapter binds exactly one substrate (adapterRef 1:1) and derives one environment identity per (runIdentity, configuration, timeout) — the composition root instantiates one adapter per declared substrate. Multi-substrate fan-out is a composition concern, not an adapter contract.
