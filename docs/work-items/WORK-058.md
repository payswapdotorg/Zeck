## Required checkpoint contracts

- **TENANT-ISOLATION** — cross-tenant access impossible by construction at the worker/runner plane, including under evacuation and reassignment: the physical claim gate (0031) enforces claim.tenant = execution.tenant = environment.tenant on EVERY admission (a successor claim is a fresh INSERT through the same gate); the store surfaces typed `tenant-scope-refused`; the work executor maps the sandbox service's tenant guards to a governed `TENANT_SCOPE_VIOLATION` refusal (nothing dispatches); the external run identity is tenant-scoped; artifacts/secrets/evidence ride the tenant-scoped existing surfaces (the runtime spec carries only the environment's declared, admitted references). Proven: I3/I3b/I4 + the physical-gate integration tests + discrimination W5.
- **SANDBOX-BOUNDARY** — strict profiles restrict the capability surface and ambient host access is absent; selection is governed, never ambient: AC-3 + AC-5 above; the sandbox-boundary architecture gate (M1..M18) passes over the extended tree.
- **IDENTITY-IDEMPOTENCY** — admission/assignment under the same profile + policy context is idempotent: the profile derivation is pure (same spec → same profile — determinism test); identical re-registration converges on the same durable record (unit + integration "IDENTITY-IDEMPOTENCY"); the admitted metadata replays identically at dispatch (the snapshot is immutable); re-claiming converges through the existing claim identity discipline (I4's successor converges with exactly one dispatch).
- **CONCURRENCY-CRASH-SAFETY** — concurrent admission, evacuation and reassignment never widen scope or corrupt pool identity: the CONCURRENCY race test (parallel hostile + legitimate acquireClaim: exactly one admission, the legitimate pool-bound worker's, pool identity intact); I4's evacuation path (abandoned claims recoverable, hostile middles refused, same-pool successor converges); the physical gates are transactional trigger enforcement (no store bug can bypass them).
- **DEPENDENCY-DIRECTION** — the isolation plane depends only on the declared seams; module semantics are import-only; no authority consults isolation state for authorization: the isolation domain imports nothing (typed data only — discrimination W7 asserts no `PolicyAuthority`/`DatabasePort`/admission surface in it); no authority module (policies/executions/budgets/capabilities/verification/auth) references the isolation vocabulary (W7 mechanical scan); the sandbox module's cross-module imports remain public-barrel-only (the architecture gate passes); the compute plane's imports remain platform-only (B5 passes).

## Pool-isolation proof (Evidence Contract)

Two pools (`gold`, `silver`) of one tenant plus the platform's unbound first-party workers, over real PostgreSQL: a gold environment admits only gold-bound workers (the claim's `pool_id` is derived and recorded); silver-bound and unbound workers receive the typed `pool-mismatch` refusal at delivery, at recovery re-selection AND at direct store admission; the physical trigger rejects a direct-SQL cross-pool claim; quota accounting is per environment (saturating gold's quota leaves silver untouched); the worker pool binding and the claim's pool identity are immutable; the claim history of an evacuated-and-reassigned dedicated execution is entirely gold-scoped (`history.every(row => row.poolId === "gold")`). Cross-TENANT pools additionally fail the tenant gate first (two tenants using the same pool string share nothing: every comparison happens under tenant+application equality enforced by the composite FKs and the physical gate).
