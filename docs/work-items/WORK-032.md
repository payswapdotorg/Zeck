## The authority model (architect-review pointers)

1. **`intent != authorization != transaction != settlement != verification` — five separate durable vocabularies, physically separated.** Migration 0014 states and enforces it: there is deliberately no table in `economics.*` that can complete an execution, settle a budget reservation or verify a delivery. The economic-action lifecycle (`proposed → authorized|denied|expired`, `authorized → executing|expired`, `executing → settled|failed`) is CHECK-bound, forward-only, terminal-immutable and no-delete.
2. **Policy is the hard authorization boundary and it comes FIRST.** The policy admission port is required; a denial is journaled with cause and produces zero downstream effects (M12's deleted/moved gate is scanner-rejected; R-M12 proves the order). A 402 signal is advisory input to a draft that must still pass the full chain (M8/R-M8). Agents and LLMs never approve transactions — deterministic constraints are evaluated by deterministic code (`evaluateAuthorizationUse`).
3. **Budget remains the canonical spending authority.** One reservation operation per action (`econ-<actionId>`, UNIQUE), reserved before issuance, ceiling = the intent's maximum amount, settled through the real `BudgetAuthority` — charge-path money movement lands on the 0003 budgets ledger, never a second ledger (M10's foreign-write/adapter-DDL/foreign-table/dropped-idempotency-reuse mutants are all rejected).
4. **Rails are replaceable, non-authoritative adapters.** The rail port has no authorize verb and the payment-rails integration tree may import only the economics public barrel (M19); a constraint-blind rail is refused before any charge (M22/R-M22); the rail is reachable only from the `authorized` status, and the charge path journals-then-dispatches: the durable `executing` transition + dispatched event commit BEFORE the rail call (M14/R-M14 — the ordering found to deadlock on real PG was reordered in `223cb80` so the terminal-mirror journaling precedes the terminal row write).
5. **Bounded, tokenized, single-use authorization.** Constraints are hard-pinned from the intent at issuance; every use is re-checked against them (recipient/amount/currency/purpose/scope/expiry substitution all denied with distinct codes — M2..M6); authorizations are consumed once (M7) and expire no later than their action (bounded expiry trigger).
6. **No payment credential crosses any boundary.** Recipients are `kind+id` references; the credential-exposure scanner watches the wire/serializer/rail-request/command contracts, the metadata scrub, the route contracts and client-supplied scopes (M1); the 402 parser carries no credential-shaped or provider-protocol field; no vendor identifier appears in the core contracts or API routes (M20).
7. **Learning is evidence, never authorization.** The economics module imports nothing from learning; the outcome-facts projection is pure data-out over durable records; the admission inputs are learning-free (M21/R-M21).
8. **The public HTTP surface is intent-creation + reads.** `POST /economic-actions` (intent only), `GET /economic-actions/:id`, `GET /:id/events`, `GET /:id/outcome`. The authorize/charge/settlement/delivery mutations are NOT routable over the public API (route test proves absence) — they live behind the module-level governed seams so the admission chain cannot be bypassed by an HTTP caller.
9. **Sandbox note.** WORK-032 declares no sandbox surface and uses none: economic actions are bounded by the policy/capability/budget seams, not compute isolation. The `SANDBOX-BOUNDARY` contract is therefore out of scope for this Work Order; the economics boundary is proven under `ECONOMIC-AUTHORITY-BOUNDARY`.

## Limitations

- **Simulated, contract-tested rails only — no real rail integration.** The `payment-rails` integration ships the provider-neutral rail contract + two simulated in-process adapters; the integration tree is network-free by design (scanner-enforced). Wiring a real provider (Stripe or any other) requires a declared dependency, credentials held by the platform's secret authority (never the agent runtime) and its own governed adapter boundary — a future Work Order decision. Provider replacement neutrality is proven at the contract level.
- **No real financial transaction was observed** (by design — see the honesty statement); the Work Order's interoperability checkpoint is met on the "contract-tested" branch of the requirement.
- **No SDK client methods for economic actions.** The provider-neutral wire TYPES are exported (`src/shared/wire.ts`: `EconomicAction`, receipt, events, outcome), but `sdk/` and `cli/` carry no economic-action client methods yet — future experience-layer work following the existing SDK pattern.
- **The learning consumer of the outcome-facts projection is not implemented in the learning module.** `economicOutcomeFacts` is the emission seam (pure data-out over durable records); consuming it into learning telemetry/scorecards is future learning-surface work (the learning module's surfaces are NOT among WORK-032's declared surfaces — the projection is deliberately the boundary).
- **API mutations are module-level seams, not public routes.** `POST /economic-actions` (intent), the three GET reads and the events/outcome projections are public; authorize/charge/settlement/delivery mutations are exposed only through the economics service's governed seams (proven unroutable over HTTP). Lifting them into HTTP routes would be an explicit API-surface amendment with its own admission design.
- **Two implementation defects were found only on real PostgreSQL** and fixed in `223cb80` (disclosed, not hidden): the SQL economic store's INSERT missed the 13th `recordedAt` parameter (order/count mismatch invisible to the in-memory store), and the charge path's terminal-mirror journaling originally wrote the terminal row before the mirrored event — a real-PG FK/row-lock deadlock; journaling now precedes the terminal write.
- **CI runs no real-PG suites** (the standing WORK-002 flag: no PostgreSQL service in CI); the PG proofs are local-verified against real PostgreSQL 16.4 and recorded above. The local instance reported 16.4 where earlier work orders' evidence recorded 17.11 — the harness is version-agnostic SQL; role/CREATEDB privileges verified before the runs.
- **The `57P01` teardown transient** (the documented platform-wide intermittent in the shared PG harness teardown, not a WORK-032 file) fired in a minority of runs with all tests passing each time; each such exit was followed by clean exit-0 runs (disclosed per suite above).
- **Authorization constraints are pinned at issuance time.** A policy/budget change after issuance does not retroactively mutate an existing bounded authorization (it still expires, stays single-use and amount/recipient-bounded); re-authorization under the current policy is a new mint through the full chain. This is the bounded-authorization trade-off, disclosed as designed behavior.
