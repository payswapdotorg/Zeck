## Architecture note (within the work order's allowed surfaces)

The chain orchestration (vision -> structured description -> derived media) lives in the multimodal-transformation application slice (`apps/multimodal-transformation/chain.ts`) over the EXISTING rails, per the design guidance — no rail code duplicated. The new platform slice `benchmarks/validation/platform/three-d.ts` carries: the structured-description derivation from a vision answer (the shared cross-modal bridge: a fixed four-field JSON schema — `subject`, `colors`, `background`, `composition` — parsed and mechanically validated; unparseable/missing/mistyped fields are honest invalids, never degraded descriptions), the 3D generation task shape (seeded prompt + declared geometry parameters), deterministic materialization with explicit NOT-RUN boundaries, canonical request bodies with sha256 request digests, the 3D "render" verification (GLB/OBJ container validity by structure — GLB magic/version/declared-length, OBJ decodable text with vertex and face lines — plus declared-format match, payload presence and digest capture; never aesthetic judgment), the surfaced `THREE_D_ACCESS_REQUIREMENT`, the dispatch binding (four pre-dispatch discriminations: wrong-modality, fixture-digest mismatch, blank prompt, invalid declared geometry — all before any network effect; the honest `three-d-rail-absent` failure when driven without a rail; bounded retry for RETRYABLE failures only when a rail later exists) and the execution driver mirroring `driver.ts`. Chain honesty invariants: each stage's output is mechanically verified BEFORE the next stage consumes it (a FAIL criterion at any stage aborts the chain — there is no provider-success shortcut); a stage failure aborts the chain with the exact stage recorded (`chain-aborted` criterion; later stages carry honest not-executed flags); per-stage provenance (request digest, response digest, measured latency, measured usage) travels on the chain outcome into evidence; the chaining itself is visible in evidence (stage 2's request digest IS stage 1's response digest); BOTH stage planning decisions are recorded on the REAL execution ledger BEFORE the dispatch (intent before effect, per stage); usage, cost and latency are measured, never estimated; payload DIGESTS (never bytes) appear in evidence.

## Issue findings and protocol

- **Stage-verification gaps found by this slice's own unit tests, fixed pre-commit.** The first draft of the chain binding aborted only on provider FAILURES — a stage whose provider succeeded but whose mechanical criteria FAILED (a missing oracle term in the vision answer; a delivered-but-malformed raster at stage 3) let the chain continue. Classification: implementation defect in the first draft of `chain.ts` (a violation of the work order's "each stage's output is mechanically verified before the next stage consumes it"). Solution: every stage now checks its criteria for FAIL statuses immediately after derivation and aborts the chain at that stage with category `stage-verification-failed` (the failing criteria themselves are recorded). Verification: the unit suite's two oracle-provenance tests and the discrimination suite's malformed-payload test (all initially red, all green after the fix). Impact: none beyond this branch (found before any dispatch path ran).
- **Shared Response objects are single-use (found by the discrimination suite, fixed pre-commit).** Reusing one scripted `Response` across tests consumed its body once and made later vision dispatches fail as empty completions — a test-harness defect that masqueraded as chain failures. Classification: test-harness defect. Solution: fresh response factories per use. Verification: the discrimination suite re-run. Impact: none.
- **No live provider verification was possible in this sandbox** (no credentials, by design). The chain's REAL rails are the ALREADY live-verified VAL-015/VAL-017 rails (reused wholesale, unmodified); the chain-level behaviors (per-stage verification, abort propagation, provenance) are verified against controlled fakes; the Lead's credentialed re-run is the live verification. Any live shape divergence is an honest finding to record here.
- **The structured-description schema tolerates extra fields (recorded calibration decision).** The instruction pins exactly four fields and the derivation validates the required contract (presence, non-emptiness, types); an answer carrying additional fields still derives validly. A stricter additionalProperties rejection would be brittle against live model verbosity for no mechanical gain — the required-field contract IS the oracle floor. Classification: validation-design decision. Evidence required to revisit: the Lead's live re-run observing the actual answers.
- **3D OBJ container well-formedness requires vertex AND face lines (recorded calibration decision).** "Container validity" for OBJ is not standardized the way GLB's header is; this slice requires decodable text with at least one `v` line and one `f` line (a renderable mesh declares both). Classification: calibration decision (the criteria only matter when a rail exists; they are offline-proven against synthetic OBJ artifacts). If a future rail delivers face-less OBJ previews, the criterion pins move in a corrective change with the Lead's live evidence.
- **The chain's wrong-modality row is credential-free by design.** The row (a foreign `transform-image` task) is rejected at the chain entry before any materialization or network effect, so the crown suite drives it whenever PostgreSQL exists — including the both-credentials-absent case — as REAL platform-path evidence with zero provider dispatches. Classification: validation-design decision (strictly stronger than the prior waves' both-absent trivial pass; the notRun list still records every absent-credential row honestly).
