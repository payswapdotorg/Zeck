## Architecture note (within the work order's allowed surfaces)

Two customer-style applications plus two platform slices, all additive in the allowed surfaces (`src/**` and `spec/**` untouched):

- **The chained multimodal-transformation slice** (`benchmarks/validation/platform/multimodal-transform.ts`): the platform derives the chained dispatch plan (stage-1 vision request facts over the deterministic synthetic source — fixture digest, seeded structured-description instruction, canonical stage-1 request digest; stage-2 derivation scaffold + declared raster size; route facts for BOTH stages) and drives the REAL chained dispatch by **chaining the two PROVEN rails**: VAL-017's OpenRouter vision rail (stage 1) feeding VAL-015's dashscope-international multimodal-generation rail in text-to-image mode (stage 2). The stage-2 prompt **genuinely binds the stage-1 structured description** (mechanically extracted from the vision answer), so the chain is REAL; each stage's request digest and output digest, measured latency and usage are captured for per-stage provenance. The structured-description contract is mechanical (JSON object with exactly `main_object` (from the fixture's closed vocabulary), `setting`, `palette`, `style`; fence/prose-tolerant extraction — normalization only, never content fabrication). Discriminations fire before the relevant network effect: closed vocabulary, fixture-digest mismatch, BOTH rails configured before ANY dispatch (never spend stage-1 money on a chain that cannot run stage 2), malformed-intermediate abort before any paid stage-2 dispatch, blank derived prompt. Provider failures at either stage FAIL and ABORT the chain (chain-abort propagation: a stage-1 failure means the generation transport is never called — provable by zero transport calls). Bounded per-stage retry for RETRYABLE failures only; waits are part of the measured latency.
- **The 3D generation/rendering slice** (`benchmarks/validation/platform/three-d.ts` + `three-d-container.ts`): pure derivations (seeded-spec materialization with NOT-RUN boundaries; spec validation against the closed primitive vocabulary; dispatch plan with request digest; verification by **container validity (magic-byte glTF `.glb` / binary STL / text OBJ sniff — never extension, never provider mime), byte bounds, non-empty payload, sha256 digest capture** — the work order's own "container validity and digest" rule), the neutral `ThreeDRail` seam an operator-authorized provider binds onto later, and the dispatch binding whose honest no-authorized-3d-rail boundary failure carries the exact surfaced access requirement. **No fabricated rail, endpoint or model result exists anywhere** — the REAL 3D dispatches are recorded NOT RUN boundaries.

## Issue findings and protocol

- **Stage-abbreviation discipline (found by the implementation's own discrimination design, fixed pre-commit).** An early binding sketch allowed a stage-1 vision success to spend a paid stage-2 dispatch even when the generation rail was unconfigured (wrong-modality discovered only at stage 2). Classification: test-strength/economics defect (pre-flight). Solution: the binding checks BOTH rails BEFORE any network effect — a chain that cannot run stage 2 never spends stage-1 money (the E1.1 right-representation preference). Verification: the unit test "a chain without BOTH configured rails…" proves zero transport calls on both seams.
- **Malformed-intermediate spending (found by the discrimination design, fixed pre-commit).** A stage-1 answer that is not a valid structured description would have been forwarded as a stage-2 prompt (spending a paid image generation on a provably-invalid intermediate). Classification: economics/honesty defect. Solution: the structured-description gate aborts the chain with category `malformed-intermediate` BEFORE any paid stage-2 dispatch. Verification: the discrimination test "a malformed stage-1 intermediate…" proves zero generation-rail calls.
- **Test-authoring bug (caught by the suite itself, fixed immediately).** Two assertions in "a chain without BOTH configured rails…" initially swapped the abort stages of the two one-rail configurations; the suite failed, the assertions were corrected to the binding's actual (and intended) semantics. Classification: test defect, no product change. Verification: the corrected suite passes (46/46).
- **No defects found in the new platform/app surfaces.** The structured-description parser's fence/prose tolerance is mechanical normalization of where the JSON object sits in the answer — it never alters, completes or augments the model's content (extraction only).
