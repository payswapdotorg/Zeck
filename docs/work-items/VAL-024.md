## System under test (per the work order's declaration)

The REAL PostgreSQL row-scoping — **every store query bound by application + tenant** — is the system under test, exercised at its two REAL surfaces:

- **The executions service (the locked-row discipline):** `src/modules/executions/adapters/sql-execution-store.ts` binds `lockExecution`/`getExecution`/`listEvents`/`listVerificationResults` by `application_id` (a foreign execution locks NO row in this application), and `src/modules/executions/application/execution-service.ts` derives the typed violations from the locked row: a create for another tenant's application → `TENANT_SCOPE_VIOLATION` ("application belongs to a different tenant"); a create with another application's environment → `TENANT_SCOPE_VIOLATION` ("environment does not belong to the target application"); a transition/planning-decision/step-event against a foreign execution → `TENANT_SCOPE_VIOLATION` (the locked-row miss: "execution not found in this application (missing or owned by another application)"); a tenant-mismatched command on an own execution → `TENANT_SCOPE_VIOLATION` ("execution belongs to a different tenant" — the locked row's tenant wins). The reads are scope-checked misses (null / zero rows — never data).
- **The public API (the server-side scope derivation):** `src/api/routes/executions.ts` resolves the scope server-side per request (the client's tenant assertion is never read as authorization authority — M2/M3): a foreign execution through the own scope is a 404 `CAPABILITY_UNAVAILABLE` scope-checked miss (indistinguishable from missing — M1, no tenant leak); the wire's create path carries the service's typed violation for a foreign environment (403 `TENANT_SCOPE_VIOLATION` — public); a forged `x-zeck-application` scope and a confused application-id create are refused by the auth scope resolver over the real membership rows (403 `AUTHORIZATION_DENIED` — the header never authorizes by itself).

The tenant-id confusion shape is worth recording honestly: at the SERVICE boundary the command carries the tenant explicitly (the operator path), so the locked-row tenant-mismatch check is directly exercisable (the `svc-*-tenant-mismatch` probes). At the WIRE boundary the tenant is DERIVED server-side from durable membership — a client cannot even express a tenant-mismatched command there (the `TENANT_SCOPE_VIOLATION` tenant-mismatch branch is defense-in-depth at the wire, unreachable by construction). Both surfaces are probed at their own honest shape.

## Architecture note (within the work order's allowed surfaces)

`src/**` and `spec/**` are untouched (forbidden by this work order; verified — the delivery is 100% additive, six new paths, zero edits to tracked files). The slice mirrors the VAL-021/022/023 platform-slice pattern:

- **The probe taxonomy as PURE derivations** (`benchmarks/validation/platform/tenant-isolation.ts`): the ten probe families (cross-tenant create-application / create-environment / read / transition / artifact-fetch / step-event / planning-decision, cross-application state-probe, forged-scope, and the false-positive control) map to concrete probe plans — the operation attempted, the foreign reference channel and the EXPECTED typed rejection (service: `TENANT_SCOPE_VIOLATION` for the locked-row families, `SCOPE_CHECKED_MISS` for the reads; wire: `TENANT_SCOPE_VIOLATION` 403, `AUTHORIZATION_DENIED` 403, `CAPABILITY_UNAVAILABLE` 404). The typed-rejection matcher matches the CODE (and the pinned wire status), never a status-only or message-only approximation; the foreign-content evidence scan hunts the planted synthetic canaries (findings carry the marker LABEL and digest — never the material); the row-count invariants derive the zero-foreign-effects and accounted-own-writes verdicts mechanically.
- **The driver** (`driveTenantIsolationExecution`) mirrors the sibling drivers: authorize → plan → planning-decision BEFORE the battery → queue → start → the row-count window opens → the probe battery (each probe: attempt → observe → match → foreign-content scan → journal EXACTLY once through the platform's OWN `agent-action-recorded` step-event vocabulary) → the row-count window closes → the invariant derivation → verify → terminal: any admitted probe, any leaked content, any row-count violation, any journal mismatch → FAILED (never a partial-success shortcut). The battery drives BOTH seams through injected ports: the executions-service surface (bound to the REAL service in the crown) and the public wire surface (bound to the REAL public clients over the REAL Fastify server — the scoped client and the forged client constructed with the OTHER application's scope). The isolation probes need NO provider: the scope checks are pre-dispatch (usage honestly `none`, per-probe latency measured).
- **The application** (`benchmarks/validation/apps/tenant-isolation/`) rides the public SDK boundary: per row it performs its own customer-side cross-tenant access attempts through the public clients (read/cancel/result/events/verification of the foreign execution; the foreign-environment and foreign-application creates; the forged-scope client), asserting each typed rejection and scanning each surfaced boundary for foreign content — then submits the carrier task through the standard harness flow (submit → poll → result) and asserts the row's outcome contract (the isolation-held battery COMPLETES with PASS verification; a FAILED there is an honest isolation-failure finding, never a fabricated isolation).
- **The corpus** (`tenant-isolation.probe.v1`, AC1/AC2): ten rows, each declaring the isolation probe family and the expected typed rejection per surface. Every row is deterministically reproducible with zero network and zero credentials — there are NO live-gated rows (the system under test is the platform's own row scoping, which needs no external rail).

## Mechanical verification (AC4)

- **Typed probe assertions:** every probe observation is matched against the plan's expected rejection — the CODE for typed errors (plus the pinned wire status on the wire surface), the zero-rows observation for reads, the own-scope admission for the control. A wrong code, an admission, or a wrong status FAILs mechanically.
- **Evidence-scan for foreign content:** the foreign world is seeded with SYNTHETIC canaries (the task-content canary, the metadata classification marker, the ledger-event marker — never real tenant data); no marker may appear in ANY probe outcome, criterion evidence, app evidence or durable ledger row. The scan's findings carry the marker label and digest, never the material.
- **Row-count invariants per tenant/application before and after the battery:** the foreign application's durable rows (executions, execution_events, verification_results, idempotency_records) must be IDENTICAL (zero foreign effects — the SQL row counts are read live inside the battery's window); the own application's delta must equal EXACTLY the driver's accounted journal writes (an unaccounted write — a "denied" probe that wrote anyway — is a mechanical isolation failure). The crown adds battery-wide invariants: the foreign rows identical before/after the whole corpus, the own executions delta exactly one carrier per row, cross-application anti-joins zero both directions, the foreign execution still `CREATED` (no cross-tenant transition ever landed).
- **The isolation journal:** each denied probe journaled EXACTLY once through the REAL ledger (`agent-action-recorded` with digest references only), ledger-verified by the crown.

## Discrimination tests (AC6 — `tests/discrimination/tenant-isolation-validation.discrimination.test.ts`)

Nine discrimination tests over the controlled fakes (each boundary exercised twice — the REAL semantics replayed, then the deliberately WEAKENED stand-in whose admission must FAIL the assertions):

- **forged tenant headers:** the REAL wire refuses the forged scope (403); a mutated server that ADMITS it (200 + the foreign record) fails the app (the admission AND the canary disclosure are both caught).
- **application-id confusion:** the REAL wire refuses the confused create (403 AUTHORIZATION_DENIED); a mutated server that ADMITS it (201) fails the row.
- **artifact-ref probing (wire + service):** mutated surfaces that answer the foreign execution/event/verification probes with the other tenant's data fail mechanically (the miss assertion catches the admission; the scan catches the canary).
- **locked-row mutations:** mutated services that admit the cross-tenant transition, the tenant-mismatched command, the foreign-application create or the foreign-environment create all FAIL (the typed-rejection criterion catches the admission; the row-count invariants catch the durable effects).
- **silent-write mutation:** a service that denies the probe but leaves a durable row (own-scoped OR foreign-scoped) fails the corresponding row-count invariant.
- **journal duplication:** a lifecycle that journals each probe TWICE fails the accounted-writes invariant (the exactly-once contract is load-bearing).
- **the control discrimination:** the control row never vacuously passes (the mutated read seam still fails the cross-tenant rows).

## Issue findings and protocol

- **The planning-decision probes were initially rejected as POLICY_DENIED, not TENANT_SCOPE_VIOLATION (found by this slice's own REAL-service unit tests, fixed pre-commit).** The REAL `recordPlanningDecision` validates its input shape BEFORE the locked-row check — an empty payload object is a pre-effect `POLICY_DENIED` ("planning decision requires a non-empty payload object"), so the first probe drafts never reached the scope boundary. Classification: probe-calibration defect (an invalid probe shape masked the real boundary). Solution: the probes (driver + crown + unit tests) carry a non-empty minimal payload `{ probe: ... }` — the validation passes and the locked-row check fires. Verification: the REAL-service unit tests now observe TENANT_SCOPE_VIOLATION for all four planning/step-event probe shapes. Impact: none beyond this slice (the sibling drivers' lifecycle planning decisions always carried full payloads — the defect was probe-local).
- **The driver's read probes initially targeted the foreign execution for the control row too (found by the driver unit tests, fixed pre-commit).** The read-target resolution only distinguished "reverse-foreign-scope" from everything else, so the control's own-execution reads hit the foreign execution and observed a scope-checked miss instead of own-scope data. Classification: probe-targeting defect. Solution: `readTargetOf` (PURE) resolves all three reference channels (foreign-execution / reverse-foreign-scope / own-execution). Verification: the control row now admits own-scope data and completes.
- **The fake wire's error shape initially carried a custom `httpStatus` field (found by typecheck + the env-create row's FAILED battery, fixed pre-commit).** The public client surfaces `ZeckApiError { status, body: { code, message } }`; the fake threw a different property name, so the driver's wire observation read `httpStatus: null` and the pinned-status match failed. Classification: fixture-fidelity defect. Solution: the fake wire throws the exact `ZeckApiError` shape. Verification: the env-create row's wire probe observes 403/TENANT_SCOPE_VIOLATION and matches.
- **Terminal semantics calibration (recorded design decision).** The probe rows COMPLETE when the battery proves the isolation held (mirroring the VAL-023 defended-completion semantics: there the goal was the probe, so the expected denial/rejection completes the execution). The control row completes on legitimate admission. Both are honest; the divergence from VAL-019's edge semantics (the purchase goal failing on refusal) is the same design decision VAL-023 recorded.
- **No live provider verification and no PG-backed crown run was possible in this sandbox** (no credentials needed — and none used; no PostgreSQL — by design). The typed-rejection semantics ARE verified against the REAL platform modules through the in-memory binding (recorded above); the SQL row-scoping itself (the lockExecution application binding over real PostgreSQL) is the Lead's crown re-run. Any live divergence is an honest finding to record here.
