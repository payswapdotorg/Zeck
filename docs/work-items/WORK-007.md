## Design decisions (architect-review pointers)

1. **Precedence semantics = per-scope meet, then scope chain.** Documents matching a request fold per scope (the tightest common form over every field — associative and commutative, so resolution is order-independent), then scopes apply in the frozen platform > application > user > task > execution order. At most ONE document per (scope, selector) is enforced at publish (determinism/totality: no ambiguous subject). A `deny` document is absolute from ANY scope and is checked FIRST — there is deliberately NO allow primitive in the vocabulary, so no lower authority can weaken a prohibition by allowance.
2. **Restriction vocabulary with comparable, not merely describable, fields.** Every one of the nine dimensions is typed with explicit tightness semantics (cost ceiling in integer micro-USD strings — the WORK-004 money convention, floats never accepted; quality floor 0..1; latency ceiling ms; provider/model + tool + host + secret-ref allow/deny lists; egress/secret-access/autonomy descending ladders; isolation ascending ladder per §15). Tightening = smaller ceiling / larger floor / subset allowlist / superset denylist / rank move toward tight. Validation rejects unknown fields, off-ladder values, list duplicates, and allow∩deny overlaps — malformed policy data never becomes authoritative.
3. **Monotonic tightening is fail-closed rejection, and the fold is an independent backstop.** `resolvePolicy` returns a typed `weakening` denial when a present lower scope's folded set is not at-least-as-tight as the next higher present scope's — the operator-facing POL-003 enforcement (proven removable only by the P2 mutation). Independently, the effective set is the MEET over every present scope, so even a configuration that somehow skipped the check still resolves to a set at least as tight as every scope's contribution — the two mechanisms are complementary (check = detect + reject; fold = compute the tightest), disclosed here so the architect can weigh the redundancy deliberately.
4. **Admission evidence rides the executions ledger — no migration this round.** Policy DEFINITIONS are configuration-resident versioned data (`PolicyStore` port; the in-memory adapter ships — WORK-005 store-port precedent); the DURABLE record of decisions is the executions EventEnvelope ledger: every authorize envelope carries `reference.policy = {policySetId, policySetVersion, policyContentHash, restrictionSetDigest}` and denials carry the same evidence on `execution.policy-denied`. That ledger is already physically append-only, gapless and provenance-bound (WORK-006, migration 0004 triggers — re-proven for the denial envelope on real PG below). Introducing a policies-owned durable table now would duplicate the ledger's authority (forbidden: no second state machine), so no migration exists in this delivery and none is needed for the criteria.
5. **`PolicyStore` + `PolicyHasher` ports are the durability/hash seams.** The authority is pure orchestration: a future SQL `PolicyStore` (one row, version-monotonic, same load/save contract) and any `PolicyHasher` plug in without touching domain or seams. `node:crypto` is confined to the single 16-line `node-policy-hasher.ts` adapter (the WORK-008 digest-confinement precedent).
6. **Publish arbitration is serialized, monotonic and convergent.** Promise-chain single-flight (WORK-005 registry precedent): validate → content-hash → compare with current → save. Identical republish converges (same hash), version rollback or same-version-different-content is rejected typed, concurrent identical publishes converge to one publication. Validation failures fail closed at publish (`POLICY_DENIED` "invalid policy data" with the issue list).
7. **Executions edits are additive; the denial write path is the SAME single write path.** The state machine table, store port surface, migration and SQL adapter are untouched. Inside the existing transition transaction, a policy denial now journals ONE `execution.policy-denied` envelope and advances the ledger sequence through the same `appendEvent` + `updateExecutionForTransition` pair (status stays CREATED — the row write is the identity-preserving sequence advance), then throws typed `POLICY_DENIED` AFTER commit (journal-then-fail, the WORK-003 dispatch-journal precedent). The idempotency record stores the denial outcome, so a same-key retry replays the same typed denial with no second envelope (proven on real PG). The OLD behavior (typed `AUTHORIZATION_DENIED`, zero writes) was WORK-006's interim seam contract; criterion 4 of THIS order mandates the typed `POLICY_DENIED` + durable evidence semantics — the one adapted WORK-006 unit assertion is disclosed below.
8. **The two seam adapters delegate; they decide nothing.** `createExecutionAuthorization` maps the locked execution row's durable facts (tenant, application, task kind, execution id + the row's own constraints) to a `PolicyAdmissionRequest`; `createDispatchAdmission` maps `AdmissionInput` (tenant, application, rail, model) to a `PolicyDispatchRequest`. Both are type-only couplings to the owning modules' public barrels (zero runtime dependency); the static gate proves delegation and flags any local decision logic.
9. **Evidence identity = canonical content, not configuration layout.** `canonicalPolicyJson` sorts object keys at every depth and sorts+dedupes string lists (restriction lists are SETS), so identical policy content in different document order or list order hashes identically and yields identical restriction-set digests — the evidence a ledger envelope binds is stable under semantically-identical republishes (proven in the canonical-form suite and the PG evidence tests).

## Known limitations

1. **Policy definitions are configuration-resident this round** (in-memory `PolicyStore`): no durable policy-configuration storage exists yet. The durable ADMISSION trail (decisions + evidence) is on the executions ledger; a durable definitions adapter is a future Work Order at the `PolicyStore` seam (design decision 4/5). A process restart requires re-publishing the current set (deterministic: same content → same identity → converges).
2. **Enforcement breadth vs. the runtime seam**: the authorize seam enforces the execution-level facts (cost/latency ceilings of the row's own constraints); the OTHER dimensions are carried by the effective set (digest-recorded at admission) and enforced at the DISPATCH seams — the models dispatch seam is wired here (`createDispatchAdmission`); tool/agent/sandbox/secret dispatch seams belong to WORK-009/010 and consume `admitDispatch`/the effective set from this module.
3. **Task/execution-scope selectors are declarative**: `taskKind` comes from the execution row's task kind; per-plan/per-step policy refinement (INT-003) is future planning authority. Execution-scope documents key on `executionId` (pre-admission pinning of a specific execution is possible but not yet produced by any runtime flow).
4. **The adaptation of one WORK-006 unit assertion** (AUTHORIZATION_DENIED/zero-writes → POLICY_DENIED/one denial envelope) is a contract evolution mandated by this order's criterion 4/5; all OTHER WORK-006 suites (schema, lifecycle, concurrency, write-path discrimination) run unchanged and green.
5. **CI has no PostgreSQL service** (carried over, governance-flagged since WORK-002): the 103 real-PG tests skip with an explicit reason in CI; local runs are the recorded proof (standing precedent).
6. **Two vitest-layer transient exits** during this session's verification (zero failing tests; disclosed in the verification table) — same class as the WORK-005 disclosure; not reproducible across 11 subsequent consecutive greens.
