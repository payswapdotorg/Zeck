**The verification core (the four new oracles):**
- **the configuration-conformance oracle** — every setting the competitor APPLIES must be declared in the pinned configuration revision: the executor reports its per-request applied set, and an applied name outside the declaration (the undocumented-configuration masquerade — something the competitor does that its declared configuration does not name) FAILs mechanically (`deriveCompetitorConfigConformance`);
- **the behavior-variance oracle (the reproducibility core)** — the competitor's routing either REPRODUCES (equivalent requests of the same class rode the same pool endpoint) or the variance is OBSERVED, and observed variance FAILs UNLESS the configuration declares it as honest variance (a competitor behavior change between runs — nondeterministic routing — without the declaration is a SILENT ROUTING CHANGE); the confidence half rides the comparison itself (the frozen VAL-040 protocol battery fails any confidence-less comparison — the Wilson 95% interval is REQUIRED, never waived for the competitor) (`deriveBehaviorVariance`);
- **the model-selection-conformance oracle** — every request rode the model-selection table's declared rail for its class (the fallback for unnamed classes): a request riding an undeclared rail FAILs mechanically;
- **the retry-posture-conformance oracle** — every request's internal attempts stayed within the declared automatic-fallback bound (attempts ≤ maxInternalRetries + 1): an undeclared retry escalation FAILs mechanically.

Plus the configuration-integrity oracle (the content-digest agreement — an in-place bound mutation with a stale digest FAILs), the replay-fidelity oracle (the offline executor's reported usage/endpoint/internal-attempts equal the recorded competitor-interface trace — a token understatement or a fabricated observation FAILs), the charge-observation-separation oracle (the rail's own charge is an observation, never the basis — every sealed cost fact's source is manifest-priced and every charge observation carries measured usage facts; the mixed-basis conflation catch) and the frozen-portfolio reference integrity (the VAL-030 content digests re-derive through the platform's own `manifestDigestOf`).

**The execution driver** (`driver.ts`): drives one competing row through the platform path — the landed execution's chain records the ARM DECISIONS BEFORE DISPATCH (the declared competitor configuration revision + digest + the model-selection table + the retry posture + the variance declaration and — for fixed-cost arms — the per-round budget bound, the worst case over the row's declared classes' model selections composed with the manifest's own batched metering) in the durable planning decision, then each pre-registered round runs through the competing stack: the fixed-cost budget gate before each request, the request through the competitor's interface with client-side bounded retry on RETRYABLE transport categories only (the competitor's OWN internal fallback happens inside each request — one request, one AGGREGATE usage report), and the per-fact usage normalization through the pinned manifest onto the canonical micro-USD basis (the competitor's own charge rides as a cross-check observation — digest-referenced, never the basis). Every round is sealed through the REAL recorder, evaluated through the REAL oracle and aggregated through the REAL aggregate; the comparison is derived + validated against the frozen VAL-040 protocol (`deriveNormalizedComparison` + `validateNormalizedComparison` + `deriveEconomicRowCriteria` — all imported from the VAL-040 delivery and reused unchanged over the structurally-compatible row). The verdict is MECHANICAL: any failure, any failed criterion → verdict fail → terminal FAILED; the observed terminal is read back from the ledger and a disagreement FAILs the row honestly.

**The corpus** (`corpus.ts`): 9 rows — 7 offline (deterministic) + 2 live (env-gated). Every row references the FROZEN app portfolio (the VAL-030 baseline revisions) by CONTENT DIGEST (the manifest entries read from the frozen corpus's exported surface — the artifacts never copied), declares the arm manifest entry (the frozen VAL-040 grammar, `integrationSurface: "stack:openrouter"` per the VAL-005 competing-stack arm grammar), the pinned competitor-configuration revision and the expected normalized outcome (the REAL derivations over the declared fixtures + the fixed-cost budget-gate simulation — exactly what the driver's own accounting must reproduce). **The app** (`application.ts`): the customer application riding the public SDK boundary — one pinned corpus row per run (the submission → the completion poll → the result retrieval → the deterministic assertions), with the app-side economic contract (the VAL-040 derivation, imported) verifying the terminal↔criteria agreement over the public result read.
