### THE ROUND-5 SIBLING DEFECT — the staged-identity `commands_pkey` collision (found by the first complete-gate run at `c42c2ff`; IN-SURFACE, fixed)

**Root cause (root-caused from the PostgreSQL server log `/home/z/pg16/pg.log`, which recorded the raw error under the failing run)**: the stress pinner above survived the 0025 gate collapse but STILL failed intermittently under full-suite load with `PlatformError: the keyed row already exists with a different identity (key reuse)` — mapped by `toTypedGuardError` from an underlying `duplicate key value violates unique constraint "commands_pkey"` raised by `insertCommand`'s `INSERT … ON CONFLICT (application_id, command_key) DO NOTHING`. The arbiter constraint `(application_id, command_key)` can NEVER raise under that clause — the violation was on the **PRIMARY KEY `(id)`**, a NON-arbiter unique index: **PostgreSQL checks a speculative insert's unique indexes in index order, and `ON CONFLICT` with an explicit arbiter target does NOT suppress a violation of a different unique index** — so the collision fires as a hard error even when the arbiter would also have conflicted (and converged). The trigger: the crash-stable command identity — `submitCommand` reuses the STAGED `commandId` checkpointed on the durable operation (`edge-service.ts`, the WORK-027 stage-checkpoint discipline, so the wallet reservation keyed by it converges across retries) — so a same-key racer that begins AFTER the first racer's operation checkpoint reuses the SAME id; once the first insert commits, every such racer's insert collides on `commands_pkey` before the key arbiter is consulted, and the keyed convergence surfaces as a hard unique violation. (Racers that begin BEFORE the checkpoint commit generate their own fresh ids and converge through the arbiter — which is why the defect fired only under load-dependent timing, once the window widened.)

**The fix (in-surface, `src/integrations/edge/adapters/sql-edge-store.ts` — the migration needed NO amendment; the 0025 header claim stands)**: `insertCommand` now treats a violation of the identity-carrying indexes — `commands_pkey` / `ec_identity_unique`, the only unique indexes the staged-id reuse can legitimately hit (the stage is keyed by the operation key, which is derived from the command key; every other submission carries a fresh generated id) — as the keyed-convergence path: it falls through to the existing keyed re-read, which arbitrates the request fingerprint exactly as the arbiter path always did. This is precisely the in-memory twin's semantics (the in-memory store converges by key FIRST, before any id is considered — the SQL twin now matches). NO semantic check is bypassed: the sequence-gate trigger runs BEFORE INSERT regardless (the typed reuse/sequence/gapless rejections are unchanged — pinned by the semantics-preservation test), and the keyed re-read surfaces `fingerprintMismatch` for the SERVICE's typed `IDEMPOTENCY_KEY_REUSED` rejection. Every OTHER unique violation — the gapless sequence arbiter `ec_sequence_unique` in particular (the different-key-same-sequence race) — keeps its typed guard mapping, so a bare `ON CONFLICT DO NOTHING` (which would have un-typed that race) was deliberately NOT used.

## Design decisions

- **The sandbox module owns the governance; the accelerators integration owns the substrate** (the WORK-031 anatomy): the training domain/ports/service/store live under `src/modules/sandbox/` (the declared module surface); the provider-neutral substrate seam is `ports/accelerator-substrate.ts`; `src/integrations/accelerators/` (domain/ports/adapters/public.ts, the WORK-029-edge module shape) implements the simulated neutral fleet + the runtime adapter + the substrate-federation operator path. The choice (a new `src/integrations/accelerators/` rather than extending substrate-federation) keeps the accelerator substrate a self-contained integration with its own public barrel, while its capability CLAIMS ride the EXISTING substrate-federation registry — no second catalog (pinned by the architecture gate).
- **No second authority, no second execution state machine**: policy admission (the REAL WORK-007 engine), capability/substrate claims (the REAL substrate-federation registry), budget admission (the REAL WORK-004 `BudgetAuthority`), execution identity (the FROZEN executions module — the workload rows reference it through composite FKs and NEVER write execution status), provenance (the canonical EventEnvelope ledger through the frozen `recordStepEvent` seam — the EXISTING step-event vocabulary; WORK-030 adds no vocabulary), verification (the REAL verification module's promotion authority). The adapters map facts and delegate.
- **The idempotency key families** (one durable effect per stable key, across process death): workload admission `(application, workload_key)` + the request fingerprint; budget reserve/settle/release keyed by the stable workload/attempt discriminators; the fleet allocation + run ledgers keyed per workload attempt (the simulated fleet's keyed idempotent ledgers); checkpoint emission keyed by the MATERIAL content identity; completion/cancellation envelopes keyed per ATTEMPT (a retried workload's success must not collide with its failed attempt's burned key); release operations keyed per verification REQUEST (re-verification after a failed verdict must be representable); the run lease per (application, workload).
- **The simulated accelerator fleet is the world-level DURABLE external substrate at the PG level** (one instance shared by every booted process — a real fleet outlives the Zeck process). Its external behavior is **UNVERIFIED** (declared in-tree at `src/integrations/accelerators/adapters/simulated-accelerator-fleet.ts` and `public.ts`; pinned by discrimination D9 — see Limitations).
- **deployments surface: honestly unused** — verified by absence: `git diff --name-only a074f983..HEAD` contains ZERO `src/modules/deployments/` entries (sandbox + integrations sufficed; the WORK-027/028/029 precedent). **sandbox consumed as the PRIMARY surface**: the training governance lives in `src/modules/sandbox/**` (17 files: domain/ports/application/adapters + the public barrel extension) — the declared module surface, used extensively (this is where the Work Order's "training workloads are governed Executions" lives).
- **Migration discipline (parallel wave-7)**: **WORK-030 claims 0025** — `0025_training_accelerator_workloads.sql` (the `sandbox.training_workloads/checkpoints/operations/run_leases` schema with physical guards + the inherited edge-gate single-statement collapse fix), pinned in the file header AND here; 0001–0024 untouched (0015 burned by WORK-019; 0022 WORK-028's, 0023 WORK-027's, 0024 WORK-029's — all merged in the frozen base). - **The accelerator/GPU/scheduler substrate is SIMULATED — UNVERIFIED against real GPU/accelerator/cloud training providers**: `simulated-accelerator-fleet.ts` models the substrate (the neutral fleet catalog with per-class capacity, the keyed idempotent allocation/run ledgers, the per-class active-allocation accounting, the checkpoint-emitting run) with keyed idempotent effects; real accelerator hardware, real schedulers, real fleet accounting and real cloud training providers are **UNVERIFIED**. - **The stress pinner is probabilistic, honestly labeled**: the deterministic proof of the inherited edge-gate fix is the single-statement snapshot collapse itself (one snapshot per trigger invocation, by construction); the 15×2 stress loop pins observable convergence at ~15× the baseline firing-rate exposure — it is a pinner, not a deterministic impossibility proof for arbitrary schedules.
