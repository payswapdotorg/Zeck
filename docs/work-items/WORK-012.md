## Design decisions (architect-review pointers)

1. **The sandbox is an environment, never a second execution system (ADR-0004/ADR-0001).** The module owns environment identity/specifications, the sandbox admission/dispatch journal and nothing else. Policy decisions live behind the REQUIRED `SandboxAdmission` seam (the WORK-007 engine); capability resolution behind the REQUIRED `SandboxCapabilityResolution` seam (the WORK-005 registry); budget reservation through the WORK-004 `BudgetAuthority`; execution lifecycle/evidence behind the REQUIRED `SandboxExecutionLedger` seam (the executions public service — step events only; the sandbox module never moves execution status and never writes executions tables). No second state machine, no second ledger — scanner-enforced end to end.
2. **The admission chain is the repository-canonical §7 order.** request validation → tenant-guarded execution binding → environment resolution (identity + lifecycle) → POLICY admission → CAPABILITY admission → BUDGET/resource admission → durable bundle → ledger evidence. No provider is consulted before admission (M15: dispatch requires the admitted row through the one-shot `claimDispatching` transition; denied rows are insert-only and cannot dispatch). Journal-then-fail denials (policy/capability/budget) are durable denied rows + `sandbox-denied` envelopes + typed canonical errors.
3. **No-execution is first class (M17).** A `no-execution` environment is a legitimate explicit choice: it declares no limits/runtime/workspace/egress/secrets (validated kind-consistently), submits NO isolation fact at admission (nothing runs — there is no isolation to evaluate; a policy isolation floor constrains executing kinds, never the no-execution choice), skips the capability gate, and dispatches as a structural no-op that never consults a provider. The platform never forces a runtime on a plan that needs none.
4. **Resource values never fall back to unlimited host defaults (M4/M18).** Executing kinds MUST declare cpu/memory/time bounds — a missing bound is a validation failure, not a default; the bounds table pins the mandatory fields (discrimination-guarded); the runtime enforces the time bound and the service enforces it defensively. Costed compute (estimate > 0) fails closed without a wired budget authority and reserves at admission, settles actuals at completion, releases on failure (idempotent per operation).
5. **The dangerous states are unrepresentable at THREE layers.** Contract layer: no field can express host mounts/host network/ambient env/secret values (network is none|allowlist; filesystem is isolated-ephemeral + opaque refs; env is explicit publicEnv validated against 9 secret patterns + secret-shaped names). Validation layer: host-shaped references rejected at spec/task validation. Adapter layer: the platform escape validator rejects every escape-shaped container configuration (the docker socket called out explicitly) and the container provider validates before dispatch, failing closed when guarantees cannot be established (no runtime client configured → honest `runtime-unavailable`, never a permissive fallback).
6. **Runtime metadata is immutable and dispatch is snapshot-driven (M13).** The admitted snapshot (spec + task + admission evidence) is persisted write-once (physical trigger); dispatch always executes the ADMITTED snapshot — a since-suspended environment cannot change what runs. `no-execution` completes structurally; executing kinds resolve a provider from the registry (capability-before-provider held at admission; the registry is dispatch infrastructure); an unwired substrate fails closed.
7. **Crash semantics are honest (§14).** Same key + same fingerprint replays; key reuse with a different fingerprint fails `IDEMPOTENCY_KEY_REUSED`; concurrent duplicates converge through PostgreSQL unique-index arbitration (the bundle commits in one transaction). A crash between the dispatch claim and the outcome leaves the honest `dispatching` row — retry fails closed as `NON_CONVERGENT_EXTERNAL_EFFECT` (sandbox code execution cannot be proven idempotent) instead of silently re-executing. The completion envelope is appended BEFORE the terminal row update (envelope-before-terminal ordering; terminal rows are physically immutable, so a terminal row without its envelope is unreachable).
8. **The step-event vocabulary stays executions-owned.** The three sandbox commands were added to `STEP_EVENT_COMMANDS` in the executions domain — the exact additive extension chain the merged WORK-010/011 comments document for module producers. No other module defines step-event vocabularies (architecture-gated: the constant exists exactly once in src/).
9. **The provider seam is execution-agnostic and reference-only (M14/M8).** `SandboxProvider` references no execution status/transition vocabulary, carries no stores/services/authorities, and its runtime spec carries secret REFERENCES only — no field in any runtime/public shape can hold a secret value (scanner-enforced). Platform mechanics live in `src/platform/sandbox/` (which imports no module — the platform-isolation rule); provider SDKs import nowhere (none is declared).
10. **Isolation honesty is documented, not claimed (M18).** The process runtime provides explicit-env + no-shell + ephemeral-workspace + hard-timeout isolation and is NOT a security boundary against arbitrary untrusted code — the POLICY isolation dimension decides which kinds may run where (a container floor denies process for untrusted work, proven). The container runtime is the untrusted-code path; without a configured runtime client its dispatch fails closed. No isolation is claimed that was not proven in this environment.

## Known limitations

1. **No concrete container runtime ships** (honest posture, M18): no container-runtime SDK is a declared dependency and the SDK boundary table pins none — the `ContainerRuntimeClient` port is the seam a Docker/containerd/OCI adapter (or the WORK-019 fleet runner) implements. Container dispatch without a client fails closed (`runtime-unavailable`); the full governed path is proven with a recording client (unit platform-seam suite) and the configuration validator proves every escape-shaped configuration is rejected. Actual OS-level container isolation was NOT exercisable in this environment and is NOT claimed.
2. **The process environment is not a security boundary against arbitrary untrusted code:** it provides explicit-env + no-shell + ephemeral-workspace + hard-timeout controls; host network/filesystem restrictions for process-class work are NOT OS-enforced here (documented in `process-runtime.ts` and design decision 10). This is exactly why containers are the initial untrusted-code path and why the policy isolation floor (proven: `minIsolation: container` denies process sandboxes) governs which kinds may run where.
3. **No runtime cost metering ships:** the process/container providers report `usageMicroUsd: "0"` (unmetered). Costed environments still enforce admission-level budgeting (the reservation bounds the spend and fails closed when underfunded — proven), and settlement uses runtime-reported actuals; real metering arrives with the runtime adapters.
4. **CI has no PostgreSQL service** (standing flag since WORK-002): the PG suites are env-gated and skip visibly in CI; the locally-executed real-PG runs above are the recorded proof (embedded PostgreSQL 16.4).
5. **Secret materialization at adapter dispatch is not wired:** the runtime contract carries secret REFERENCES only (by design); the connections-vault materialization seam a real container runtime would call for allowlisted refs arrives with the runtime adapters (the WORK-003 BYOK model is untouched — no second secret store exists here).
6. **Artifact staging for container mounts is a contract-level model:** `readOnlyArtifactRefs` are opaque references the object store stages; the recording client proves the mount projection (artifact refs + the synthetic workspace only — host-shaped sources rejected), while a real runtime client performs the actual staging.
7. **Parallel-PR merge interaction with WORK-013 (PR #22, unmerged at the time of this evidence):** both branches extend the SAME `STEP_EVENT_COMMANDS` array in `src/modules/executions/domain/event.ts` and the SAME exact-vocabulary assertion in `tests/unit/executions/step-events.test.ts` (additive entries on both sides — a trivial textual conflict the architect resolves by taking both sides); both also touch `spec/development-state/{program,frontier,checkpoint}-state.json` (each moves only ITS OWN Work Order's entry — likewise additive at the JSON-entry level).
