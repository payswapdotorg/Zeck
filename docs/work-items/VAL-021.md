Per-decision-distinct idempotency keys everywhere the ledger sees distinct payloads (the VAL-018 lesson — the per-attempt journal, the per-effect journal, the per-depth escalation keys); the re-escalation probe deliberately re-issues the SAME key + payload (the idempotent replay — the authority receives the escalation exactly once).

The driver's criteria derivation follows the VAL-020 review calibration: NO short-circuit on a failed outcome — the criteria prove the SEMANTICS (bounded retry, journal exactly-once, effect multiplicity, resume-exactly-once, escalation routing) so a correctly-bounded exhausted retry PASSES every criterion while the terminal stays honestly FAILED; the failure's own category rides the run result's `failure` field. The no-op resume replay is observed AFTER the terminal completion (the probe re-issues the completion itself), so it CANNOT ride the pre-completion criteria — the driver returns `noOpResumeReplayed` and the caller asserts it (the VAL-013 no-op-resume precedent).

The app (`benchmarks/validation/apps/idempotency-continuation/`) declares the corpus (AC1): 9 offline rows + 2 env-gated live rail rows, each row declaring the submission pattern (duplicate / conflict / retry / escalate / continue), the submission contract (total creates, expected replayed receipts, expected typed rejections), the expected ledger outcome (terminal, wait-user/resume cycles, escalation routing, the bounded dispatch attempt sequence) and the expected effect multiplicity (the exactly-once settlement contract). ## Issue findings and protocol

- **The first driver draft never journaled the effect records to the lifecycle port (found by this slice's own unit tests, fixed pre-commit).** The `applyEffects` helper pushed to the driver's local array and the world's journal hook but never called `lifecycle.recordEffect` — the REAL ledger would have carried no effect journal. Classification: platform-driver defect. Solution: `applyEffects` awaits `lifecycle.recordEffect` per applied effect. Verification: the unit suite's per-row journal assertions. Impact: none beyond this slice (found before any PG path ran).
- **The first criteria derivation short-circuited on a failed outcome (found by this slice's own unit tests, fixed pre-commit).** The exhausted retry row's criteria collapsed to a single failure criterion — deviating from the merged VAL-020 calibration (a correctly-attributed/bounded failure PASSES its semantics criteria while the terminal stays honestly FAILED). Classification: test-oracle/driver calibration defect. Solution: no short-circuit — the criteria are derived fully; the failure's own category rides the run result's `failure` field; the outcome-contract criterion compares the oracle's expected terminal against the outcome-derived one. Verification: the exhausted-row unit test (all criteria PASS + terminal FAILED + failure category journaled). Impact: none.
- **The no-op resume replay cannot ride the pre-completion criteria (recorded design decision).** The probe re-issues the terminal completion itself, so it is observable only after the criteria have been recorded on the ledger. The driver returns `noOpResumeReplayed` and the unit/discrimination/crown suites assert it directly — the VAL-013 no-op-resume precedent, followed exactly.
- **The stale-worker probe's admitted double resume now counts as an admission (calibration fix, pre-commit).** The first draft only set the failure; the resume-exactly-once criterion saw one admission against one park and PASSed. The admission now increments `resumeAdmitted`, so the criterion detects 2 admissions against 1 park mechanically. Classification: test-oracle defect. Verification: the double-resume discrimination test.
- **The faulted dispatch's request digest originally included the attempt number (calibration fix, pre-delivery).** The digest is over the LOGICAL request (execution + segment); the attempt is journal metadata — every retry of the same logical request must carry the SAME digest (the reproducibility contract). Classification: fixture-design defect. Verification: the request-reproducibility unit test (all three retries digest identically).
- **No live provider verification and no PG-backed crown run was possible in this sandbox** (no credentials, no PostgreSQL — verified directly, by design). The lifecycle binding, the ledger assertions and the gateway binding mirror the live-proven VAL-013/019/020 crown precedents exactly; the Lead's credentialed re-run is the live verification. Any live divergence is an honest finding to record here.
- **Live-row oracles pin continuation semantics, not model behavior beyond the confirmation word (recorded risk).** The live rows require the continuation supervisor to answer "continue" (the VAL-013-proven protocol). A model that refuses to confirm fails the healthy rows honestly — a capability-matrix datum, not a harness defect. The attempt sequences are deliberately unpinned for live rows (a transient rail failure may legitimately retry within the bounded policy).
