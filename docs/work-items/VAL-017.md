## Issue findings and protocol

- **Doorbell fixture misclassification (found by live model-selection probes, fixed pre-commit).** The original `event-001` design (ding-dong-ding at 880/660/880 Hz) was classified "alarm" by both omni models (6/6 misclassifications) — multiple rapid tones read as an alarm signature. Classification: fixture-design defect. Solution: the canonical single-chime doorbell (587 Hz, 1200 ms, slow decay) — stable ("doorbell" 4/4 on `qwen3-omni-flash`, 2/2 on `qwen-omni-turbo`) and cleanly discriminative against the rapid-beep alarm ("alarm" 4/4). Verification: the crown run's contains:doorbell PASS.
- **Chart-oracle instability (found by stability probes, fixed pre-commit).** The corpus row's `containsText: ["trend"]` appears in free chart descriptions only 1/3 runs (the model paraphrases: "positive linear relationship"). Classification: oracle-strength defect (paraphrase-prone ground truth). Solution: the pinned VLM task asks the focused question ("Is the line in this chart rising or falling?") whose one-word ground truth ("rising") is the fixture's own annotation term — 3/3 stable. The corpus row's intent (the chart's trend is captured) is preserved by a mechanically stronger oracle. Verification: contains:rising PASS.
- **Healthy-row rate limits tolerated by the first crown run (found by the first REAL run, fixed pre-commit).** Two healthy rows were 429-rate-limited mid-run and the val-010-style consistency assertions did NOT catch it (a provider-failed healthy row still satisfied `appPassed === (expected === terminal)`). Classification: test-strength defect. Solution: (a) the crown assertions now REQUIRE each row's corpus-declared terminal (healthy rows must genuinely complete; corrupted rows must genuinely fail) and require the apps' assertions to PASS; (b) the platform dispatch binding gained a bounded retry policy (2 extra REAL attempts, 6 s delay) for RETRYABLE failures only — non-retryable failures (corrupted media, auth, wrong-modality, digest mismatch) are never retried, and retry waits are part of the measured latency. Verification: the final crown run has every healthy row COMPLETED (img-c-002 via one honest retry, latency 13272 ms) and every corrupted row FAILED.
- **Provider-failure taxonomy verified live:** the corrupted PNG produces a REAL OpenRouter 400 ("Failed to load image: cannot identify image file"); the corrupted WAV a REAL dashscope 400 ("The audio is empty"). Both map to invalid-request (non-retryable) — the FAILED edge rows are genuine provider rejections, never synthetic journal entries.
- **Model-availability findings (live-probed, recorded):** the stale vision model IDs above; audio chat models absent on dashscope-intl compatible-mode; `qwen3-asr-flash` requires the dedicated ASR task API (not usable through the chat rail). The two selected rails are verified working.
- **Transient flake:** one live-load failure in the full integration suite's first run (val-010's REAL dispatch after heavy probe traffic); isolated rerun and full-suite rerun green (the recorded VAL-009 flake class).
