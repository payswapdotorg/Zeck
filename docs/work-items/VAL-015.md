## Provider rail (per the work order's design guidance; live verification is the Lead's re-run)

- **Image generation AND transformation:** dashscope-international, the multimodal-generation task API for `qwen-image-2.0` (env credential `QWEN_API_KEY`, host `dashscope-intl.aliyuncs.com`, env-overridable model via `ZECK_VAL_015_IMAGE_MODEL`). Text-to-image rows dispatch `{ model, input: { prompt }, parameters: { n: 1, size: "W*H" } }`; transformation rows dispatch `{ model, input: { prompt, image: <data-URI of the synthetic source> }, parameters: { n: 1 } }`. The compatible-mode chat endpoint is NOT used (it is the understanding path, not the image-generation path).
- The rail handles BOTH provider answer shapes honestly: a synchronous image payload (content parts / results entries as data/base64 — or an image URL fetched through the SAME injected transport, still a REAL fetch) and the async task API (task id → bounded polling of the REAL task endpoint → SUCCEEDED/FAILED/CANCELED/UNKNOWN). Image bytes are sniffed by magic bytes (PNG/JPEG), their declared dimensions parsed from the container header (PNG IHDR / JPEG SOF markers), and usage captured from the provider's report (`image_count` → output tokens; nothing estimated).
- **NOT RUN in this worker's sandbox:** no operator credentials reach workers by design — every REAL provider dispatch (generation and transformation rows alike) is an env-gated NOT RUN boundary here. The Tech Lead re-runs the crown suite with the authorized credential at review time; the offline battery below is the recorded proof of everything short of the live wire.

## Issue findings and protocol

- **Edit-fixture region out of bounds (found by this slice's own unit tests, fixed pre-commit).** The first draft of `img-edit-001` declared the bus-body target region as `[24,46,216,142]` — y1=142 exceeds the 256×128 fixture's height (the bus occupies y 46..120: body 46..96, tires to 120). Classification: fixture-design defect. Solution: the region-grounds test now mechanically bounds-checks every edit fixture's target region against its decoded source (`[24,46,216,120]` shipped). Verification: the unit suite's edit-fixture table-integrity test. Impact: none (found before any dispatch path ran).
- **JPEG transform outputs cannot be pixel-compared in pure TypeScript (recorded boundary).** The pixel-region change bounds require a losslessly decodable output container; the dependency-free decoder handles PNG (the rail's expected format). A JPEG transform output still passes container/dimension/payload/digest criteria but FAILS change-present/intersects-target with the mechanical reason `output-not-pixel-decodable` recorded — an honest mechanical failure, never a fabricated pass. Classification: external limitation (no lossless JPEG decoder without new dependencies). Viable solutions: (a) keep the honest FAIL (chosen — no new dependencies, no aesthetic shortcut); (b) add an image dependency to the lab (rejected: repository-borne weight for one edge); (c) request PNG output from the rail (parameter support unverified). Evidence required to revisit: the Lead's live re-run observing the rail's actual output container.
- **Declared-size support on the live rail (recorded risk, by design).** The healthy generation rows declare 1328×1328 and 1664×928 (rail-supported shapes adapted from the corpus rows' 512×512 / 768×512 aspect intent) and the dimensions-declared criterion requires exact equality — an unsupported size would fail honestly (a visible 400 or a mechanical dimension mismatch, never a silent pass). Classification: calibration decision. If the live rail quantizes sizes, the honest failure surfaces in the Lead's re-run and the row pins move in a corrective change.
- **Empty-prompt edge row is a pre-dispatch rejection (by design, mirroring the corpus).** The corpus's "edge: empty prompt" row expects FAILED/FAIL; the platform rejects a blank prompt BEFORE any paid dispatch (zero transport calls — discrimination-tested) rather than gambling on the provider's blank-prompt behavior. Classification: validation-design decision (the platform never spends a paid dispatch on a provably-invalid request).
- **No live provider verification was possible in this sandbox** (no credentials, by design). The rail's response-shape handling (synchronous content images; task-id polling; data/base64 and URL references; usage image_count) is implemented per the work order's design guidance and verified against controlled fakes; the Lead's credentialed re-run is the live verification. Any live shape divergence is an honest finding to record here.
