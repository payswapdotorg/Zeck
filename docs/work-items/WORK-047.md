## The delivery model (what the machinery actually does)

- **The release identity** (`src/platform/release/port.ts`): a release is the exact Git revision + the manifest digest; its id is content-addressed (`sha256(["zeck-release-v1", gitRevision, manifestDigest])`). A release not tied to an exact 40-hex commit is unrepresentable (fail closed at the store boundary — the discrimination proof). The per-environment deployment binding records the D-01 deployment identity document (idempotent; identity mismatch is a typed refusal; the binding is immutable).
- **The promotion ladder** (`src/platform/release/policy.ts` + `deploy/manifests/release-policy.json`): the CLOSED gate-kind vocabulary (13 kinds with scope and evidence contracts) and the per-phase entry gates. The ladder order and per-phase requirements remain the D-01 `environments.json` truth — the policy loader FAILS CLOSED on drift (every environments.json requirement must be covered; the weakening mutation is rejected by the unit + discrimination suites and pinned by the architecture B8 floor).
- **The ledger** (`src/platform/release/pg-store.ts` + migration `0029_release_control.sql`, schema `release_control`): releases immutable (attribution: id, exact commit, manifest digest, recorder, time); environment deployments immutable; gate results APPEND-ONLY attempts (the latest attempt per kind is the effective result — a failed gate is re-run to pass, history never rewritten); the promotion journal append-only (refusals are evidence too); the single active-deployment pointer per hosting environment moved ONLY by the governed store transaction (policy-enforced gate sufficiency + journal linkage — both typed refusals, both proven); rollbacks append-only events + pointer flips in ONE transaction; rows never deleted; CHECK-bound vocabularies and physical immutability triggers everywhere.
- **The gate evaluators** (`deploy/release.ts`): tool-run evidence (validation via the shared deploy:validate core; identity-audit recomputing the deployment identity at the exact revision — drift/tampering detection; migration comparing the target database's `platform.schema_migrations` ledger with the shipped set — unapplied-shipped, applied-but-unshipped (the DOWNGRADE hazard: database ahead of code) and checksum drift all fail closed with the ordered ledger digest recorded; health requiring readiness "ready"; preview/staging smoke through the shared deploy:smoke attestation; governance-check/typecheck/lint/full-test-suite as bounded exec evaluations) and external-attach evidence (ci-gates from the CI workflow conclusion; architect-approval — worker tooling records it, never fabricates it).
- **The cost/quota guards** (`src/platform/observability/alerts.ts` + `deploy/manifests/quota-guards.json`): snapshots from the AUTHORITATIVE stores only (compute-plane live claims vs environment quotas, queue backlog, dead letters, terminal-failed executions, database size); warn at 80% BEFORE exhaustion, critical at 95%; every alert carries an ACTION; the D-05 hard cap stays the overage guard (the claim beyond the quota is refused typed — no uncontrolled paid overage); a CRITICAL alert blocks promotion (the guardrail).
- **The observability plane** (`src/platform/observability/`): a provider-neutral SINK (traces, metrics, bounded structured logs) carrying the STABLE correlation identity — executionId, the D-03 dispatch correlation key, sandboxId, claimId, releaseId, requestId. The trace id is DERIVED deterministically from the primary business identity (fixed priority order), so an operator reconstructs an execution end-to-end from the execution id ALONE (AC4, proven end-to-end over real PG: dispatch correlation key → claim → disposition share one trace id). Secrets never enter telemetry: secret-shaped attribute KEYS are rejected outright; credential-shaped VALUES are redacted before buffering; rejected records are counted, never exported (the collector never receives them — the OTLP suite's wire proof). Boundedness is STRUCTURAL: buffer maxima, attribute counts, value lengths, message lengths, export batches and retries are hard-bounded constants; overflow is dropped and counted. The OTLP exporter speaks the documented OTLP/HTTP-JSON protocol over plain fetch (zero new SDKs; the sanctioned runtime import set stays fastify + pg); 2xx accepts, 401/403/404 permanent, 429/5xx/network transient with bounded retry; unconfigured = the declared logs-only degraded mode (the self-hosting default). The observability plane has NO database dependency and NO module imports (architecture B1/B3) — telemetry is write-blind (the discrimination proof: an exporter acceptance or a lying dashboard claim changes NO authoritative state).
- **The minimal correlation seams** (the ONLY existing-surface consumption, per the work order): `ExecutionWorkerFabricDeps.telemetry?` — optional, absent ⇒ zero behavioral change; the fabric emits bounded, non-throwing, reference-only observations at claim admission, delivery disposition, dead-letter and recovery-scan completion (the D-03 correlation key travels on every record); `ApiServerDeps.telemetry?` — one bounded log + metric per completed request through a LOCAL structural seam type (`RequestTelemetrySeam`, structurally satisfied by the platform sink — the pinned `src/api` import boundary stays untouched). The composition binds the deployment environment (`bindSinkEnvironment`; records arriving unbound are rejected fail-closed) and the worker service flushes on a bounded cadence with the OTLP bearer token resolved through the environment-scoped secret store immediately before export composition — never logged.
- **The CI/CD path** (`.github/workflows/deployment-release.yml`): a MECHANISM over repository tools (the self-hosting boundary — a self-hosted operator runs the identical `deploy:release` commands with equivalent effect; the workflow invokes only bun/repository scripts; the only actions are checkout/setup-bun/upload-artifact). `pull_request` = record + the fast evidence gates + the ENFORCEMENT PROOF (a promotion without its gate evidence must be refused — asserted in CI). `push to main` = the full local→ci gate ladder (governance, typecheck, lint, full-test-suite, validation, identity-audit) + the journal + pointer promotion + the ci-gates attachment + the release inspection artifact + the alert evaluation.
- **The environment isolation** (AC6): each environment's release ledger lives in ITS OWN PostgreSQL; cross-environment secret references are rejected fail-closed through the environment contract + the release tool's own resolution path (the discrimination proof: preview credentials do not satisfy staging/production bindings).
