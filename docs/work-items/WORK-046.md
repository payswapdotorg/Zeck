## Revision 1 (CHANGES REQUIRED response — the external run identity)

**The Architect finding on PR #10 (blocking; submission marked CHANGES REQUIRED, not merged):** the container runner derived its external `runId` only from the container configuration and the timeout — two different Zeck executions doing identical work could receive the same runner id and collapse into one external run; the provider-neutral runtime contract carried no execution/sandbox identity to prevent it. The fix must bind the external runner identity to the existing deterministic execution/sandbox identity while preserving same-execution replay convergence, with regression tests for both distinct-execution separation and same-execution idempotency.

**The fix (three seams, one derivation):**

- `src/platform/sandbox/runtime-client.ts` — the provider-neutral contract now carries the REQUIRED `ContainerRunOptions.runIdentity` (the durable execution-scoped identity of the logical run; documented derivation obligation: distinct logical runs never collapse into one external run, a replay of the same logical run converges to the same external id). This is the WORK-012 platform seam — outside the Work Order's declared module list, extended exactly as the Architect's fix directive requires (the provider-neutral runtime contract was named in the finding as the missing-identity surface).
- `src/modules/sandbox/adapters/container-provider.ts` — the provider composes the identity from the sanitized runtime spec's durable binding (`containerRunIdentity`: `zeck-run:<applicationId>:<executionId>:<sandboxId>`) and passes it with every dispatch. The sandbox row is the idempotency anchor: re-selection converges on the committed row, so the triple is stable per logical run (same-execution replay convergence) and distinct across executions (separation).
- `src/platform/compute/container-runtime.ts` — the external run id derivation binds the identity FIRST: `runId = "run-" + sha256([runIdentity, config, timeoutMs])[0:32]`; the run options are validated fail-closed BEFORE any wire call (non-empty bounded identity, positive integer timeout — an unidentified run is never dispatched). The protocol and derivation are documented normatively in deploy/README.md §D-05 ("The run-id derivation (identity binding)").

**The regression battery (8 new tests + the mutation check):**

- Protocol layer (`tests/integration/compute/container-runner-protocol.test.ts`, over real HTTP): distinct-execution separation (identical config + timeout + different identities → two distinct run ids, two 202 submissions, each result its own run's outcome); same-execution idempotency (same identity replayed → exactly one held run, the 202-then-409 submission record, converged outcomes); fail-closed identity (missing/empty/oversized/non-string identity, non-positive timeout → rejected with ZERO wire traffic).
- Provider layer (`tests/unit/sandbox/platform-seam.test.ts`): the run options carry the exact durable binding; two specs with identical task/limits but different execution/sandbox ids dispatch byte-identical configurations with DISTINCT identities (the identity is the only separator — the pre-revision defect's exact shape); the same spec re-derived twice yields the same identity.
- End-to-end (`tests/integration/postgres/worker-external-run-identity.test.ts`, over real PostgreSQL + the real provider + the real client over real HTTP): the full governed composition with only the runner HOST being the documented in-process protocol server — two executions carrying the IDENTICAL task object complete through the governed path while the runner holds exactly TWO external runs (both 202; each execution's recorded sandbox outcome maps to its own run); the same-execution recovery re-drive (the C4 crash shape) converges with exactly ONE external run and ONE submission.
