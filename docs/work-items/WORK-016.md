## Design decisions (architect-review pointers)

1. **The integration tree imports EXACTLY {executions, agents} public barrels + src/shared** (architecture-gated). This is the mechanical form of "integrate without duplicating authority": the adapter cannot decide policy, budgets, verification, capabilities, tools or model routing because those modules are not even importable from it — every such decision stays with the authorities the executions/agents services consult. The dependency engine's `cross-module-public-only`/`internal-never-cross-module` rules cover the integration zone (it classifies `src/integrations/` as a first-class zone), and the WORK-016 gate pins the narrower allowlist.
2. **WorkflowOS no-mutation is structural, not advisory (M1/M2/M9)**: the integration holds no outbound network channel, no SQL, no WorkflowOS SDK, no mutation verbs and no state-store classes — five independent scanners, each proven by a static mutant. The only WorkflowOS-facing surface is DATA (receipts): WorkflowOS decides what the evidence means for its own workflow state (ADR-0006's "the AI platform returns evidence and artifacts; WorkflowOS decides").
3. **Idempotency is delegated, never duplicated (§15)**: the submission passes the caller's idempotency key to the executions authority; same key + same fingerprint replays the durable outcome, same key + different fingerprint fails `IDEMPOTENCY_KEY_REUSED`, concurrent duplicates converge through PostgreSQL uniqueness arbitration — proven over real SQL (one row, one `execution.created` envelope). No idempotency store exists in `src/integrations/` or `benchmarks/`.
4. **BYOA = projection + sanitization, never authority (M19–M24)**: registration consumes the WORK-011 registry (the neutral descriptor maps into the canonical `AgentDefinition` — requested permissions are requests, policy decides); the runtime wrapper implements the agents module's public `AgentProvider` port and adds ONLY the sanitization boundary (thrown framework errors → honest session-failure observations with no internals; failure reasons bounded and single-line; rogue authority fields — status/permissions/executionStatus — structurally dropped: the observation surface is a closed four-field set). External frameworks are never NAMED anywhere in the tree (M10/M20 scanners; the doc comments included).
5. **The benchmark harness distrusts its strategies**: each strategy returns only execution IDs; every measured dimension is re-read from the executions authority's public reads. The MEASUREMENT surfaces (`harness.ts`/`report.ts`/`contract.ts`) hold no authority mutation call (scanner-enforced — the §21 non-authority rule made mechanical); the STRATEGY surface rides only the governed paths (executions transitions, session service, the integration submission seam) and holds no policy/budget/registry/verification mutation. Setup (agent registration through the canonical path) precedes measurement.
6. **Fair comparison without hidden privileges (§20)**: the three strategies share ONE wiring (one executions service, one admission chain, one submission contract) and drive the SAME canonical lifecycle (`authorize → plan → queue → start → verify → pass` with durable verification results — the only completion path in the platform). The agents are deterministic stubs (the comparison measures the governed paths, not live-model quality); the verification dimension is recorded through the canonical path with harness-identified provenance (`benchmark-harness`) — disclosed honestly in the environment block, never presented as independent evaluator judgment.
7. **The BYOA contract's home**: the frozen IMPLEMENTATION.md layout pre-declares exactly one integration directory (`src/integrations/workflowos/`), and the Work Order's declared surface is that tree — so the BYOA adapter contract lives under it with `Byoa*`-prefixed neutral exports from the integration's public barrel. The contract itself is framework-neutral and framework-free; if the architect prefers a dedicated `src/integrations/byoa/` directory, that is an additive Work Order amendment decision (disclosed here, not silently taken).

## Limitations

- No WorkflowOS SDK/client is wired (none is a declared dependency): the integration ships the provider-neutral submission/receipt contract; a real `@workflowos/*` client adapter would live ONLY in `src/integrations/workflowos/adapters/` (the dependency engine's pre-declared boundary) and requires a dependency declaration — an architect decision when the real WorkflowOS API contract stabilizes.
- The WorkflowOS→Zeck direction is inbound (WorkflowOS calls the adapter); a push-based WorkflowOS-facing event delivery (the reverse direction) would be outbound transport — deliberately NOT built here because it would be a WorkflowOS-state mutation channel unless carefully scoped; the receipts are pull-based (WOS-003's data-return semantics).
- BYOA external-agent execution is the external side's responsibility: the wrapper sanitizes observations but cannot police what the external framework does inside its own runtime — the governance boundary is exactly what crosses the port (references in, neutral observations out), which is the ADR-0013 model.
- The benchmark's verification dimension uses the canonical governed completion path with harness-identified provenance (`benchmark-harness`), not the verification module's independent evaluators — honest provenance, disclosed in every report's environment block; wiring real evaluators into benchmark tasks is future benchmark-surface work.
- Benchmark evidence is returned to the caller as a pure record; a durable benchmark-evidence STORE (persisted reports, history, comparisons over time) is a future surface (needs its own Work Order — benchmarks are non-authority measurement, and storing their outputs durably is a new surface decision).
- CI runs the architecture/unit/integration suites but not the real-PG suites (the standing WORK-002 flag: no PostgreSQL service in CI); PG proofs are local-verified against real PostgreSQL 17.11 and recorded above.
- The BYOA registration seam requires the caller to hold a governed actor (the registry's actor-scoped methods); production integration credential transport (per-application integration principals with scoped tokens) extends WORK-015's `authenticate` seam pattern — future auth-surface work.
