## The crash-safety standard (the architect's review bar for this wave)

Every side-effecting messaging operation (conversation-start, turn-reply, delivery-apply, human-escalation, conversation-close) owns ONE durable, recoverable operation row in migration 0020 (`deployments.messaging_operations`: PENDING → COMPLETED|FAILED, bounded stage checkpoints, monotonic `attempts`, terminal immutability, write-once identity core, no deletes — physical triggers), claimed BEFORE the rail side effect and completed AFTER every durable outcome, plus **STABLE rail-level idempotency keys** derived deterministically from the same durable coordinates across retries (a retry or crash-resume re-issues under the SAME key; the rail converges — exactly one upstream side effect, ever). A stage checkpoint marks the point of no return: resumption past it NEVER re-runs admission (the decision preceded the side effect) and completes the durable tail from the checkpointed facts.

## The messaging conversation model (design decisions)

- **The conversation is the channel-side twin of a governed Execution**: started through the executions public create seam (idempotent by key — the single birth path, walked authorize → plan → queue → start to RUNNING through the public transition surface); execution status is touched ONLY through public transition commands (`wait-human` for escalation). The deployments module owns none of the executions vocabulary (MG8).
- **One provenance authority**: conversation start, turns, delivery callbacks, escalations, failures, denials and completion ride the executions EventEnvelope ledger as step events (executions-owned `agent-session-started` / `agent-action-recorded` / `agent-session-completed` commands; semantic detail in payload/reference); `deployments.messaging_messages` is the CONVERSATION ledger — conversation state, the inbound idempotency ledger, ordering evidence and the `ledger_sequence` linkage — never a second event authority. Delivery state is EVIDENCE (the append-only `messaging_deliveries` ledger + the guarded monotonic projection on agent-reply rows), never a second execution state machine.
- **ORDERING SEMANTICS are explicit and declared per conversation** (the Work Order's implementation requirement): the conversation records its channel's `ordering_mode`. `thread-sequenced` channels supply a per-thread monotonic sequence; the fabric records the deterministic marker `in-order` (seq == max+1), `out-of-order` (seq ≤ max) or `gap` (seq > max+1) as EVIDENCE on the message row — async messaging cannot wait, so ordering never blocks dispatch. `unordered` channels get the fabric-assigned arrival ordinal (`assigned`). Global ordering is NEVER assumed.
- **THE IDEMPOTENCY KEY SCHEME** (stable, conversation-scoped where event-derived): the inbound event key is the upstream-supplied id OR the deterministic substitute `msg-<conversationId>-<threadRef|root>-<occurrenceOrdinal>`; every application-scoped key derived from an inbound event is scoped by the conversation identity (`scopedKey = <conversationId>:<eventKey>` — the turn-reply operation key `msgop:turn-reply:<scopedKey>`, the stable rail send key `msgrail:send:<scopedKey>`, the responder's `turnKey`, the budget `operationId`, the executions evidence keys) because event keys are unique per (application, CONVERSATION), not per application — a same-key message on another conversation is a different logical turn, never a collision (C23/S7). The reply row's send key is `<eventKey>:reply`. Delivery callbacks dedupe on the upstream callback id or `dlv-<conversationId>-<messageKey>-<status>`, scoped `<conversationId>:<callbackKey>`. Conversation starts, escalations and closes key on the caller idempotency key (application-scoped). Rail keys: `msgrail:open|send|escalate|close:<discriminator>`.
- **Admission ordering is frozen and pre-side-effect**: TENANT (server-derived, durable-row-decided) → planner route (the REAL planning module's deterministic-sufficiency decision through the planner-messaging-subtask-router) → POLICY (the REAL policies engine through the policy-messaging adapter) → CAPABILITY (the plan's declared capabilities + the rail's) → BUDGET (paid routes only; deterministic routes NEVER reserve) → SECRET (mediated rail-channel credential access, reference-only grants) → responder → rail send. Denials are journaled on both ledgers before the typed failure (`POLICY_DENIED` / `CAPABILITY_UNAVAILABLE` / `BUDGET_EXCEEDED` / `AUTHORIZATION_DENIED`); refused mediation releases the reservation.
- **Attachments live in the artifact plane**: messages carry bounded previews (≤512) and ARTIFACT REFERENCES (≤512 each, ≤8) only; the raw-secret nine-pattern refusal (WORK-011 discipline) rejects secret-looking free text at validation; the migration's attachments trigger makes embedded binaries physically unrepresentable.
- **Delivery callbacks are correlation-guarded and monotonic**: the callback resolves the outbound reply by its Zeck send key INSIDE the conversation (a callback for another conversation's message is unrepresentable — service guard AND the `msg_deliveries_correlated_guard` trigger); a mismatched rail message reference fails closed; the evidence row converges on UNIQUE (application, conversation, callback_key); the projection moves only FORWARD through the frozen vocabulary (pending → sent → delivered|undelivered; terminal immutable; a stale callback records evidence but cannot regress the projection — and CONVERGES instead of failing the recovery).
- **Escalation is a governed step, not a flag**: policy-designated, the public `wait-human` transition (auditable, idempotent by `${idempotencyKey}:wait-human`), the rail notice under the stable escalate key, the immutable record with the wait linkage; the conversation STAYS active (the human and the agent coexist in async messaging).
- **Version pinning, never drift**: the conversation pins (planId, planVersion) at start (physically immutable core); promotion/rollback move the deployment pointer for NEW conversations only; every turn reads the CONVERSATION's pin (S10 static mutant flags drift to the deployment's current pointer).
- **Migration discipline (parallel wave)**: **WORK-025 claims 0020** — `0020_messaging_conversations.sql` (five deployments-schema tables: `messaging_conversations`, `messaging_messages`, `messaging_deliveries`, `messaging_escalations`, `messaging_operations`), pinned in the file header; 0015 untouched (burned — WORK-019), 0016/0017/0018 untouched (WORK-022/020/024), 0019 left to the sibling WORK-021. Tenant scope is never dropped (composite `(application_id, tenant_id)` FKs to `applications.applications`); `execution_id` is a UUID reference WITHOUT FK by design (the executions module's idempotent identity is authoritative; provenance linkage only — recorded in the migration header); `messaging_operations.conversation_id` is deliberately FK-less (a conversation-start operation row is durably claimed BEFORE its conversation row exists — that ordering IS the crash window the ledger closes).
