## The crash-safety standard (the architect's review bar for this wave)

Every side-effecting media operation — **job submission, paid dispatch, observation application (poll or callback), job completion, cancellation, variant adoption** — owns ONE durable, recoverable operation row in migration 0021 (`deployments.media_operations`: PENDING → COMPLETED|FAILED, bounded stage checkpoints `job-recorded` / `dispatched` / `artifact-adopted` / `rail-issued` / `variant-adopted`, monotonic `attempts`, terminal immutability, write-once identity core, no deletes — physical triggers), claimed BEFORE the side effect and completed AFTER every durable outcome, plus **STABLE rail-level idempotency keys** derived deterministically from the claim-pinned durable job identity (`mediarail:dispatch:<jobId>` / `mediarail:cancel:<jobId>`; the budget reservation's `media-reserve:<jobId>`; the verification evaluation's `media-verify:<jobId>`; the adoption keys `out:<jobId>` / `variant:<key>`; the executions evidence keys `media:<jobId>:<class>`): a retry or crash-resume re-issues under the SAME key and every seam converges — exactly one upstream paid side effect per job, ever (MOD-013: "retries and callbacks are idempotent and cannot silently create uncontrolled paid duplicates"). A stage checkpoint marks the point of no return: resumption past it NEVER re-runs admission (the decision preceded the side effect) and completes the durable tail from the checkpointed facts.

### The defects the proofs found (all disclosed, all fixed)

1. **The concurrent-duplicate budget-reservation defect** (found by the C23/C22 key-discipline work, fixed in `5687de9`): the per-job keyed seams (budget operation id, evidence keys, the insert) derived from a per-invocation generated job id, so concurrent duplicates of one submission each reserved under DIFFERENT operation ids — orphaned reservations and budget double-holding. Fixed: the durable operation claim pins the job identity BEFORE any duplicate exists (`durableJobId = begun.record.jobId ?? jobId`) and EVERY keyed seam derives from that claim-pinned identity.
2. **The insertArtifact placeholder-count defect** (found by the PG jobs suite, fixed in `5e21c05`): the SQL store's artifact insert declared 15 placeholders for 16 parameters — the adoption path would fail at runtime against real PostgreSQL (the in-memory store masked it).
3. **The concurrent-duplicate forward-progression landing defect** (found by the PG jobs suite's N=8 race, fixed in `5e21c05`): concurrent duplicates of one submission race between their identical guarded job moves; the losers' guarded mutation failed closed `INVALID_STATE_TRANSITION` when the winner had already moved the row PAST their target along the forward pipeline. Fixed: `isMediaJobForwardProgression` convergence (SQL + in-memory parity) — a committed status past the target along the forward pipeline converges; genuine regressions and foreign-terminal states still fail closed.
4. **The jsonb key-order digest defect** (found by the P6 crash proof, fixed in `ffe8ca3`): PostgreSQL `jsonb` does not preserve object key order, so the observation body digest over a re-read `output_descriptor` disagreed with the caller's insertion-ordered digest — a legitimate same-body crash-resume replay failed closed `IDEMPOTENCY_KEY_REUSED` in the SQL store's conflict-path arbitration. Fixed: `mediaObservationBodyDigestBase` digests the recursively key-sorted canonical form (key-order-invariant; a same-key/different-BODY replay still fails closed; array order preserved). Red/green validated: with the fix reverted, P6 fails exactly at the conflict-path arbitration; with it, all 10 P-proofs pass. The unit C-proofs had passed because the in-memory store preserves key order — only the SQL path had the defect (the WORK-025 P5 precedent: the PG proof's value demonstrated). A unit regression test pins the jsonb round-trip property.

Earlier-round test-infra fixes (disclosed for completeness): `e172951`/`55fd121` fixed leftover compile/assert defects in test fixtures from the crashed rounds (a typed verification-gate fixture, an indexed-access guard, unused fixtures, and bun `toMatchObject` needing `stringMatching` for message regexes) — no source-semantics change.

## The media job model (design decisions)

- **A media job is the generation-side twin of a governed Execution** (the invariant #1): execution identity is established only through the idempotent public create seam (`${idempotencyKey}:execution`); status moves ONLY through public transition commands (verify/pass/fail/cancel) driven by the deployments media ledger adapter; provenance rides the executions EventEnvelope ledger (executions-owned vocabulary; the media tables are job state + idempotency + observation evidence + `ledger_sequence` linkage — never a second event authority). MG8/MG9/S14 enforce this structurally (an execution-transition method on the store port is a flagged mutant).
- **The closed lifecycle**: `submitted → dispatching → generating → verifying → completed|failed|cancelled` with terminal immutability and no second media/execution state machine. Provider states are NORMALIZED at the rail adapter into the closed observation vocabulary (`accepted`/`progressed`/`provider-completed`/`provider-failed`/`provider-cancelled`) — a raw provider state string is never a job status (S13: opening either vocabulary is flagged, domain AND migration CHECK).
- **THE IDEMPOTENCY KEY SCHEME** (stable, claim-pinned): the job-submission operation keys on the caller idempotency key (`mediaop:job-submission:<key>`); the durable claim PINS the job identity before any concurrent duplicate exists, and every per-job seam — the paid-dispatch operation (`mediaop:paid-dispatch:<jobId>`), the rail keys (`mediarail:dispatch|cancel:<jobId>`), the budget operation id (`media-reserve:<jobId>`), the verification key (`media-verify:<jobId>`), the adoption keys (`out:<jobId>` / `variant:<callerKey>`), the evidence keys (`media:<jobId>:<class>`) — derives from that ONE claim-pinned identity (C22). Observation application keys on the job-scoped observation key (`mediaop:observation-apply:<jobId>:<observationKey>`); the observation key is the upstream callback id/poll discriminator or the deterministic substitute. This is the fix for defect 1: concurrent duplicates converge on the SAME keyed seams instead of creating orphaned reservations.
- **Provider completion is an OBSERVATION, verification controls completion**: a `provider-completed` observation moves the job to `verifying` and runs the deterministic postprocessing shape check; when `verification.mode = required`, the verification authority's verdict is consulted under `media-verify:<jobId>` (a crash-resume re-consult converges on the recorded conclusion — C15); `criteriaMet=false` or a shape-check rejection FAILS the job — unverified output can never reach `completed` (S9/S10).
- **Budget-before-paid-dispatch is structural**: the reservation (amount = the rail's declared per-kind cost, never a caller assertion) is made and recorded on the job row BEFORE the rail dispatch, which is its OWN durable operation under the stable rail key; settle happens after the durable dispatch facts; refusal/failure/cancellation paths RELEASE. P10 proves the pre-settlement crash window: a job left `dispatching` without a rail reference cancels and the HELD reservation is physically refunded.
- **Artifacts are adopted, never re-implemented**: `MediaArtifactAuthority` wraps the artifacts public service (put-if-absent convergence by full identity — parents + sourceRefs are identity-bearing, so a lineage-dropping mutant produces a DIFFERENT digest and the S11 probe catches it); the deployments `media_artifacts` rows are the adoption ledger linking job ↔ digest ↔ lineage ↔ pinned version, write-once.
- **Version pinning, never drift**: jobs pin `(planId, planVersion)` at submission (physically immutable identity core); promotion/rollback move the deployment pointer for NEW jobs only; the v1 job completes on its pin (AC7, PG record).
- **Migration discipline (parallel wave)**: **WORK-026 claims 0021** — `0021_media_generation_jobs.sql` (four deployments-schema tables: `media_jobs`, `media_observations`, `media_artifacts`, `media_operations`; 12 guard triggers, 8 indexes, closed-vocabulary CHECKs, unique arbitration keys), pinned in the file header; 0015 untouched (burned — WORK-019), 0016/0017/0018/0019/0020 untouched (WORK-022/024/021/025), 0022 is the sibling WORK-028's (its file is not in this branch). Tenant scope is never dropped (composite `(application_id, tenant_id)` FKs to `applications.applications`); `execution_id` is a UUID reference WITHOUT FK by design (the executions module's idempotent identity is authoritative; provenance linkage only); `media_operations.job_id` is deliberately FK-less (a job-submission operation row is durably claimed BEFORE its job row exists — that ordering IS the crash window the ledger closes).
