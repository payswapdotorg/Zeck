## Design decisions (architect-review pointers)

1. **Learning is an observation island (the §10 invariant made physical).** The learning module imports NO other module — not even public barrels (the architecture test + the shared discrimination scanner prove it; every M2–M6/M17 static mutant is detected). Its only outbound seams are its OWN ports: `LearningStore` (durable appends/reads of its OWN tables) and `DigestPort` (sha256 through the crypto-confined node adapter). There is no policy seam, budget seam, capability seam, execution-transition seam, route explorer, dispatch surface or provider adapter anywhere under `src/modules/learning/` — a live side effect or an authorization is UNREPRESENTABLE in the wiring, not merely avoided (M7: the deps surfaces are pinned by name in the scanner).
2. **One authoritative observation per source execution.** The durable identity of telemetry is `(execution_id)` — UNIQUE at the storage boundary with converge-or-fail-closed semantics: identical re-observation (same canonical fingerprint over everything except identity/wall-clock) replays the durable row; a conflicting re-observation fails `IDEMPOTENCY_KEY_REUSED` (the observation of one execution can never silently fork into two "facts"); concurrent duplicates converge through the unique-index arbitration (PG proof: two concurrent ingests of the same execution land ONE row, both callers receive the same telemetryId).
3. **Scorecards are immutable versioned cumulative snapshots.** Every version aggregates the full immutable observation history up to its `computedAt` (window bounds recorded — consumers can reconstruct the exact evidence population); version N+1 requires NEW evidence (no version churn without observation); version monotonicity is arbitrated by `UNIQUE(application_id, definition_id, scorecard_version)` — concurrent builds converge onto the durable winner (the service re-reads and returns it); rows are physically immutable (triggers reject UPDATE/DELETE — M9's "historical scorecards never mutate silently"). The aggregation definitions are a FROZEN registry (route/tool/environment/plan/subgraph by task class): extending it is a reviewed version bump, never an in-place edit.
4. **Uncertainty is preserved, never collapsed (§13).** Entries record integer population + success count (the point rate is derived and recorded); uncertainty is an honest classification from the binomial 2-sigma spread (low/material/high + machine-readable reason code); sub-minimum populations are EXCLUDED with the pre-filter population still recorded (`totalPopulation` — the exclusion is visible, never silent); shadow comparisons are `inconclusive` when the proposed/baseline success-rate intervals overlap — a forced winner under overlap is unrepresentable. A shadow result is never a production result (M15: record class CHECK-pinned to `shadow` in domain AND migration).
5. **The planner READS; learning never commands (§9).** The consultation happens AFTER the governed selection (the pipeline order is the protection — the discrimination scanner pins the ordering: `selection-segment-references-learning` and `consultation-before-selection` are both detectable mutants) and is captured as evidence INSIDE the durable decision record. Learning's preference considers ADMISSIBLE candidates only (a forbidden route with a perfect score is neither selected nor preferred — R-M1); deterministic-first is untouched (a sufficient deterministic task stays zero-model with an EMPTY consultation — nothing fabricated); an unversioned/malformed signal fails the planning request CLOSED (M13 on the consumer side: the planner never silently degrades on corrupt learning data).
6. **Shadow evaluation is side-effect-free by construction.** The evaluator's deps are store + digest + clock + ids ONLY; it consults the LATEST durable scorecard version (the exact versioned basis recorded — M13) and appends one immutable `shadow` record. The runtime red records instrument a full governed world (spy policy authority, spy route explorer, real executions service) and observe ZERO authority/dispatch interactions; the PG proof observes the execution ledger UNCHANGED. Adoption of any learning-derived strategy re-enters the normal governed planning path — nothing here can shortcut it.
7. **Ratings are immutable evidence (§12, ADR-0009/0012).** The durable identity is `(execution_id, evaluator_id, rating_dimension)`: duplicate submissions converge, conflicting re-ratings fail closed (evidence never forks); the bounded [1,5] scale, provenance (source user|human + submission channel + optional request ref) and non-empty evidence refs are CHECK-bound; rows are immutable (M16: a rating gains no authority — the runtime red record observes zero policy interactions; ratings never cross the planning READ seam).
8. **Deterministicization compatibility without deterministicization (§11, M19).** Telemetry preserves per-subgraph identity (`subgraphId`/`stepPath`/`computationType` — the planning `SubgraphObservation` vocabulary) so future WORK-021 analysis can answer "these N executions using model X followed the same subgraph". The `subgraph-frequency-by-task-class` definition aggregates exactly that identity. WORK-014 records identity + outcomes; it performs NO code synthesis, NO promotion, NO rollout — the scanner detects any promote/canary/rollout vocabulary appearing in the learning module (M19 static).
9. **Provider neutrality (M18).** Routes cross as opaque neutral `{provider, model}` strings exactly like the planning `PlanStepRouteRef` and the policy restriction vocabulary; the provider-identifier scanner runs over every non-adapter learning file (a leaked `Anthropic`/`OpenAI`/… identifier is a detectable mutant); the SQL store parameterizes routes as JSONB — no provider SDK type ever enters the domain.

## Limitations

- Learning ingestion is a service API, not yet wired to automatic execution-terminal observation collection (a platform-internal scheduler/dispatcher integration is future surface — no Work Order has declared it); the telemetry contract, validation, idempotency and durability are complete and proven.
- `consultSignals` reads the LATEST scorecard version only (version-history consultation is a consumer-side concern; the store exposes `getScorecard` for exact-version reads).
- The in-memory learning store is the reference-semantics adapter; production composition uses `SqlLearningStore` (both prove the same invariants; only SQL is the durable authority).
- The scorecard population window is cumulative-by-default (`recordedFrom: null`); time-boxed windows are constructible through the store's `listTelemetry` window parameters (the definition registry does not yet declare windowed definitions — future definitions are versioned registry additions, not edits).
- Uncertainty classification uses binomial 2-sigma thresholds (documented constants `MINIMUM_POPULATION_FLOOR = 5`, spread bands 0.1/0.2); Bayesian/sequential methods are future learning work (WORK-017+).
- CI runs the architecture/unit/integration suites but not the real-PG suites (the standing WORK-002 flag: no PostgreSQL service in CI); PG proofs are local-verified against real PostgreSQL 17.11 and recorded above.
- The user-rating surface is the durable evidence shape + idempotent append; the HUM-001..003 selective-rating trigger/promotion flows belong to WORK-022.
