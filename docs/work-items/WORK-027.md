## The governed computer-use standard (the architect's review bar — the ENTIRE Work Order)

Computer use is a **fallback computational mode, never an authority and never an unrestricted side-effect channel**. One capability family spans three interaction modes — deterministic/API, isolated browser automation, isolated desktop/terminal interaction — under the SAME authorities every other tool answers to: policy admission (the REAL WORK-007 engine), capability admission (the REAL WORK-005 registry), budget admission (the REAL WORK-004 wallets — reserve the FULL route ceiling BEFORE any stage's spend), tenant scope (the frozen executions binding), secret mediation (the REAL WORK-003 connections module; reference-only grants) and provenance (the FROZEN executions module's canonical EventEnvelope ledger through the `recordStepEvent` seam).

Side effects occur ONLY after the full admission chain; the deterministic-first route evaluation is a PURE planning preference (an API/deterministic route that covers the task with verified confidence starts — and stays — deterministic with ZERO GUI dispatch; the GUI ladder `deterministic → browser → desktop` ascends EXACTLY one rung at a time and ONLY on RECORDED, digest-verified insufficiency of the prior stage). Every side-effecting operation — session create, action dispatch, escalation, termination, environment open/close — flows through the DURABLE, RECOVERABLE OPERATION STATE (`tools.computer_use_operations`: PENDING → COMPLETED|FAILED, stable keys, stage checkpoints, terminal immutability — the WORK-024 crash-safety standard) with stable idempotency keys on every durable row, ledger event, wallet finalization and external effect. A crash at any boundary leaves the honest PENDING row; a re-booted process over the SAME world converges with EXACTLY ONE durable side effect per stable key.

## Design decisions

- **One capability family, three modes, one authority set**: the computer-use domain defines the deterministic/browser/desktop capability contracts and the governed session service composes the SAME authorities every tool answers to through REQUIRED seams (architecture CU2/CU3 pin the seam set and the deps — no additional authority handles, no default-allow path anywhere).
- **The deterministic-first routing is a pure function, never an authority**: `evaluateComputerUseRoute` runs BEFORE the durable claim (architecture CU4); a sufficient verified deterministic route yields zero GUI dispatch; the GUI ladder ascends exactly one rung on RECORDED insufficiency (the digest is verified over a REAL failed action of the prior stage — a fabricated digest, a tampered action or a sufficient-route displacement all fail closed, discrimination S4).
- **Subordinate bookkeeping, no second execution state machine**: every migration-0023 table FK-references the EXISTING execution identity; execution status is NEVER written here; provenance rides the CANONICAL EventEnvelope ledger through the frozen `recordStepEvent` seam with the tools producer vocabulary (tool-requested/tool-result/tool-denied — the WORK-010 discipline). Architecture CU9 gates the subordinate-bookkeeping property; S12 flags any execution-transition method on the store port or any ledger-vocabulary opening.
- **The crash-safety standard is the WORK-024 durable-operation discipline**: every side-effecting operation claims a keyed PENDING operation row first, records stage checkpoints (the session/action identity recovery points), and completes/fails terminally; every ledger event, wallet finalization and external effect carries its own stable key. The committed-effect distinction: a durable terminal row (a session, an action, an escalation, a terminal session) IS the committed-effect proof — the replay converges the operation row, the ledger evidence and the settlement onto it (the five fixed defects above were all violations of exactly this discipline).
- **The external-effect keys**: `cu-env-open:<sessionId>:<mode>` / `cu-env-action:<sessionId>:<actionKey>` / `cu-env-close:<sessionId>` on the environment seam; `cu-terminal:<sessionId>:<actionKey>` on the sandbox rail; `cu-budget-reserve:<sessionId>` / `cu-budget-settle:<sessionId>` / `cu-budget-release:<sessionId>` on the wallet. One external effect, one ledger event, one wallet finalization per key — across process death.
- **Credentials are references, never values**: the secret-mediation seam over the REAL connections module yields an opaque grant reference stored in the admission bundle; the BYOK material is scanned for in EVERY durable computer-use byte by the proofs; secret-shaped observation content is refused BEFORE persistence (the fail-closed evidence model).
- **sandbox/deployments surfaces**: `src/modules/sandbox/` is used through its EXISTING public seams only (the terminal executor composes the sandbox service + environment catalog; zero sandbox-tree modifications — the surface was declared in case a seam was required, and none was). **`src/modules/deployments/` was NOT modified** — no computer-use deployment seam was required (the isolated environments are provided by the sandbox catalog; recorded as honestly unused).
- **Migration discipline (parallel wave-5)**: **WORK-027 claims 0023** — `0023_computer_use_sessions.sql` (five tools-schema tables: `computer_use_sessions`, `computer_use_escalations`, `computer_use_actions`, `computer_use_observations`, `computer_use_operations`), pinned in the file header AND here; 0001–0022 untouched (0015 burned by WORK-019; 0021 WORK-026's, 0022 WORK-028's — both merged in the frozen base). The only change to any sibling's tests is the `9bf0360` migration-tail assertion fix (disclosed above). Tenant scope is never dropped (composite `(application_id, tenant_id)` FKs).
