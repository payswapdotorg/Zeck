## Design decisions (architect-review pointers)

1. **Admission order follows IMPLEMENTATION.md §7** (the repository-canonical dispatch sequence): identity/tenant + execution binding → tool resolution (registry) → POLICY admission → BUDGET admission → CAPABILITY admission → durable intent → dispatch. The Work Order prompt carried two orderings (its "mandatory execution flow" puts capability first; its "authority chain" puts policy first) — the repository-resident specification is authoritative and matches the only implemented dispatch seam (the models gateway: policy before capability). The scanner pins the §7 order (M20 flags policy-after-capability).
2. **The invocation row IS the idempotency authority.** One row per `(application_id, invocation_key)` — the same durable contract as `platform.idempotency_records` on the module's own journal (the WORK-003 dispatch-journal precedent: idempotent by its own key). Same key + same fingerprint replays the same durable outcome; different fingerprint fails `IDEMPOTENCY_KEY_REUSED`; concurrent identical claims converge through PostgreSQL unique-index arbitration (the loser's insert waits for the winner's commit, then adopts the committed row — proven N=4 on real PG).
3. **Durable intent precedes the adapter call (§14); the ledger result event precedes row finalization.** `claimDispatching` (durable intent) → `execution.tool-requested` (idempotent append, bound to the row while dispatching) → adapter → normalization → `execution.tool-result` (deterministic payload — no timing values, so retries replay the same envelope) → guarded `recordOutcome` (first-writer-wins `WHERE status='dispatching'`) → budget settle/release. Terminal rows are physically immutable, so the result sequence binds while dispatching; a crash between event and finalization leaves the row honestly `dispatching` and the retry converges — a terminal row without its result envelope is unreachable by construction.
4. **Crash recovery: converge or fail closed.** A committed `dispatching` row is the honest §14 unknown-outcome state. Retry with a contract-idempotent tool re-executes and converges (safe by the contract's own declaration); a non-idempotent tool fails closed `NON_CONVERGENT_EXTERNAL_EFFECT` rather than silently guessing (§14's non-convergence rule). The recovery path does NOT re-evaluate admissions — the original admission evidence is durable on the row (documented in code).
5. **Budget admission is fail-closed for costed tools.** The authority is optional at construction (free deterministic tools need none) but a tool declaring `estimatedMicroUsd > "0"` with no wired authority is denied `BUDGET_EXCEEDED` — costed work never executes unbudgeted (deny-by-default; the scanner pins the check, M6). Reservations use deterministic operation ids (`tool-invocation:<key>`) so concurrent duplicates and retries converge on ONE reservation; actual usage settles once on success; the hold releases on tool failure and on post-reservation capability denial; the replay fast path re-attempts settlement (idempotent keys) to reconcile a settle-crash.
6. **Step events are executions-owned; tools only produce them through the public seam.** `recordStepEvent` appends `execution.tool-requested|tool-result|tool-denied` envelopes through the SAME single write path (`appendEvent` + `updateExecutionForTransition`, status-preserving — the policy-denied precedent), keeps the executions module the sole ledger authority, and physically cannot move the state machine (terminal rows reject updates). The tools module holds no SQL against the executions tables (scanner-enforced); the vocabulary (`STEP_EVENT_COMMANDS`) is owned by the executions domain so WORK-011 (agents) extends it without touching tools.
7. **The adapter port's shape IS the customer-domain-authority protection.** Adapters receive `(dispatch, context)` — identity, validated input, tenant binding, deadline — and return a `ToolObservation`. They are never handed stores, services, execution-mutation surfaces or any platform authority handle: criterion 4 holds by unrepresentability, not convention (architecture-gate-tested).
8. **Outcome classification is physically tool-axis-only.** `outcome_class ∈ {tool-success, tool-failure}` is CHECK-bound (migration 0005); verification vocabulary (`PASS|FAIL|INCONCLUSIVE`) and provider-axis classes are unrepresentable at the storage boundary. Admission refusals carry `denial_class` (policy|budget|capability) and surface as their canonical codes (`POLICY_DENIED`/`BUDGET_EXCEEDED`/`CAPABILITY_UNAVAILABLE`); tool failures surface as `TOOL_ERROR`-axis records with typed failure classes (`tool-execution|output-contract|adapter-error|timeout|unknown-outcome`). A tool outcome NEVER produces verification evidence.
9. **Deterministic tools are first-class (ADR-0007).** The shipped built-ins (`calculator` — bigint arithmetic; `schema-validator` — the domain's pure field-schema check) declare `deterministic: true`, `sideEffect: none`, zero network/secrets/cost and execute through the identical admission chain with NO model anywhere; the tools module imports neither models nor agents (scanner-enforced). Side-effecting tool CLASSES (filesystem/terminal/HTTP/browser/…) arrive with their owning adapters in later Work Orders; their ADMISSION semantics (side-effect class, network/secret declarations, policy gates, §14 ordering) are fully specified and enforced here — test adapters with `write-external` classes prove the ordering and budget discipline.
10. **Concurrent duplicates may re-dispatch only contract-idempotent tools.** Two same-key callers can both execute an idempotent tool's adapter (safe by contract); both converge on ONE durable row/outcome (guarded finalization) and ONE ledger pair (idempotent append keys). A non-idempotent concurrent duplicate fails closed on the loser (`NON_CONVERGENT_EXTERNAL_EFFECT`). Strictly-once adapter execution would require holding a transaction across the external call — rejected (the §14 journal discipline deliberately avoids that).

## Known limitations

1. **Tool CLASSES beyond the two deterministic built-ins ship as contracts + runtime, not as production adapters.** Filesystem/terminal/HTTP/browser/search/DB tool adapters belong to later Work Orders (WORK-012's sandbox seam, WORK-018's synthesis); their admission semantics (side-effect class, network/secret declaration, policy gates, §14 ordering, budget discipline) are fully specified and enforced here — proven with test adapters carrying `write-external`/network declarations. The built-ins cover the deterministic-first path (ADR-0007) end to end.
2. **Concurrent duplicates of a contract-idempotent tool may dispatch the adapter more than once** (safe by the contract's idempotency declaration; both writers converge on one durable row/outcome/ledger pair). Strictly-once adapter dispatch would require holding a database transaction across the external call — deliberately rejected (§14 journal discipline; design decision 10).
3. **Budget reservation for a costed tool is not atomic with the tools durable-intent insert** (cross-module transactions are impossible through public barrels). A crash in that window leaves a converged-by-key reservation that the retry reuses or the reconciliation path releases; an un-retried orphan stays active until a future budgets reconciliation job (the models dispatch-journal has the identical disclosed window).
4. **The `dispatching` recovery path does not re-evaluate admissions** (the original admission evidence is durable on the row — a policy change between crash and retry cannot retroactively deny an already-admitted-and-possibly-executed invocation). Documented in code; consistent with §14 convergence semantics.
5. **Real-egress tool adapters would materialize secrets through the connections vault seam** (post-admission, like the models fabric); no shipped tool declares secret access yet, so the `CredentialMaterializer` wiring is exercised by no production adapter this round — the policy dimension (secret-ref facts through `admitDispatch`) IS wired and tested via declared contract refs.
6. **CI has no PostgreSQL service** (carried over, governance-flagged since WORK-002): the 23 real-PG tools tests skip with an explicit reason in CI; local runs against a real PostgreSQL 17.11 server are the recorded proof (standing precedent). One disclosed vitest-layer teardown transient (57P01 during suite-database drop, zero failing tests) in one of three full runs — the WORK-005/007 disclosed class.
