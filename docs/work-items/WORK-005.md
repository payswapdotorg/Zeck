Key mechanics:
- **Registry-as-single-authority**: capability facts enter the world ONLY through `registry.publish()`, which validates (shape, frozen kind/evidence vocabularies, neutral slug ids, numeric versions, primitive attributes, mandatory evidence reference, provenance), then arbitrates transactionally in-memory under the module lock. Resolution is served exclusively from the arbitrated catalog — never from raw adapter output. There is no second capability authority, no parallel state machine, and no path around validation.
- **Arbitration rules** (claim identity `(id, kind, version)`, one kind per id): invalid → rejected; kind conflict → rejected; identical republish → converged (original record retained verbatim — evidence durability); same version with different attributes → rejected (versions are immutable once arbitrated; corrections are new versions); otherwise accepted with `catalogRevision` +1.
- **Ordering boundary**: `ModelGatewayDeps.capabilities` is REQUIRED (mirroring the admission discipline — a gateway cannot be constructed without a capability authority; no default/bypass implementation exists, proven statically). The gate input is the task profile ONLY (rail-agnostic by construction): capability resolution cannot see the provider, and provider selection cannot precede resolution.
- **Denial symmetry**: capability denials journal through the same `recordDenial` evidence path as policy denials (reason `capability-unavailable: <id>(<why>)…`), then surface canonical `CAPABILITY_UNAVAILABLE` — no new error vocabulary (`tests/unit/errors.test.ts` taxonomy sync untouched).
- **Adapter publishing**: both rails export fact publisher functions; descriptors for shared capabilities (`text-generation@1.1.0`, `structured-output@1.0.0`, `streaming-generation@1.0.0`, `tool-use-generation@1.0.0`) are IDENTICAL neutral claims — the second rail's publish converges to one arbitrated claim (cross-rail convergence proven), with each rail's specifics retained only in provenance/evidence references.
- **Seeds earn their place**: the code-resident seed catalog is arbitrated through the identical publish path at construction; a seed that failed validation would fail construction (proven).

## Design decisions (architect-review pointers)

1. **No new durable DB state — deliberate, not an omission.** "Persist durable authority state transactionally where required" (`IMPLEMENTATION.md` §15 / Work Order requirement 4): the arbitrated capability catalog is a VERSIONED, CODE-RESIDENT dataset (seed + adapter facts) rebuilt at composition; a fact's durability requirements are satisfied by (a) the frozen seed in source control and (b) adapter facts being re-publishable deterministically from the owning adapter files. Nothing a caller writes needs to survive a process restart, so there is no durable-authority boundary that a migration would own — introducing tables would ADD an authority surface without a requirement driving it (and migrations are Implementer A's parallel surface this wave). The `CapabilityCatalogStore` port keeps the storage boundary explicit so a future Work Order that needs durable, tenant-scoped capability observations can swap in a SQL adapter without touching the authority logic. Consequence, disclosed honestly: **all WORK-005 verification beyond the existing suites is in-process**; no new real-PG suites were added because no new PG state exists (the full existing real-PG battery — 54 tests incl. the dispatch journal that now also records capability denials via the unchanged `recordDenial` path — runs green).
2. **In-memory arbitration is still transactional.** Publish decisions serialize under the module lock: concurrent identical publishes converge to exactly one accepted record + one revision; concurrent distinct publishes lose nothing; resolutions read snapshot copies and never observe half-applied arbitration (both proven in `capability-registry.test.ts`). This is the honest in-memory equivalent of the WORK-002/003 transactional-arbitration discipline; there is no crash-atomicity obligation because no durable state exists (a crash discards only rebuildable catalog state).
3. **The gate sits between admission and rail resolution — the canonical §7 position.** `IMPLEMENTATION.md` §7 orders … effective policy → budget reservation → capability resolution → plan → dispatch authorization → adapter call. Policy admission still precedes dispatch (unchanged, re-proven); capability resolution precedes ALL provider/rail selection (new, proven); budget reservation is not in the models fabric (WORK-004's authority, not re-ordered here). The frozen WORK-003 gateway sequence is preserved with one strictly-additive step — all pre-existing order/isolation/byok/transport-durability suites pass unmodified except for the required-dep wiring.
4. **`ModelRequest.taskProfile` is optional in this wave — the boundary is the ORDERING, not profile mandating.** Deriving task profiles is `/planning`'s authority (INT-001, a future Work Order). An absent profile resolves the empty profile through the SAME gate (the gate is always consulted; construction without it is impossible). Until planning exists, callers declare profiles; WORK-005 enforces and proves what INT-002 names: capability requirements resolve BEFORE provider/model selection. Known limitation #1 below.
5. **Rail-level claim binding (which rail can SERVE a satisfied claim) is deferred to `/planning`.** `spec/architecture.md` §12 / the rail-registry header reserve capability/quality/cost/latency ROUTING for the planning Work Order; binding claims to rails here would create a second routing authority. WORK-005 delivers the authority + the ordering boundary; adapters' facts are in the catalog for planning to consume.
6. **Provider-neutrality proven at three layers**: statically (the shared scanner over the real `src/modules/capabilities/` tree — the capabilities sources contain no provider identifier or rail slug by construction), by mutation (synthetic leaks into the vocabulary are flagged), and at runtime (the actual adapter-published descriptors serialize without provider specifics; identity lives in provenance/evidence, exactly where `spec/contracts.md` wants provider detail retained).
7. **Validation is injectable FOR DISCRIMINATION ONLY.** `CapabilityRegistryOptions.validateFact` exists so the R3 mutation record can prove the published-fact rejection lives in validation (an accept-anything registry demonstrably admits the invalid fact). The default is the pure domain validator; the injection point is documented as a discrimination hook, and the seed path uses the same default (a tampered default would fail R1, the seed-construction test, and the validation unit suite).
