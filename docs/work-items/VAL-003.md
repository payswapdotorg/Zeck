## Corpus shape

- **`CORPUS_VERSION = "val-corpus.1.0.0"`** — append-only growth bumps the minor digit; removing a scenario is a MAJOR version (a documented, Architect-reviewed invalidation event).
- **22 workload families** (the roadmap's coverage list; the Tech Lead contract separates voice and realtime voice) × **440 golden tasks** (20 per family minimum, exactly at the documented floor), each carrying: task input, controlled environment state, expected outcome, ≥1 forbidden outcome, quality rubric (weights sum to 1), ≥1 safety constraint, evaluation method, determinism classification, provenance, and (where relevant) latency targets and capability requirements.
- **Scenario families** (`benchmarks/validation/corpus/scenario.ts`): parameterized definitions expanding deterministically to tasks with stable identities `<scenarioId>#<index>`.
- **Outcome/state separation (AC3):** `expectedOutcome` holds response-quality expectations (terminal status, verification, output shape, containsText); `expectedEnvironmentEffects` holds actual state-effect assertions (artifact-created, tool-invoked, approval-recorded, state-transitioned, side-effect-count) — 113 tasks assert environment effects, all the rest are quality-judged.
- **Safety (AC4):** every task carries safety constraints; 100+ adversarial/edge rows; prompt-injection defense constraints on 21+ rows; authority-boundary constraints on all authority-sensitive families; human-confirmation on the HITL gates; secret-flow and data-boundary guards scenario-wide.
- **Determinism (AC5):** evaluation methods split deterministic (exact oracles: coding tests, structured extraction, tool traces, routing matrices, event ordering) / tolerance (stated numeric bands: WER, IoU, accuracy) / evaluator (rubrics resolved by the VAL-008 scoring engine). The schema REJECTS a deterministic evaluation backing a nondeterministic-tolerance task.
- **Capabilities:** capability-requiring families declare neutral `requiresCapabilities` strings resolved by the VAL-009 matrix — an absent capability is a NOT RUN boundary, never a silent pass.
- **Provenance (AC7):** every task records `synthetic-authored / repository-license / external: false` — the corpus contains NO external material, no production secrets, no personal data.
- **Fixture manifest (AC5/AC7):** `fixtures.ts` declares all 39 fixture keys with determinism classification, materialization recipe (embedded-document / deterministic-generator / synthetic-media-recipe / workspace-blueprint) and the owning work order; integrity is checked both directions (no undeclared keys, no orphan manifest entries). Media fixtures materialize in the app portfolio (VAL-014+).
- **Run metadata (AC6):** `runMetadataForTask` builds VAL-001 `RunMetadata` with `corpusRevision = CORPUS_VERSION` and the task identity + scenario in the run configuration — every run id is deterministic AND task-distinct (tested).
- **Growth (AC8):** append-only identities; assembly is pure module composition (no environment, no randomness — fingerprint-tested); adding rows/scenarios never changes historical identities.

## Issue findings and protocol

- **Determinism/evaluation mismatches (classification: validation-defect).** Reproduction: the schema validator rejected three scenario families (browser-use ×2, research.fact-check, customer-service.escalation) whose evaluation method was `deterministic` while the classification said `nondeterministic-tolerance`. Impact: none (caught at corpus definition time — exactly what the gate is for). Root cause: authoring drift between the two fields. Viable solutions: weaken the schema rule (rejected — it is the honesty gate), reclassify the scenarios (chosen), split evaluation methods. Recommended: reclassify — those scenarios' outcome assertions are exact comparisons; nondeterminism lives in the path, not the verdict. Trade-offs: none observed. Verification: `deterministic evaluation never backs a tolerance task` test green.
- **Task identity missing from run metadata (classification: validation-defect).** Reproduction: two different corpus tasks produced the SAME run id. Impact: run-level traceability (AC6). Root cause: `runMetadataForTask` did not bind the task identity into the digested configuration. Fix: the run configuration now carries `corpusTask` + `corpusScenario`. Verification: `different tasks produce different run configurations` test green.
- **Environment-effect coverage initially thin (classification: validation-defect).** 33 of 440 tasks asserted state effects. Fix: scenario-level effect defaults for the state-bearing families (coding/structured/research/tools). Verification: 113 effect-asserting tasks; separation test green.
